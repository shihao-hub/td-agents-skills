# 阶段④：接口设计

> 主入口见 SKILL.md。输入是阶段③冻结的概念模型 + 用例走查表。接口是概念模型的「外部投影」，也是它的第一次压力测试。

## 为什么接口在物理 DDL 之前

1. **接口是团队契约**（前端/调用方依赖），上线后难改；表结构是内部实现，可演进而不动接口。先定难改的，后定易改的。
2. **接口设计会反推数据需求**：设计「GET /orders 响应要商品名」时，才发现订单明细要存快照——概念模型的规则在接口层被激活。
3. 接口先定，前端并行开工，协作解耦。

## 设计步骤

### 1. 资源命名

- 用名词复数：`/orders`、`/products`，不用动词（`/createOrder` ❌）
- 层级表达从属：`/users/{id}/orders`（某用户的订单）
- 动作用 POST + 动词子资源：`POST /orders/{id}/cancel`（状态变迁不是 CRUD）
- 避免超过两层嵌套，深了用查询参数：`/comments?article_id=1`

### 2. 每个接口的五要素（缺一不可）

```
路径 + 方法 + 请求参数（含校验规则）+ 响应结构 + 错误码
```

**请求**：明确每个参数的类型、必填、校验规则（手机号格式、数量 ≥1）。
**响应**：统一信封结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... }
}
```

**错误码**：分层设计（1xxx 参数错 / 2xxx 业务错 / 3xxx 权限错…），错误信息要能指导用户行动（「库存不足：还剩 2 件」而不是「失败」）。

### 3. 列表接口四件套（最容易被漏的）

每个集合接口必须设计：
- **分页**：`page/size` 或游标（数据量大时用游标，见异常篇深度分页）
- **过滤**：哪些字段可筛？（对应用例走查的「按什么条件查」）
- **排序**：默认排序 + 可选排序字段
- **字段裁剪**：列表返回摘要，详情返回全量（列表不要返回大字段）

### 4. 写接口的三个关键设计

**幂等**（与阶段⑦衔接）：POST 接口要防重复提交——
- 方案 A：客户端生成 `client_token`，服务端按 token 去重（唯一约束兜底）
- 方案 B：业务自然幂等（唯一键冲突返回已有记录）
- 支付/下单类接口**必须**幂等

**批量**：要不要批量创建/更新/删除？批量接口的部分失败语义（全部回滚 vs 跳过失败项返回明细）。

**响应即时性**：耗时操作（采集、导出）同步返回还是异步任务？异步的话返回 `task_id` + 查询接口。

### 5. 接口 ↔ 概念模型互相校验（本阶段核心动作）

**每个接口设计完，做两问**：

- 问数据：「这个响应字段从哪来？」——若来自关联实体，确认概念模型里有这个关系；若是「下单时刻的值」，确认概念模型里有快照规则
- 问规则：「这个操作违反约束吗？」——唯一性（重复提交返回什么错误码？）、状态机（已取消的订单能再取消吗？返回什么码？）、权限（这个资源只有 owner 能操作吗？接口层怎么鉴权？）

**校验发现的缺口 → 回改概念模型**（这就是④⑤迭代环的前半环）。

### 6. 版本与演进

- 破坏性变更走新版本：`/v2/orders`
- 只加字段不改字段类型、不删字段（向后兼容）
- 时间字段统一 ISO 8601 / 时间戳，时区约定写进文档

## 阶段④产出：API 契约文档

```
## 接口：创建订单 POST /orders
用途：用户提交订单（用例 U-03）
鉴权：用户 token
请求：{ items: [{sku_id, quantity}], address_id, coupon_id?, client_token }
校验：quantity ≥ 1；sku 必须在售；地址必须是本人的
响应：{ order_id, order_no, pay_amount, expire_at }
错误码：
  2001 库存不足（含剩余数） 2002 地址不存在 2003 优惠券不可用
幂等：client_token 去重，重复请求返回原订单
备注：创建成功即锁定库存 30 分钟（→ 异常篇：超时释放）
```

## 阶段间衔接

- **→⑤ 表结构**（见 `03-schema-design.md`）：把所有接口的「响应字段来源 + 请求校验规则 + 错误码触发条件」汇总成一张「数据需求清单」，表结构设计逐条满足它
- **→⑦ 异常**：本阶段标记的幂等、超时、状态机问题带入异常补全
