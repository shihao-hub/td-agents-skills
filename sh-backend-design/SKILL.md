# 从需求到设计：后端全流程方法论

## 这个 skill 解决什么问题

拿到新需求直接跳到「建哪些表、写哪些接口」，会同时埋下多类隐患：概念理解错、接口难演进、异常流没兜底、设计说不清 why。本 skill 用固定的八阶段流程，把「一段需求描述」变成「一份可评审、可落地的设计」。

## 核心流程总览

```
① 澄清需求 ──→ ② 需求分析 ──→ ③ 需求确认 ──→ ④ 接口设计 ──→ ⑤ 表结构设计 ──→ ⑥ 工程设计 ──→ ⑦ 异常补全 ──→ ⑧ 设计评审
   (量级/边界)   (四步法→       (与需求方       (API契约)      (物理DDL,       (目录/分层/     (幂等/并发/     (记录why,
                 概念模型)       对齐)                          与④互校验)      链路时序)       超时/补偿)      ADR)
```

### 每阶段速览与路由

| 阶段 | 目标 | 核心产出 | 详细方法见 |
|------|------|---------|-----------|
| ① 澄清需求 | 搞清真实意图、量级、边界 | 非功能需求清单（量级/并发/时效） | `references/01-requirement-analysis.md` |
| ② 需求分析 | 名词/动词/属性/规则四步拆解 | 概念模型 + 待确认问题清单 | `references/01-requirement-analysis.md` |
| ③ 需求确认 | 用例走查、与需求方对齐 | 确认后的概念模型（蓝图冻结） | `references/01-requirement-analysis.md` |
| ④ 接口设计 | 定义系统边界与语言 | API 契约（路径/参数/响应/错误码） | `references/02-api-design.md` |
| ⑤ 表结构设计 | 概念模型的存储投影 | 完整 DDL（类型/索引/约束） | `references/03-schema-design.md` |
| ⑥ 工程设计 | 模块怎么组织、链路怎么走 | 目录结构 + 分层 + 链路时序 | `references/04-engineering-design.md` |
| ⑦ 异常补全 | 从「能跑」到「可靠」 | 幂等/并发/超时/补偿方案 | `references/04-engineering-design.md` |
| ⑧ 设计评审 | 决策可追溯、可被挑战 | 设计文档（含 ADR 决策记录） | `references/04-engineering-design.md` |

**执行时按阶段读对应 reference，不要一次全读。** 每完成一个阶段，先检查该阶段产出是否齐全，再进入下一阶段。

## 阶段路由：用户可能从中间进入

用户不一定从①开始。先判断当前所处阶段：

- 用户给了一段需求描述，问「怎么设计/怎么做」→ 从①开始走全流程
- 用户已有明确的概念模型/实体清单，问「接口怎么设计」→ 从④进入
- 用户已有接口或表结构之一，问「另一个怎么办」→ 从④或⑤进入，先校验已有产物再补另一侧
- 用户已有设计与表结构，问「目录怎么组织/异常怎么处理」→ 从⑥进入
- 用户只想要需求分析（理实体/关系/字段/约束，不要接口不要 DDL）→ 只走①~③，产出「概念模型蓝图 + 待确认问题清单」即停，不进入④

**判断依据是「用户已有什么产物」，而不是用户嘴上说从哪开始。** 已有产物要先用对应阶段的标准校验一遍（常见情况：需求没分析透就直接给了表，此时要回退到②补概念模型）。

## 贯穿全程的三条铁律

### 铁律一：概念设计先行，接口与表结构是它的两个投影

「表结构设计」要拆成两件事：**概念设计**（实体/关系/规则，属于阶段②）与**物理设计**（DDL/索引/类型，属于阶段⑤）。概念模型是本体，接口是外部视图，表结构是存储视图。**没有概念模型就设计接口是空中楼阁；没有概念模型就写 DDL 是盲人摸象。**

### 铁律二：接口先于物理 DDL 定稿，两者互相校验迭代

- 接口是团队契约（前端/调用方依赖），上线后难改；表结构是内部实现，可演进（加索引/拆表/加缓存）而不动接口。**先定难改的，后定易改的。**
- 设计接口时会反推数据需求（「响应里要商品名」→ 订单明细要存快照）；写 DDL 时会暴露接口问题（「这个字段没唯一约束」→ 接口要做防重）。**④⑤ 不是单向流水，而是一个迭代环：每写一张表，回头扫一遍接口；每定一个接口，确认数据支撑。**
- 例外：数据密集型系统（采集/报表/数据平台）中数据模型就是需求本体，可让概念模型（不是物理 DDL）先行深化。

### 铁律三：设计质量体现在异常流，正常流只是及格线

每个阶段都要问「出错了怎么办」：状态机有哪些失败态？并发重复请求会怎样？依赖方超时/挂掉如何补偿？**异常流分析是阶段⑦的输入，但素材要从②起持续收集**——凡遇到「状态」「支付」「库存」「第三方调用」这类词，立刻记下异常问题。

## 各阶段完成标准（离开一个阶段前自查）

| 阶段 | 完成标准 |
|------|---------|
| ① | 能回答：数据量级？并发量？时效要求？有没有安全/合规约束？ |
| ② | 四张清单齐：实体清单（含隐含实体）、关系清单（含基数）、属性清单（含必补字段）、规则清单 + 待确认问题清单 |
| ③ | 每个核心用例都能在概念模型上「走通」数据流；关键待确认问题已有答案 |
| ④ | 每个接口有：路径、方法、参数、响应结构、错误码；列表接口有分页方案 |
| ⑤ | 每张表有：主键策略、字段类型、约束（唯一/非空/默认）、索引（对应到接口的查询路径）；每字段有注释 |
| ⑥ | 目录结构图 + 分层职责说明 + 核心链路的时序描述 |
| ⑦ | 幂等/并发/超时/补偿四个维度逐一有答案（或明确标注「本期不处理+理由」） |
| ⑧ | 设计文档含每个关键决策的「背景→备选→选择理由→代价」 |

## 最终产出物：一份完整设计文档

流程走完，把各阶段产出组装成设计文档：

```
# XX 功能设计文档
1. 需求理解（澄清记录 + 概念模型）
2. 接口设计（API 契约）
3. 表结构设计（ER 关系 + DDL）
4. 工程设计（目录/分层/链路时序）
5. 异常与边界（幂等/并发/超时/补偿）
6. 设计决策记录（ADR：为什么这样选）
7. 待确认问题（未拍板项，标注影响面）
```

## 语气与深度

- 每阶段**深入但不啰嗦**：挖隐含、补缺口，但显而易见的不长篇大论。
- 有争议的点标「⚠️ 待确认」，不假装确定。
- 清单用表格，结构优先于散文。
- 设计文档的灵魂是 **why**：说不清 why 的设计等于没设计。
