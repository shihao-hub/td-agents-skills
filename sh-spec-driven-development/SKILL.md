# Spec-Driven Development

## 版本信息

| 项 | 值 |
|---|---|
| 版本 | 2.0.0 |
| 创建 | 2026-09-21 |
| 更新 | 2026-09-21 |

本 skill 以最新提取的生产级 spec 工作流提示词为骨架全面重写（去产品化）：工作流总则、五条路径路由、需求/设计/任务三份文档的撰写规则、设计评审清单与机械判定、快速路径与反馈分诊、修订保障全部来自源提示词。个人规范叠加：specs/ 目录位置与编号、每个文档先批准再继续、执行默认不写测试不跑测试。

## 总则

把粗想法系统性变成详细设计文档 + 实施计划 + 任务清单：精化想法、做必要调研、创建全面设计、形成可执行的实施计划。**需求澄清与调研之间可以迭代往返**，不是单向流水线。

- **Ground-truth 原则**：全流程依靠用户逐步确立事实基准——**任何文档变动先让用户满意再前进**（每个文档先批准再继续）。已确认的内容是 ground truth，后续文档与其冲突时以其为准
- **工作流隐蔽**：不告诉用户"我在走工作流 / 现在是第几步"；只在文档完成、需要用户输入时告知
- **入口先行**：任何文档创建之前，先呈现入口选择（类型 + 路径）
- 文档静默生成期间（快速路径）输出一行进度（如"正在生成 design.md…"），避免长时间无响应
- 有子代理环境可把各阶段派发为独立子代理（隔离上下文）；没有就自己顺序执行同一套流程，规则不变

## Step 0：入口选择

| 维度 | 选项 | 判定信号 |
|---|---|---|
| **类型** | Feature（默认） \| Bug Fix | 新功能/新模块 vs "修 bug / 报错 / 崩溃 / 回归 / 行为不符合预期" |
| **路径**（Feature） | 需求先行（默认） \| 设计先行 \| 快速 | 需求明确按部就班；方案未定先探索设计（design→requirements）；小功能走快速路径（见下文） |
| **路径**（Bug Fix） | 固定需求先行 | 无选择 |

类型或路径模糊时问一句；用户明确说了就不再确认。选完提取 **feature_name**（kebab-case，取自想法或缺陷本身，如 `user-authentication` / `quantity-zero-crash-fix`），创建 `specs/{NN}-{feature_name}/`。

## 文档落盘位置与编号（个人规范）

- 三份文档必须位于同一个 `specs/{NN}-{feature_name}/` 目录；同一项目所有 spec 始终在同一个 `specs/` 下
- 取号：扫 `specs/` 下子目录 `^\d+-` 前缀取最大 +1，空则 `01`；零填充（`01`–`09`）；同号顺延；99 以上提示一次不阻断；无数字前缀的旧目录忽略不改名；从已有 spec 继续按原目录名定位
- `specs/` 放哪里（先扫项目结构，禁止不看结构取默认）：已声明"文字归 docs/"→ `docs/specs/`；已有 docs/ 判语义（项目文档中心→`docs/specs/`，知识参考库→根 `specs/`）；判不清问用户。`specs/` 编号与 `plans/` 相互独立
- 无写权限：不贴文件内容充数、不静默跳过——停下告知需要写权限，放行后从被中断的步骤继续

## Phase R：需求文档（requirements.md / bugfix.md）

### Feature 分支：requirements.md

```
# Requirements Document

## Summary
[一段话概述功能请求与项目现状]

## Functional Requirements
- [功能需求，逐条]

## Non-Functional Requirements
[仅在相关时保留：性能/安全/兼容等约束]

## Acceptance Criteria
### AC-1
[具体、可测、编号的验收标准]
### AC-2
...

## Out of Scope
[明确排除的范围]
```

规则：**按复杂度缩放**——小改动全文档 3-5 条即可，大功能才用完整结构。请求含糊时**推断合理的需求并显式标注假设**（后续设计评审会兜底）——不要停下来反复追问。只写需求，不设计、不实现。

### Bug Fix 分支：bugfix.md

```
# Bug Fix Document

## Summary
[缺陷现象一句话]

## Reproduction
[复现步骤/触发条件]

## Root Cause
[根因分析——先只读调查代码定位根因再写本节；定位不了就明说假设]

## Impact
[影响范围：哪些功能/调用方受影响]

## Fix Acceptance Criteria
### AC-1
[WHEN <复现条件>，修复后 <预期行为>——具体、可测]
```

Bug Fix 澄清**默认从轻**：bug 报告本身就是需求，只在根因定位不了或验收标准写不出来时才问，一次不超过两个问题。

### Approval loop（每个文档的关卡）

呈现给用户，明确询问：**批准，还是需要修改**。修订后重新呈现，直到明确批准。

**修订纪律**：修订前必须先读当前文档全文，在现有内容基础上修改，**绝不从零重写**——用户的批注与手改一经确认就是 ground truth，覆盖它们等于销毁已达成的事实基准。

## Phase D：设计文档（design.md）

### 撰写规则（逐条对照）

1. **先探索代码库**：读相关源码、构建配置、相近功能的既有实现——设计要贴合既有模式，而不是发明新模式
2. 设计必须**具体到实现者无需再做架构决策**
3. 多个方案可行时：简述各方案、**选定一个并给理由**——绝不留"用 X 或 Y"给实现者解决
4. **技术栈一经批准即锁定**；明确要修改的具体文件、要调用的 API、集成点；描述边缘情况
5. **错误处理逐操作具体化**：失败条件、可恢复还是致命、调用方收到什么、是否记录日志及在哪层——"适当处理错误"不是设计决策
6. 每个外部输入的**校验规则**：必填/可选、类型、限制、失败行为
7. 显著**不变量**：由哪一层负责执行、为什么
8. **可测性**：标注哪些可单测、哪些要集成测试——难测试的设计通常需要重新思考
9. 可选深化：为核心不变量各写一句**正确性属性**（"对任意合法输入 X，系统应始终满足 Y"），供基于属性的验证使用——概念即可，不强制

### 模板

```
# Design Document

## Overview
[高层概述]

## Context
[背景、现状、动机；可配 mermaid]

## Goals and Non-Goals
- Goals: [具体目标]
- Non-Goals: [明确排除]

## Detailed Design
### {模块/组件}
- `CREATED|UPDATED` [文件/组件路径]
    - **Purpose** [目的]
    - **Changes** [具体改动]
    - **Complexity** [Low|Medium|High]

### Module Collaboration and Data Flow
[依赖方向、组装顺序、关键数据流、并发模型——只有文件卡片没有协作说明的设计不合格]

### Acceptance Criteria Mapping
| AC ID | Design Component |
|---|---|
| AC-1 | ... |

## Design Review Notes
[自审/评审发现的回应：已修复 / 挂起（理由）/ 说明忽略依据]
```

### 设计评审（自审或派子代理）

以**零上下文**视角重读设计（评审者不带产生它的上下文是有意的：设计站不住就不该实现）。逐项检查：歧义（"用 X 或 Y"、"适当处理"）、**未验证的假设**（声称"现有 helper 会处理"——去读源码验证，不信设计的一面之词）、缺失细节（引用了未定义的签名）、可行性、范围蔓延、章节冲突、错误处理缺失、输入校验缺失。

产出：编号发现清单，每条标 **HIGH / MEDIUM / NIT** 并给**具体修复**（片段/明确的规则/一个选择）；附"已验证假设 / 未验证或错误假设"两节。**判定是机械的**：HIGH 或 MEDIUM 数量 >0 = 返修（CHANGES_REQUESTED），=0 = 通过。**不许为了放水把发现降级为 NIT**。返修循环比把问题漏给实现者便宜。

### Approval loop

同 Phase R：批准或修改；修订纪律同（先读全文、绝不从零重写；与已批准的需求文档冲突时以需求为准）。评审发现的回应记录在 Design Review Notes。

## Phase T：任务清单（tasks.md）

写前**必读** requirements 与 design 两份文档；每个任务要能追溯到验收标准。

**探索先行**：用项目真实的构建/测试命令（从 README/构建配置读出来），不要发明命令。

**规则**：

- 有序的小任务列表，**按依赖排序**（任务 3 需要任务 2 的产出就写明）；每个任务完成后代码库保持**可构建状态**
- **不过度拆分**："创建含 4 个方法的类"是一项不是四项；同一改动模式跨多文件是一项列文件清单
- 每个任务**自包含**：读任务本身就能动手，不需要回头猜

**格式**：

```
# Task List

- [ ] 1. [做什么，1-2 句完整描述]
  - Files: [真实文件路径]
  - 实现细节：[关键步骤、确切的依赖及版本]
  - Verify: [真实构建/测试命令 + 预期结果]（默认仅作备用信息，执行阶段不跑）
  - Ref: [AC-N]
  - [test]（仅测试类任务带此标签，执行默认跳过）
```

**验证必须是真验证**：❌"grep 确认函数存在"；✅"跑改动模块的单元测试并确认通过"。验证行没写预期结果的不合格。

### Approval loop

同上；修订纪律同（与已批准的需求/设计冲突时以后者为准）。

## 完成门（硬性关卡）

tasks.md 获批即三份文档全部就绪，**必须停下**：告知用户"三份 spec 文档已完成"，附带选项行：

`[OPTIONS: 开始执行全部任务 | 逐任务执行 | 暂不执行]`

**批准文档不构成执行授权**——选项只是指令入口，用户选中之前不执行任何任务。

## 快速路径（Quick Spec）

小功能可走快速管线：**澄清（2-4 个问题）→ 静默生成 requirements → 静默生成 design → 生成 tasks → 摘要评审**。静默阶段各输出一行进度；三文档落盘但不逐份中断用户，最后一次性呈现摘要 + 完成门。

**反馈分诊**（摘要评审后用户给反馈时）：

| 反馈类型 | 回溯路径 |
|---|---|
| 任务级（重排/拆分/改描述） | 只重做 tasks |
| 范围/需求级（增删功能、改标准） | requirements → design → tasks 顺序重做 |
| 架构/设计级（换方案、换组件） | design → tasks 顺序重做 |

**修订保障**：任何重做前**必读当前文件内容**作为上下文，绝不覆盖用户手改；重做期间流式进度。

## 执行

**唯一入口：用户明确下令**（"开始执行"/选中执行选项）。

- **默认：从任务 1 连续执行到最后一个，不暂停、不写测试、不跑测试**——跳过所有 `[test]` 任务（保持 `[ ]`），Verify 命令是备用信息不执行
- 按编号顺序；完成任务在 tasks.md 标 `[x]`，偏差或新发现追加实施说明
- 用户明确指定时才改变节奏（可独立指定）：**逐任务执行**（每完成一个停下等确认）；**执行测试**（补做 `[test]` 任务、按 Verify 命令逐任务验证）
- 用户没明说时一律按默认：不主动停、不主动跑测试、不主动写测试

## Troubleshooting

| Issue | Solution |
|-------|----------|
| 分型错误（Bug Fix 走了 Feature 全流程） | 回 Step 0：Bug Fix 用 bugfix.md、需求先行、澄清从轻 |
| 设计含"用 X 或 Y" | 选定一个并给理由，或作为发现返修 |
| 设计声称的假设未验证 | 评审时读源码核实，列入未验证假设 |
| 再生成覆盖了手改 | 修订前必读当前文件；已确认内容是 ground truth |
| 任务不可独立执行/过度拆分 | 按依赖重排、合并同型改动 |
| 验证是 grep 式伪验证 | 换成真实构建/测试命令 + 预期结果 |
| 阶段间没请求批准 | 每份文档完成必须走 approval loop |
| 写入被当前模式拒绝 | 告知用户切换可写模式，从被中断步骤继续 |
