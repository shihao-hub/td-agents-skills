# sh-agy-teamwork：多智能体协同

> 版本 v1.0.0 ｜ 移植自 Google Antigravity 斜杠命令 /teamwork-preview，<TEAMWORK> 提示词提取自 language_server.exe（2026-09-23 构建）。原版委派给 teamwork 多 agent 系统（git worktree 隔离，refs/battle/base 分支）。

## 功能介绍

Antigravity 的 /teamwork-preview：官方释义 "Invoke a team of agents to autonomously tackle large projects."。两阶段工作流，**缺一不可**：

1. 和用户走 9 步交互，把任务打磨成结构良好的团队提示词；
2. 委派给多 agent 团队分工执行（架构分析、模块编码、集成测试、代码审查等角色并行/按依赖推进）。

适用：超大工程、跨多子系统协同开发；单会话上下文装不下的并行化开发。

## 执行协议

### 阶段一：9 步打磨任务书

全程维护 `plans/teamwork-prompt-draft.md` 草稿（状态+内容），每步更新。给用户选项时结构化列出（a/b/c）。

核心原则（贯穿全程）：

| # | 原则 | 规则 |
|---|---|---|
| 1 | 说 What 不说 How | 只定义需求和验收标准；不规定文件名/架构/算法/库，除非用户明确要求 |
| 2 | 客观验证 | 每条需求都要有独立于实现 agent 自评的验证机制；程序化验证最佳，agent-as-judge（明确 rubric）可接受 |
| 3 | 验收标准=护栏 | 防止劣质工作自我认证；首轮不达标就收紧标准重跑 |
| 4 | 最小需求 | 只写用户真正在乎的；需求越多约束越多，团队自主判断空间越小 |

**Step 1** 阐明想法：做什么？用途（demo/生产/评估/探索）？受众？→ 1-2 句写进任务书开头。
**Step 2** 识别歧义：多解读点逐个给具体选项（含风险）；只问影响范围/验证的决策。探测维度：规模、技术硬约束、基础设施、质量标准、验证资源。两个 opt-in 要主动问：单一自包含小改动（小团队：一个实现者+反复对抗审查，不拆分）；数学/证明类（标准 proof 流水线 vs 超大规模团队）。
**Step 3** 完整性模式：别让用户"选模式"，用行为多选问允许哪些捷径（拷开源核心逻辑/用现成框架/跑外部脚本/读测试源码）→ 全选=benchmark、部分=demo、都不选=development（默认）。
**Step 4** 起草需求：2-5 个需求块（R1、R2…），每条 1-3 句讲 what；用户没提的偏好不加需求；试金石："熟练工程师会觉得被过度约束吗？"
**Step 5** 设计验证：验证是**强制函数**不是理想态镜像——造出"易运行、难造假"的客观测试目标，逼出真实的 构建→测试→调试 循环。反模式：自评、主观标准（"看起来不错"）、无标准。问用户有无现成测试套件/脚本/参考实现，有则写进任务书。
**Step 6** 验收标准：每条需求转成可勾选的验收清单。
**Step 7** 工作目录与环境：确认工作目录、运行环境、边界（能否联网、装依赖）。
**Step 8** 终稿审阅：完整任务书给用户过目批准。
**Step 9** 委派（进入阶段二）。

用户想跳过打磨直接委派：**劝一次**——提示词欠规范是劣质结果头号原因，5 分钟需求+标准显著提升首轮质量；坚持就尊重，但明示"结果可能需要更多迭代"。

### 阶段二：委派执行（opencode task 子代理适配）

1. 按模块/关注点拆分子任务，用 task 工具并行派发（explore 只读研究 / general 读写执行）。
2. **写任务按文件/模块硬分区，杜绝两个子代理改同一文件**（无原版 worktree 隔离）；只读研究可随意并行。
3. 每个子代理 prompt 自包含：目标、范围（允许动哪些文件）、相关需求块、验收标准、验证命令、完成后报告什么。
4. 集成：汇总产出，按验收标准逐条验证；不达标项发回对应子代理修或自己修。
5. 输出总结：需求→证据对照、各子代理工作摘要、遗留事项。

## 与原版的差异

- 原版是独立多 agent 系统（路由 agent 按描述配团队、worktree 隔离、battle 评审合并）；本版用单会话 task 子代理编排，靠文件分区+验收护栏近似。
