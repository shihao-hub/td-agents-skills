# Cheatsheet — 判断与决策速查（Brooks 视角）

## 决策规则（When X → do Y, because Z）

| 情形 | 决策 | 理由 |
|---|---|---|
| 项目进度落后，想加人 | 不加；先重排进度/削减任务 | Brooks 法则：加人使沟通与培训成本增加，更落后（Ch2） |
| 要估算工期 | 用历史数据×幂律（指令数^1.5），按复杂度与交互程度分层校准 | 编码只占 1/6；小程序数据不可外推（Ch2、Ch8） |
| 系统测试没排时间 | 至少留总进度 1/4 | 系统测试是最难估、最常被砍的部分（Ch2） |
| 设计第二个系统 | 砍掉"修饰功能"，坚持资源预算约束 | 第二系统效应：功能膨胀的最高发期（Ch5） |
| 团队对体系理解不一 | 手册=外部规格说明，书面化并广播；周例会+年度大会 | "只有书面计划是精确和可以沟通的"（Ch6、Ch10） |
| 小组想改接口约定 | 禁止；变更走结构师与工作手册 | 私自变更破坏概念完整性（Ch6、Ch7） |
| 里程碑报"90% 完成" | 视为未完成；改为具体可度量事件 | 慢性滑坡一天一天累积成灾难（Ch14） |
| 第一次做新系统 | 计划抛弃第一版 | "你反正会抛弃的"（Ch11） |
| 修 bug 后 | 必须回归测试 | 修复有 20%-50% 概率引入新 bug（Ch11） |
| 追求某局部最优性能 | 先问系统级瓶颈 | 局部优化=争取小红花的学生（Ch9） |
| 有人宣称"这工具/语言/方法能解决软件危机" | 默认怀疑；找本质 vs 偶然复杂性归属 | 没有银弹：本质复杂性不可被工具消除（Ch16） |
| 想加功能"反正只多几行代码" | 核对规模预算（驻留空间+后台访问） | 削足适履：规模必须编入预算并度量（Ch9） |

## 阈值与默认值（Brooks 承诺的数字）

- 成本倍增律：编程产品 ×3，编程系统构件 ×3，编程系统产品 ≈**×9**
- 进度切分：1/3 计划 / 1/6 编码 / 1/4 构件测试+早期系统测试 / 1/4 系统测试
- 沟通成本：n 人有 n(n-1)/2 条沟通路径
- 幂律指数：工作量 ≈ 常数 × 指令数^1.5
- 生产率参考（指令/人年）：Aron 交互少 10000、中 5000、多 1500；Corbato MULTICS 1200 行 PL/I
- 维护成本 ≥ 开发成本的 40%；bug 修复引新 bug 率 20%-50%
- 交互式编程生产率 ≥ 2× 批处理
- 计划控制小组：1-3 人，独立于开发
- Portman 规律：技术人员约 50% 时间才是有效技术时间

## 危险信号（Tells & Smells）

- "加几个人就赶上了" → 人月谬误发作
- "编码基本完了，快了" → 系统测试没排进去
- 结构师口头传达决策 → 概念完整性将瓦解
- 里程碑全是百分比 → 进度汇报在撒谎（未必故意）
- 手册越写越像实现内部文档 → 过度规定，外部规格失守
- 文档与代码分开维护 → 必然漂移，走向自文档化
- 原型获得好评就直接交付 → 用户拿到的是试验工厂
- 修复后不跑回归测试 → 熵增加速
- 第二个系统里"人人都想要的功能" → 画蛇添足
- 大会小会无决策记录 → 会议白开，决策权没集中

## 选择速查（该用哪个模式）

- 质量关键的核心模块 → 外科手术队伍
- 多组并行的大项目 → 树状队伍 + 工作手册 + 两级会议
- 全新领域系统 → 为舍弃而设计 + 增量开发
- 控制膨胀 → 资源预算约束 + 规模预算
- 追踪进度 → 具体里程碑 + PERT + 计划控制小组
- 沟通体系 → 手册（外部规格）+ 工作手册 + 电话日志
