# 第5章：画蛇添足（第二系统效应）

## 核心思想
第二个系统是设计师所设计的最危险的系统：第一个系统积累的自信 + 第一个项目中被搁置的"装饰和润色功能"，会一起倾泻进第二个系统，形成过分设计的"大馅饼"。应对之道不是跳过第二个系统（无法跳过），而是有意识地关注其特殊危险，运用特别的自我约束准则。

## 框架/模型
- **第二系统效应（second-system effect）**：第一次设计者因不了解而谨慎精炼；第二个系统则倾向加入过多修饰功能与想法；到第三、四个系统，经验相互验证，能识别经验中不通用的部分。何时警惕：任何成功完成第一个系统、正着手第二个同类系统的结构师。
- **结构师-实现者交互准则**：结构师只建议不支配——(1) 牢记实现责任在开发人员；(2) 随时为规格建议实现方法，同样准备接受其他任何能达到目标的方法；(3) 建议保持低调和不公开；(4) 准备放弃坚持的改进建议。
- **预算-估算反馈环**（类比建筑业）：结构师用估算编制预算 → 承包商报价验证修正 → 超预算时削减设计或改用更便宜的实现。尽早、持续的交流让结构师有成本意识、让开发人员对设计有信心。
- **资源预算约束法**：为每个小功能分配一个值——"每次改进，功能 x 不超过 m 字节内存和 n 微秒"。设计期作决策向导，物理实现期作警示。
- **基于基本理念舍弃功能**：当基本系统设想已变、某技术已落后时，应有意识舍弃围绕旧理念精炼出的功能。

## 关键概念
- **second-system effect（第二系统效应）**：第二次开发某类系统时因过度自信而过分设计的倾向。
- **修饰功能（装饰和润色功能）**：第一个项目中"放到下一个项目"的想法，在第二个系统中集中涌入。
- **过时技术的细化精炼**：第二系统效应的另一种表现——不是加新功能，而是对已因基本设想改变而落后的技术做到极致。
- **architecture / implementation / realization**：结构（体系结构）、设计实现、物理实现的区分。
- **"大馅饼"**：Ovid 所述"聚沙成塔"的反面——小功能不断累加成臃肿整体。
- **自我约束准则**：结构师对抗第二系统效应的纪律性手段（预算值、舍弃）。
- **项目经理的职责**：坚持任用有两个以上系统开发经验的结构师，并保持对特殊诱惑的警觉。

## 思维模型
把每个系统设计看作一次"经验的采样"：第一个样本教谨慎，第二个样本诱发放纵，第三个之后的样本才能区分"通用经验"与"个案偶然"。因此经验的价值不在于数量而在于交叉验证——设计决策应接受"这是不是上次成功但未必通用？"的质询。

## 反模式
- **过分设计第二个系统**：把第一个系统搁置的所有装饰一次性塞入，只加不减。
- **给恐龙做精炼**：在基本运行方式已改变后，仍把旧技术打磨到顶峰（如静态覆盖的链接编辑器出现在多道程序动态内核分配系统中）——"最后和最优秀的恐龙"。
- **只建议不放手/支配实现**：结构师越界支配实现方式，打击实现人员的创造性责任。
- **项目经理纵容**：不质疑修饰性功能，或任用只有一个系统经验的结构师而不加警觉。
- **无预算约束的"免费"改进**：任何功能改进不标明字节/微秒代价，导致失控膨胀。

## 经典论断/数据
- "第二个系统是设计师们所设计的最危险的系统。"
- IBM 709（704 的二次开发）："操作集合设计得如此丰富和充沛，以至于只有一半操作被客户经常使用。"
- Strachey 评 Stretch："富有创造性，设计非常复杂……却粗糙、浪费、缺乏优雅。"
- "OS/360 是典型的开发第二次所引起的后果，是软件行业的 Stretch 系统。"例：26 字节的常驻日期翻转例程处理闰年第 366 天，"其实它完全可以留给操作员来完成"。
- 链接编辑器讽刺："链接程序的目的是为了避免重新编译"却比编译还慢——"像一个挺着大肚子的节食者"。
- 建筑业对照："承包商的报价总会超过预算"，结构师据此调整设计。

## 关键要点
- 警惕的对象不是无能，而是成功：第一系统的成功恰恰是第二系统膨胀的燃料。
- 第二系统效应有两种形态：疯狂添加修饰功能；对已过时的旧技术做终极精炼——后者更隐蔽。
- 结构师的纪律：建议不支配、低调、可放弃；为每个功能标注内存/时间预算。
- 基本理念已变时，围绕旧理念打磨的优秀功能应当被舍弃，而非保留。
- 项目经理的两大杠杆：坚持用有 2+ 系统经验的结构师；不断提出正确的问题，确保概念完整在详细设计中体现。
