# 跨 Agent 会话交接

把一段会话的任务上下文，从一个 AI agent 交给**另一个** agent 继续做。不依赖任何具体产品、不绑定某台机器。

这个 skill 只有两种角色，看用户给了什么就能判断：

| 用户给了什么 | 角色 | 你要做的 |
|---|---|---|
| 只有任务/主题，没给路径 | **导出侧** | 写一份交接简报文件，把**路径**告诉用户 |
| 给了一个文件路径（通常还带一个问题） | **接管侧** | 读那个文件，复述理解，然后解决用户的问题 |

## 适用边界

- 跨 agent 交接：pi → Claude Code、opencode → Cursor、Zed 里的 agent → 命令行 agent，任意组合。
- 同一个 agent 只是换个会话窗口时**不需要**本 skill——那用产品自带的 `/fork`、`--continue`、`/clone` 就够，无损且更便宜。
- 目标 agent 是网页版、读不到文件系统时，走"直接输出正文"分支。

## 交接文件放在哪

**不要放在当前项目目录里**，也不要用系统临时目录。项目目录会污染 `git status`，monorepo/submodule 下还容易误提交；临时目录会被系统清理，交接进行到一半文件消失最麻烦。

按平台选一个用户级数据目录（只读环境变量、不要写死任何用户名）：

| 平台 | 目录 |
|---|---|
| 用户设置了 `AGENT_HANDOFF_DIR` | 直接用它的值（最高优先级） |
| Windows | `%APPDATA%\agent-handoff` |
| macOS | `~/Library/Application Support/agent-handoff` |
| Linux / 其他 | `${XDG_DATA_HOME:-$HOME/.local/share}/agent-handoff` |
| 上面都取不到 | `~/.agent-handoff` |

路径取不到时回退而不是报错——交接本身比存放位置重要，先让流程走通，再告诉用户实际落点。

完整文件名：

```text
<root>/<project>/<YYYYMMDD-HHmmss>-<topic>.md
```

- `<project>`：当前 git 仓库根目录的目录名；不在 git 仓库里就用当前目录名。小写、非字母数字替换成 `-`、截断到 40 字符。加上这层是为了不同项目的交接件不混在一起。
- `<topic>`：3–5 个英文小写单词概括主题。
- 若所在仓库有自己的数据目录约定，让用户用 `AGENT_HANDOFF_DIR` 覆盖，不要改这个 skill。

## 导出侧

### 1. 判断输出方式

默认写文件并把路径给用户。只有用户明说接收方没有文件系统（网页版、聊天窗口）时，才改成把简报正文直接输出到对话里。

### 2. 写文件

先创建完整目录链（含父目录），再写文件。写出简短反馈即可，不要把简报正文也贴一遍——用户要的是路径。

### 3. 简报内容

这是交接质量的唯一决定因素。接手侧读不到旧会话的任何历史，所以简报必须自包含。严格用这个结构：

```markdown
# 交接简报：<主题>

- 生成时间：<YYYY-MM-DD HH:mm>
- 来源 agent：<产品名与模型，能确认才写>
- 来源工作目录：<绝对路径>
- 仓库根目录：<绝对路径；不在 git 仓库则写"无">

## Goal
这次要达成什么。一句话说清，接手侧据此判断后续每一步是否有意义。

## Constraints & Preferences
用户明确提出的约束、偏好、不可动的边界。写清楚"为什么"，否则接手侧会以为是随意选择而改掉。

## Progress
### Done
- [x] 已完成的动作，以及验证方式（跑了什么命令、看到什么结果）
### In Progress
- [ ] 正在做的事，卡在哪一步
### Blocked
- 阻塞点，以及已经排除过的方案。

## Key Decisions
- **决策**：理由。

必须包含"试过但不行"的方案。这是最容易被漏掉、也最容易让接手侧重复踩坑的信息——它无法从代码里推出来。

## Next Steps
按优先级排列的下一步。每步尽量写清动哪个文件、验收标准是什么。

## Critical Context
继续干活必需的事实：分支名、环境前提、要启的服务、凭据位置、ID、外部链接。不要在这里复述代码。

## Referenced Files

每行一个，标注 read / modified。仓库内的文件给出仓库相对路径 + 绝对路径；仓库外的（用户配置目录、
依赖安装目录、系统路径等）没有相对路径，就给出绝对路径并标注"仓库外"，避免接手侧白白在仓库里翻找：
- `src/a.ts`（read） — `D:\proj\src\a.ts`
- `src/b.ts`（modified） — `D:\proj\src\b.ts`
- `~/.config/x/s.yaml`（read，**仓库外**） — `C:\Users\me\.config\x\s.yaml`

## 原始片段
可选，默认省略。只在这三类内容上贴原文，其余一律只写路径：
未提交的 git diff、报错堆栈/失败测试输出、接口签名与 SQL 这类"差一个字符就错"的片段。
```

两条关于体积的要求：全文控制在 150 行以内；凡是在磁盘上能读到的内容（文件内容、日志、配置）**只写路径，不要复制**——接手侧有工具能自己读，而且读到的必然是最新版。交接简报价值高但脆，越短越准。

仓库相对路径不是可选项。接手侧可能换了机器：绝对路径会失效，但只要仓库还在，相对路径就仍然可用。

### 4. 交付路径

最后单独输出一行，格式固定，方便用户直接复制：

```text
sh-agent-handoff: <绝对路径>
```

这一行同时也是**交给接手侧的调用形式**——用户要在新 agent 里贴这一行，再补一句自己的问题。所以要放在回复最末尾，前后不要混入其他内容。

## 接管侧

### 1. 读文件

完整读完再动手。读不到（路径不存在、权限不足、在另一台机器上）就直接告诉用户，不要凭文件名的猜测往下编内容。

### 2. 校验引用

检查 `Referenced Files` 里的路径是否真的存在。有对不上的（常见于换了机器、仓库没克隆），把对不上的路径列出来，请用户给出正确的仓库根目录。**不要**因为某个文件找不到就跳过它继续做——那通常正是要做的那部分。

### 3. 复述理解

在动手之前，用不超过 6 行复述你接手到的状态：目标、已完成、卡点、你打算先做的下一步。这一步是为了让用户一眼确认"交接成功"，而不是等你做完一大段才发现理解偏了。

### 4. 干活

然后处理用户的问题。简报里已经写明的信息不要再问一遍——那是交接失败最典型的表现。只有真正阻塞、且简报里没有的信息才问。

## 常见错误

- **把交接简报写进项目目录**。默认放用户级数据目录，理由见上文。
- **简报只写"改了什么"不写路径**。接手侧无法重读文件，只能靠描述猜。
- **把整份会话转录（JSONL、导出的 HTML）交给接手侧**。那些是私有格式、给人看的、可能已被截断，还会直接压爆接手侧的上下文窗口。
- **把交接简报当成一次性临时文件而随手丢在 `/tmp`**。交接进行到一半被清理掉就白做了。
- **在接管侧重新总结一遍**。总结必须由导出侧做——它手上还有完整上下文，接手侧只有摘要，重总结只会更差。
- **忘记交接件的血缘**。简报头部的来源 agent、来源工作目录是排查"接手侧理解偏了"时唯一的线索。
