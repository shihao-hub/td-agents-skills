# 跨 Agent 会话交接

把一段会话的任务上下文，从一个 AI agent 交给**另一个** agent 继续做。不依赖任何具体产品、不绑定某台机器。

这个 skill 有三种调用形态，看用户丢了什么就能判断，不需要问：

| 输入 | 角色 | 你要做得 |
|---|---|---|
| `sh-agent-handoff`（空手） | **导出侧** | 写一份交接简报文件（标为待接管），把路径告诉用户 |
| `sh-agent-handoff <任务描述>` | **接管侧**，自动定位 | 找出候选交接件（含状态标记并推荐），**必须先经用户确认**再读 |
| `sh-agent-handoff: <绝对路径>` + 任务描述 | **接管侧**，指定文件 | 读血统头检查状态：**若已接管则二次确认**；未接管则直接读并校验干活 |

### 空手输入的歧义怎么处理

空手形式在两种场景下含义不同，区分它的信号不是用户的描述（空手时压根没有描述），
而是**当前会话自己有没有内容**：

- **本会话已有实质工作历史** → 导出侧。用户是在旧会话尾部顺手丢了一个 skill 名，直接写简报，
  不要反问"交接给谁""主题是什么"——接收方是谁不影响简报内容，主题从会话里自己概括。
- **本会话基本没有内容**（刚开的新会话，没什么可交接的） → 这是"想接管却忘了写任务描述"的典型误用。
  不要凭空生成一份空简报，而是告诉用户这个会话没有可交接的内容，并列出候选交接件（含接管状态标记）问他是不是要接管那一个。

导出侧也不需要用户交代接收方是谁：简报模板是 agent 无关的。

### 导出侧交出的那一行

最后输出的这一行，同时也是接管侧可以直接粘的调用：

```text
sh-agent-handoff: <绝对路径>
```

所以用户不需要自己拼命令。但在他知道交接件位置的情况下，
只丢 `sh-agent-handoff <任务描述>` 让接管侧自己找也行——两条路都支持。

## 适用边界

- 跨 agent 交接：pi → Claude Code、opencode → Cursor、Zed 里的 agent → 命令行 agent，任意组合。
- 同一个 agent 只是换个会话窗口时**不需要**本 skill——那用产品自带的 `/fork`、`--continue`、`/clone` 就够，无损且更便宜。
- 目标 agent 是网页版、读不到文件系统时，走"直接输出正文"分支。

## 交接文件放在哪

**不要放在当前项目目录里**，也不要用系统临时目录。项目目录会污染 `git status`，monorepo/submodule 下还容易误提交；临时目录会被系统清理，交接进行到一半文件消失最麻烦。

按平台选一个用户级数据目录（只读环境变量、不要写死任何用户名）：

| 平台 | 目录 |
|---|---|
| 用户设置了 `AGENT_HANDOFF_DIR` | 直接用它的值（最高优先级） |
| Windows | `%APPDATA%\agent-handoff` |
| macOS | `~/Library/Application Support/agent-handoff` |
| Linux / 其他 | `${XDG_DATA_HOME:-$HOME/.local/share}/agent-handoff` |
| 上面都取不到 | `~/.agent-handoff` |

路径取不到时回退而不是报错——交接本身比存放位置重要，先让流程走通，再告诉用户实际落点。

完整文件名：

```text
<root>/<project>/<YYYYMMDD-HHmmss>-<topic>.md
```

- `<project>`：当前 git 仓库根目录的目录名；不在 git 仓库里就用当前目录名。
  - **标准化格式（kebab-case）**：全小写、非英文字母和非阿拉伯数字（包括下划线 `_`、空格、标点等）一律替换为中折线 `-`、连续多个 `-` 合并为单个 `-`、去除首尾 `-`、截断到 40 字符。
    例如当前仓库名为 `language_projects`，标准目录名必须是 `language-projects`。加上这层是为了不同项目的交接件不混在一起。
  - **接管侧归一化容错扫描（强约束）**：接管侧自动检索时，**必须同时把 `_` 和 `-` 视为同义等价匹配**。例如当前项目是 `language_projects`，接管侧扫描候选时必须同时扫描 `language-projects/` 与 `language_projects/` 下的 `.md`，彻底防止因不同 Agent 未严格替换下划线导致交接件失联。
- `<topic>`：3–5 个英文小写单词概括主题。用户不会主动给主题，自己从本次会话内容里概括。
- `AGENT_HANDOFF_DIR` 是**用户自己需要时才用的逃生口**（比如他有目录洁癖或已有归档习惯）。不要主动建议用户设置它，更不要替他写环境变量——默认值已经足够通用。

## 导出侧

### 1. 判断输出方式

默认写文件并把路径给用户。用户只丢了一个 skill 名时也是这个默认，不要为了确认输出方式而停下来问。
只有用户明说接收方没有文件系统（网页版、聊天窗口）时，才改成把简报正文直接输出到对话里。

### 2. 写文件

先创建完整目录链（含父目录），再写文件。写出简短反馈即可，不要把简报正文也贴一遍——用户要的是路径。

### 3. 简报内容

这是交接质量的唯一决定因素。接手侧读不到旧会话的任何历史，所以简报必须自包含。严格用这个结构：

```markdown
# 交接简报：<主题>

- 生成时间：<YYYY-MM-DD HH:mm>
- 来源 agent：<产品名与模型，能确认才写>
- 接管状态：[ ] 待接管
- 来源工作目录：<绝对路径>
- 仓库根目录：<绝对路径；不在 git 仓库则写"无">

## Goal
这次要达成什么。一句话说清，接手侧据此判断后续每一步是否有意义。

## Constraints & Preferences
用户明确提出的约束、偏好、不可动的边界。写清楚"为什么"，否则接手侧会以为是随意选择而改掉。

## Progress
### Done
- [x] 已完成的动作，以及验证方式（跑了什么命令、看到什么结果）
### In Progress
- [ ] 正在做的事，卡在哪一步
### Blocked
- 阻塞点，以及已经排除过的方案。

## Key Decisions
- **决策**：理由。

必须包含"试过但不行"的方案。这是最容易被漏掉、也最容易让接手侧重复踩坑的信息——它无法从代码里推出来。

## Next Steps
按优先级排列的下一步。每步尽量写清动哪个文件、验收标准是什么。

## Critical Context
继续干活必需的事实：分支名、环境前提、要启的服务、凭据位置、ID、外部链接。不要在这里复述代码。

## Referenced Files

每行一个，标注 read / modified。仓库内的文件给出仓库相对路径 + 绝对路径；仓库外的（用户配置目录、
依赖安装目录、系统路径等）没有相对路径，就给出绝对路径并标注"仓库外"，避免接手侧白白在仓库里翻找：
- `src/a.ts`（read） — `D:\proj\src\a.ts`
- `src/b.ts`（modified） — `D:\proj\src\b.ts`
- `~/.config/x/s.yaml`（read，**仓库外**） — `C:\Users\me\.config\x\s.yaml`

## 原始片段
可选，默认省略。只在这三类内容上贴原文，其余一律只写路径：
未提交的 git diff、报错堆栈/失败测试输出、接口签名与 SQL 这类"差一个字符就错"的片段。
```

两条关于体积的要求：全文控制在 150 行以内；凡是在磁盘上能读到的内容（文件内容、日志、配置）**只写路径，不要复制**——接手侧有工具能自己读，而且读到的必然是最新版。交接简报价值高但脆，越短越准。

仓库相对路径不是可选项。接手侧可能换了机器：绝对路径会失效，但只要仓库还在，相对路径就仍然可用。

### 4. 交付路径

最后单独输出一行，格式固定，方便用户直接复制：

```text
sh-agent-handoff: <绝对路径>
```

这一行同时也是**交给接手侧的调用形式**——用户要在新 agent 里贴这一行，再补一句自己的问题。所以要放在回复最末尾，前后不要混入其他内容。

顺带告诉用户一句：如果在新侧丢 `sh-agent-handoff <任务描述>`，接手侧也能自己找到最近的交接件，不必回来抄路径。两条路都行，用户选顺手的那条。

## 接管侧

### 1. 定位交接件与状态确认

接管侧分为两种入口：**显式指定（指定文件）** 与 **自动定位（未指定文件）**，两种情况均须针对「接管状态」与用户对齐：

#### 场景 A：显式指定文件（`sh-agent-handoff: <绝对路径>`）
用户给出了显式路径时，无需全盘扫描，但**必须先读取文件顶部血统头部（前 8 行）检查接管状态**：
- **若为【已接管】**（即已打上 `[x] 已由 <agent> 于 <time> 接管`）：
  - **必须停下来主动向用户询问确认**：
    > ⚠️ 检测到该交接件已被接管：
    > - 接管记录：`[x] 已由 xxx 于 YYYY-MM-DD HH:mm 接管`
    > - 简报主题：`<主题>`
    >
    > 请确认：您是需要基于该历史节点**重新接管/复盘**，还是交接文件路径有误？
  - 用户明确确认要继续后，再往下执行；若用户提供了新路径，则按新路径重走。
- **若为【待接管】**（`[ ] 待接管`）或历史无状态标记文件：直接进入步骤 2 读取全文。

#### 场景 B：自动定位（`sh-agent-handoff <任务描述>` 或空会话下空手）
用户没给路径时，接管侧自己找：

- 扫描交接根目录下的 `<root>/*/*.md`（包含 `AGENT_HANDOFF_DIR` 覆盖后的目录）。
  - **归一化目录匹配**：将目录名中的 `_` 与 `-` 视为等价（如当前工程为 `language_projects`，同时扫描 `language-projects/` 与 `language_projects/`）。
- **按文件名里的时间戳排序，不要用文件 mtime**：交接件一旦被复制、网盘同步或换盘，mtime 就不不可信了，而文件名里的时间戳是写进去的。
- **只读每个候选文件顶部的血统头部**（约 5~8 行），提取主题、生成时间、来源 agent、仓库、**接管状态**。绝对不要全文读，候选一多会吃掉上下文。
- 排序与推荐：
  - 把当前工作目录所属 project（含归一化目录）的交接件排在前面，同一组内按时间倒序。
  - **优先推荐同 project 里最新的【待接管】交接件**；若该 project 下全部都已被接管，则标出最新已接管件。
- **底线：只要是自动定位，就必须让用户确认候选，无论候选是 1 个还是 10 个**：
  - **1 个候选** → 列出其主题、生成时间、来源 agent、仓库、接管状态（如 `[待接管]`），说明这是唯一候选，等用户确认。并给出另一条出口（若跨机器请给路径）。
  - **多个候选** → 列出最近 5 个，每条带状态前缀（例如 `1. ⭐ [待接管] ...`、`2. [已接管 @ 09-23] ...`），明确标注推荐项，请用户确认序号。
  - **0 个候选** → 明确告知没找到，请用户提供路径。

确认之前不要读简报正文，也不要开始干活的任何一个步骤。

### 2. 读文件

用户确认后，完整读完简报再动手。读不到（路径不存在、权限不足、在另一台机器上）就直接告诉用户，不要凭文件名的猜测往下编内容。

### 3. 校验引用

检查 `Referenced Files` 里的路径是否真的存在。有对不上的（常见于换了机器、仓库没克隆），把对不上的路径列出来，请用户给出正确的仓库根目录。**不要**因为某个文件找不到就跳过它继续做——那通常正是要做的那部分。

### 4. 复述理解 并 回写接管状态

在动手之前：
1. **复述理解**：用不超过 6 行复述你接手到的状态：目标、已完成、卡点、你打算先做的下一步。让用户一眼确认"接管成功"。
2. **回写接管状态（打标）**：复述后、开始写代码干活前，接管侧必须将该交接件头部的接管状态行回写更新为：
   ```markdown
   - 接管状态：[x] 已由 <当前Agent/模型> 于 <YYYY-MM-DD HH:mm> 接管
   ```
   （若为缺失状态标记的旧简报，在 `- 来源 agent:` 所在行之后插入该行）。这样该文件在后续检索中即被视为已完成，不再被误当作待处理事项推荐。

### 5. 干活

然后处理用户的问题。简报里已经写明的信息不要再问一遍——那是交接失败最典型的表现。只有真正阻塞、且简报里没有的信息才问。

## 常见错误

- **自动定位后不确认就直接用交接件**。自动定位是猜测，即使只找到一个候选也可能不是他要的那个；只有用户显式确认才算他做了选择。
- **显式指定已接管文件时不提示不确认**。用户可能误贴了旧交接件路径，若文件已打标被接管过，必须主动询问是否确认重新接管。
- **接管成功后忘记回写状态打标**。接管侧完成复述后未更新 `- 接管状态：[x] ...`，导致下一次检索仍然将其当成待接管任务推荐。
- **按 mtime 排序候选交接件**。文件被复制、网盘同步或换盘后 mtime 就不不可信了，时间戳写在文件名里。
- **列举候选时把每个文件全文读一遍**。候选一多就直接吃掉接手侧的上下文窗口；只读顶部血统头部。
- **把交接简报写进项目目录**。默认放用户级数据目录，理由见上文。
- **简报只写"改了什么"不写路径**。接手侧无法重读文件，只能靠描述猜。
- **把整份会话转录（JSONL、导出的 HTML）交给接手侧**。那些是私有格式、给人看的、可能已被截断，还会直接压爆接手侧的上下文窗口。
- **把交接简报当成一次性临时文件而随手丢在 `/tmp`**。交接进行到一半被清理掉就白做了。
- **在接管侧重新总结一遍**。总结必须由导出侧做——它手上还有完整上下文，接手侧只有摘要，重总结只会更差。
- **忘记交接件的血统**。简报头部的来源 agent、来源工作目录是排查"接手侧理解偏了"时唯一的线索。
