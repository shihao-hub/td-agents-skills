# 阶段⑥⑦⑧：工程设计、异常补全、设计评审

> 主入口见 SKILL.md。输入是已收敛的接口契约 + 表结构。这三阶段把设计从「图纸」变成「可施工、可评审」的方案。

## 阶段⑥ 工程设计：目录、分层、链路

### 目录结构（Python 后端参考）

按「分层」组织，职责单一、依赖单向（上层依赖下层，禁止反向）：

```
app/
├── api/            # 接口层：路由、参数校验、调用 service、组装响应
│   └── v1/
│       └── order.py
├── services/       # 业务层：业务逻辑、事务边界、状态机
│   └── order_service.py
├── models/         # 数据层：ORM 模型（对应⑤的表）
│   └── order.py
├── repositories/   # 数据访问层（可选）：隔离 ORM 查询
├── schemas/        # Pydantic 请求/响应模型（对应④的契约）
├── tasks/          # 异步任务（采集、通知、补偿）
├── core/           # 配置、鉴权、异常、日志
└── utils/
```

**分层铁律**：
- api 层不写业务逻辑，service 层不写 SQL 细节（用 repository/ORM）
- **事务边界在 service 层**（一个业务动作一个事务）
- 跨服务调用只在 service 层出现

小项目可以合并层（api+service），但「请求校验/业务逻辑/数据访问」三类代码混在一个文件里是债务起点。

### 模块划分

- 按**业务域**划分模块（order/product/coupon），不按技术类型划分（controller/service 统一目录是另一风格，团队统一即可）
- 判断标准：一个模块的改动尽量不牵连另一个模块（高内聚低耦合的落地）

### 链路时序（核心用例各画一条）

对阶段③走查过的每个**写入用例**，写清同步链路：

```
创建订单（含支付）：
客户端 → POST /orders
  → order_service.create()
      → 事务{ 校验库存(SELECT FOR UPDATE/乐观锁) → 写 order + order_item → 扣库存 → 标记优惠券 }
  → 返回 order_no
（异步）超时未支付 → 定时任务取消订单、回补库存、释放优惠券
```

要素：每一步同步还是异步？事务包到哪？失败回滚什么？**链路图是异常补全（⑦）的直接输入。**

## 阶段⑦ 异常补全：从「能跑」到「可靠」

**对每条链路，过四个维度**。每个维度要么有方案，要么明确「本期不处理 + 理由」。

### 1. 幂等（重复请求）

- 来源：用户重复点击、网络重试、MQ 重复投递
- 方案：`client_token` + 唯一约束兜底；或业务键自然幂等（唯一冲突返回已有）
- 检查点：**所有写接口**，尤其支付、下单、领券

### 2. 并发（同时请求）

- 典型：超卖（两个请求同时扣同一份库存）、重复领取（同时领同一张券）
- 方案：
  - 乐观：`UPDATE ... SET stock=stock-1 WHERE id=? AND stock>=1`（影响行数=0 即失败）
  - 悲观：`SELECT ... FOR UPDATE`
  - 分布式锁（Redis）用于跨库/跨服务资源
- 检查点：**计数器、库存、额度、状态机**（已取消的订单不能再支付：`UPDATE ... WHERE status='待支付'`）

### 3. 超时（依赖方无响应）

- 第三方支付/短信/采集接口超时怎么办？重试几次？重试会不会造成重复操作（回到幂等）？
- 订单类超时业务化：30 分钟未支付自动取消（定时任务/延迟队列）
- 检查点：**所有跨进程调用**

### 4. 补偿（部分失败后恢复一致）

事务内失败 → 数据库自动回滚，无需补偿。**补偿处理的是「已部分成功的链路」**：
- 扣了库存、优惠券标记失败 → 事务应包住两者（回到⑥事务边界检查）
- 跨服务无法用本地事务 → 设计补偿动作（失败后反向操作）或最终一致（对账任务+人工干预入口）
- 检查点：**一个业务动作写多个聚合/调多个服务的地方**

| 用例 | 幂等方案 | 并发风险与方案 | 超时行为 | 补偿动作 |
|------|---------|--------------|---------|---------|
| 创建订单 | client_token 去重 | 库存乐观锁 | 支付超时→30min取消回补 | 事务包住库存/订单/券 |

## 阶段⑧ 设计评审与文档

### ADR：决策记录（设计文档的灵魂）

**说不清 why 的设计等于没设计。** 每个关键决策记录四要素：

```
### 决策：订单明细存商品快照而非 JOIN
- 背景：商品改名/改价会污染历史订单（真实事故）
- 备选：a) JOIN 实时取  b) 商品改名历史表  c) 明细快照
- 选择：c。b 查询复杂且无法覆盖改价；成交价本来就与当前价不同，快照绕不开
- 代价：商品名冗余存储；快照字段清单需维护
```

**必须写 ADR 的决策**：为什么先接口后表结构、快照 vs JOIN、软删 vs 硬删、要不要外键、同步 vs 异步、分表与否。

### 评审前的自查（挑战自己）

拿三个问题挑战设计：
1. 量级 ×10 时哪张表先崩？（→ 有没有归档/分表预案）
2. 每个状态机：非法迁移挡住了吗？（并发 + 幂等）
3. 半年后需求变了（如「一人多角色」「多租户」），哪个决策会被推翻？（→ 标注演进路径）

### 组装设计文档（最终产出）

```
# XX 功能设计文档
1. 需求理解（澄清记录 + 概念模型 + 用例走查）
2. 接口设计（API 契约，含幂等与错误码）
3. 表结构设计（ER + DDL + 索引说明）
4. 工程设计（目录分层 + 核心链路时序）
5. 异常与边界（异常矩阵）
6. 设计决策记录（ADR 列表）
7. 待确认问题（未拍板项 + 影响面 + 建议默认值）
```

第 7 节很重要：**评审时带着「已知未决项」比假装完整更专业**——它让评审聚焦在真正需要决策的点上。
