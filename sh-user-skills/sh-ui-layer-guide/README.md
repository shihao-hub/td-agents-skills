# UI 浮层与弹出提示交互选型指南（sh-ui-layer-guide）

> 本技能为前端开发、UI/UX 设计、产品需求评审时的**浮层提示与容器交互选型标准与防坑自查清单**。
> 解决团队沟通中“张口就加个弹窗”、导致打断用户心流或表单装不下的经典体验硬伤。

|---|---|:---:|---|
| 图标/专有名词补充说明 | **Tooltip（文字提示）** | ⚪ 极轻 | 鼠标悬停即出、移开即隐，绝不可藏必填项与核心数据 |
| 操作成功/失败简短反馈 | **Toast / Message（轻提示）** | 🟡 轻度 | 居中或顶部浮现 2~3 秒自动消失，不阻断后续点击 |

## 一、浮层组件图谱（按打扰程度从轻到重）

不要把所有弹出来的东西都叫“弹窗”。从最安静到最霸道，各组件层级与红线分工明确：

### 1. Tooltip（文字提示）
- **触发与生命周期**：鼠标悬停（Hover）或轻触即出，鼠标移开立刻隐去。
- **正向场景**：辅助解释图标含义、被省略号截断的长文本全称、操作快捷键提示。
- **🚨 红线禁忌**：
  - 严禁把核心操作指引或必填项校验规则塞进 Tooltip（移动端无法 Hover，易造成信息断层）；
  - 严禁在 Tooltip 内放置可点击的链接或复杂交互。

### 2. Toast / Message（轻提示）
- **触发与生命周期**：操作完成后触发，浮现 2~3 秒（通常 2000~3000ms）后自动淡出消失。
- **正向场景**：轻量操作状态反馈（“复制成功”、“草稿已自动保存”）。
- **🚨 红线禁忌**：
  - 严禁在普通 Toast 里塞交互按钮（用户还在阅读，浮层可能已经自动销毁，点空体验极差）；
  - 带有关键报错且需要排查的内容（如带错误码、接口异常堆栈）建议使用 Notification 或 Alert，不可一闪而过。

### 3. Alert / Banner（警告提示/通告栏）
- **触发与生命周期**：嵌在页面顶部或表单首部，页面加载时常驻，或在触发特定条件时渲染；可设手动关闭（×）。
- **正向场景**：全局系统维护公告、账户余额不足预警、表单顶部批量校验未通过提示。
- **🚨 核心特征**：非模态、占据文档流高度，不遮挡下方操作，提醒用户但不停滞主流程。

### 4. Popconfirm（气泡确认框）
- **触发与生命周期**：点击按钮时，以该按钮为锚点向上/下就近弹出小气泡，带“确定/取消”。
- **正向场景**：**高频单项确认的最佳选择**。例如管理后台列表每行末尾的“删除”、“下架”、“重置密码”。
- **💡 体验优势**：
  - 鼠标移动距离从屏幕中央缩小到十几像素；
  - 消除屏幕大面积暗色遮罩带来的突兀感；
  - 连续批量清理数据时，操作行云流水。

### 5. Modal / Dialog（模态对话框）
- **触发与生命周期**：屏幕正中央弹出，背后整页添加半透明深色蒙层（Backdrop/Mask），锁定焦点。
- **正向场景**：
  - 涉及资金、删除核心数据等不可逆的破坏性阻断；
  - 简短强交互输入（如“输入验证码”、“重命名文件夹”）。
- **🚨 体验代价**：彻底打断用户当前心流，迫使用户在“取消”与“确认”中二选一，属于最重武器，切忌滥用。

## 二、【弹窗 vs 抽屉 vs 页面】选型决策树

当需要承载较多表单项或内容时，如何在大厂交互规范中优雅选型？按两个维度推导：

```
                              [需要承载新内容/表单]
                                       │
                  ┌────────────────────┴────────────────────┐
           [维度一：看信息量与长短]                  [维度二：看是否需对照上下文]
                  │                                         │
        ┌─────────┴─────────┐                     ┌─────────┴─────────┐
     [内容较少]          [表单很长/深度内容]       [需要对照主列表]      [独立完整主流程]
        │                   │                     (边看边改不丢焦点)    (如下单/支付/多步向导)
        ▼                   ▼                             ▼                   ▼
    【弹窗 Modal】      【抽屉 Drawer / 新页面】       【抽屉 Drawer】        【新页面 Page】
 (常用宽: 400/520/720)
```

### 维度一：看信息量与长短
- **内容少、轻量聚焦** → **Modal 弹窗**
  - 大厂常用宽度规范一般遵循三档：
    - `400px`（极简确认、单字段输入）
    - `520px`（标准表单，4~6 个字段）
    - `720px`（含左右分栏或复杂小表格）
- **表单很长、层级很深** → **Drawer 抽屉** 或 **新页面**
  - 如果弹窗高度超出屏幕 80% 并产生内部上下滚动条，立即重构为抽屉或新页面。

### 维度二：看是否需要对照主界面（上下文连贯性）
- **需边看边改、对照主列表** → **Drawer 抽屉**
  - 经典场景：后台订单列表，运营人员点开某一笔订单看详情或备注，改完后关掉抽屉直接看下一条。背后列表滚动条位置、筛选条件、搜索输入完全不动，心智负担极低。
- **流程彻底切换** → **独立新页面（Page）**
  - 经典场景：创建大型项目、下单结算、包含 3 步以上的分步向导（Wizard）。需要独立的 URL 地址（方便收藏与直接分享）、支持浏览器前进后退。

## 三、3 个 90% 人都踩过的防坑铁律

### 铁律 1：表单弹窗严禁点击蒙层（Backdrop/Mask）直接关闭！
- **血泪教训**：用户认真填写了十几项内容，手滑不小心点到了弹窗外面空白的暗色蒙层，弹窗瞬间销毁，输入内容灰飞烟灭。
- **落地规约**：
  1. 所有承载表单或可编辑状态的 Modal，**必须显式禁用点击蒙层关闭**：
     - Ant Design / Element Plus: 设置 `:maskClosable="false"` / `maskClosable={false}`
  2. 必须保留右上角明确的关闭按钮（×）和底部的“取消”按钮；
  3. 若用户点击“取消”或“×”，且检测到表单已发生改动（`isDirty`），必须弹出二次拦截：“当前有未保存的内容，确定要放弃修改吗？”；
  4. 进阶体验：针对长表单提供本地草稿自动缓存（LocalStorage / IndexedDB），误退后再次打开可一键恢复。

### 铁律 2：能支持撤销（Undo），就别弹二次确认窗！
- **血泪教训**：用户点个归档或普通删除，频繁弹出“确定要删除吗？”，导致用户形成肌肉记忆，看都不看就直接狂点“确定”，彻底失去了防错意义。
- **落地规约**：
  1. **低风险/可反悔操作**：直接执行前端乐观更新或后端标记删除，界面弹出带【撤销（Undo）】操作的轻提示条，给予 5 秒倒计时可逆窗口；
  2. **不可逆/高破坏性操作**：只有涉及资金扣费、彻底清空库表、永久注销等无法找回的操作，才允许使用 Modal 弹窗阻拦。

### 铁律 3：确认按钮严禁只写生硬的“确定”与“取消”！
- **血泪教训**：用户的即时注意力聚焦只有 200~300 毫秒。弹窗标题写着“确定要退款并放弃此权益吗？”，底部两个按钮写着【确定】和【取消】，用户大脑需要额外转弯分析“确定是放弃还是保留”。
- **落地规约**：
  - 按钮文案必须采用**动宾短语**，明确指出操作后果：
    - ❌ 【确定】 / 【取消】
    - ✅ 主按钮：`确认扣费并退票` ｜ 次按钮：`放弃退票`
    - ✅ 主按钮：`保留草稿并退出` ｜ 次按钮：`直接丢弃`
  - 破坏性主按钮建议赋予危险色（红色/Danger），引导用户产生警惕感。

## 四、团队沟通“翻译器”（业务方说加弹窗时的应对指南）

| 业务方/产品常见口述 | 实际背后的体验痛点 | 建议沟通与落地话术 |
|---|---|---|
| “这里点一下，加个弹窗让用户填信息” | 如果表单字段超过 6 个，弹窗会非常憋屈 | “这个表单字段较多，做弹窗容易产生双滚动条，建议改用**右侧滑出抽屉**，用户还能对照左侧数据填。” |
| “列表每一行加个删除，点删除弹窗确认” | 用户批量删 10 条需要挪 10 次鼠标到屏幕中间 | “单行删除频率高，做中央模态弹窗太打断节奏，建议用**按钮旁的气泡确认框（Popconfirm）**，鼠标不用挪窝。” |
| “做个批量归档，每次都弹窗问一下防止手滑” | 频繁弹窗让人麻木，变成无效阻碍 | “我们可以直接归档并在顶部出个 **5 秒可撤销的 Toast**，用户真手滑了点撤销就能还原，体验更流畅。” |
