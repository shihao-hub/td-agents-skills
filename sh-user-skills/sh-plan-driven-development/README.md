# Plan-Driven Development：统一计划与规划工作流

> 本技能是 **工程规划与计划模式的唯一总入口**。  
> 统一收敛两种截然不同的规划诉求：
> 1. **交付计划模式（默认 / `--kiro`）**：以单文件 `plans/{NN}-{feature}.md` 为中心，严格执行“澄清 ➔ 落盘 ➔ 批准 ➔ 连续执行”；
> 2. **探索规划模式（`--claude`）**：以方案对齐与架构探索为中心，严格执行“只读探索 ➔ 权衡澄清 ➔ 方案与关键文件呈现 ➔ 审批门”，防范冒进改动既有系统；
> 3. **架构扩展预留**：预留 `--agy`（Antigravity 任务编排）与 `--dsh`（长思维链深度推演）分发槽位。

---

## 零、分发引擎与模式选择

当用户呼叫本技能时，AI 根据命令参数或用户意图自动选择对应的规划流派：

| 模式 / 标记 | 核心目标 | 产出物形态 | 典型触发场景 |
|---|---|---|---|
| **默认交付模式（Default / `--kiro`）** | 确定性落地交付 | `plans/{NN}-{feature}.md`（含任务复选框、真实构建命令、Demo 预期） | 需求明确，需要分步落地、改动多个文件、大中型重构或功能迭代 |
| **探索规划模式（`--claude`）** | 架构方案探索与对齐 | 对话内呈现方案拆解 + `### Critical Files for Implementation`（按需沉淀探索备忘） | 需求高度模糊、架构路线存疑、选型比较，或用户明确要求“Claude 风格/只读 plan” |
| **任务编排模式（`--agy`，预留）** | 多 Agent 协作拆解 | 依赖拓扑图 + Subagent 委派清单 | 多分支并发开发、需要工作区隔离或跨 Agent 交接 |
| **深度推演模式（`--dsh`，预留）** | 形式化状态机推导 | 状态转移矩阵与边界论证 | 复杂高并发竞态、底层锁机制、数学算法推演 |

- **路由判定**：
  - 用户输入 `sh-plan --claude`、`只读规划`、`方案探索`、`claude plan` ➔ 进入 **【模式二：Claude 探索规划模式】**；
  - 用户输入 `sh-plan`、`plan this`、`制定实施计划`、`规划一下` ➔ 默认进入 **【模式一：Kiro 交付计划模式】**。

## 模式一：Kiro 单文件交付计划模式（默认）

以 **澄清 ➔ 调研落盘 ➔ 批准 ➔ 连续执行** 为核心骨架。

### 1. 核心理念与只读纪律
- **规划期严格只读**：在产出计划文件之前，只读探索代码库（Glob/Grep/Read/只读 Shell），严禁修改既有业务代码。
- **强制计划门**：任何涉及新建、修改、删除业务文件的任务，一律先落盘计划、经用户明确批准后才开工。豁免仅限用户显式说“不用计划，直接改”。纯只读操作不设门禁。
- **落盘位置与动态取号（目标归属判定，严禁无脑扔仓库根）**：
  - **位置判定决策树（先判定归属，再镜像换算）**：
    1. **先查 `AGENTS.md` / `CLAUDE.md`**：检查当前仓库是否存在文档归档与目录结构硬约定（如 Monorepo 要求子项目文档镜像到 `docs/projects/<lang>/<subproject>/plans/`，且子仓内禁止建文档目录）；若有约定，**必须以仓库 AGENTS.md 约定为最高准则**！
    2. **判定任务作用域（子项目 vs 父仓级）**：
       - **子项目级任务**（如针对某个具体服务、库或子模块）：实际落盘位置必须跟随目标子项目走，严禁默认扔仓库根或父仓根级 `docs/plans/`。如父仓镜像到 `docs/projects/<lang>/<subproject>/plans/`；若单体独立项目则放该项目的 `plans/`（或项目声明的文档目录）。
       - **父仓级任务**：仅限全仓多模块批量提交、全仓大扫除、根级站点构建等真正跨越所有工程的仓级运维任务，才落盘至父仓根级的 `docs/plans/` 或 `plans/`。
       - **拿不准或语义冲突时**：主动问用户，绝不可不看结构取默认。
  - **取号隔离**：取号必须在**目标落盘目录内部**动态扫描 `^\d+-` 文件，取最大数字 +1，零填充两位（如 `01`、`08`）；每个子项目的 `plans/` 自成独立编号体系，**严禁跨目录参考其他子项目或父仓的编号**！

### 2. 第一步：结构化澄清提问
1. **先复述**：用自己的话 1~2 句复述用户想要什么，确认理解无误后再提问；
2. **结构化代码块提问**：每轮最多 3 个问题，用 ``` 围栏包裹（**围栏内严禁 markdown 加粗语法**，末项固定为自由回答）：
   ```text
   [1]: 这个功能需要兼容现有移动端吗？
   a. 仅桌面 - 实现最简单，交互不受限
   b. 响应式 - 多一套断点样式，工作量约 +30%
   c. 其他 - 自由回答
   ```
3. **收敛节奏**：问完即停并等待回答，回答计入计划要点；通常 2~3 轮内收敛，不为问而问。

### 3. 第二步：调研与计划落盘模板
必须真实阅读项目约定（README/AGENTS.md）、依赖清单与相近功能代码，拿到真实的构建/测试命令。落盘模板格式：

```markdown
# Plan for: <功能或任务名称>

**问题陈述**：要解决什么问题、范围边界在哪
**需求确认**：澄清阶段确认的要点与用户原话决策
**背景现状**：调研发现的代码结构与相关机制
**方案架构**：高层设计（复杂结构配 mermaid 流程图）

**任务分解**（复选框行行首顶格，严禁缩进到代码块内）：
- [ ] Task 1: <目标一句话>
  - 文件：<要新建/修改的真实路径，多文件全列>
  - 实现：<关键步骤与装配逻辑>
  - 验证：<真实构建/测试命令 + 预期结果（反 grep 式伪验证）>
  - Demo：<完成后能演示什么效果>
- [ ] Task 2: <后续任务，接线收尾>
```

### 4. 第三步：审批门与连续执行
- **审批提示**：计划落盘后，对话内输出单屏摘要并提问：“**这份计划可以吗，还是需要调整什么？**”，等待确认，期间不改任何代码。
- **连续执行**：用户明确批准后，按 Task 编号顺序连续执行；完成一项在文件中勾选 `[x]`；执行期默认不写测试不跑测试（验证命令作为备用）；全部完成后输出总结报告。

## 模式二：Claude 探索规划模式（`--claude`）

源自 Anthropic 官方生产级规划模式（references 见 `references/claude-code-originals.md`）。  
核心原则：**在动代码之前先取得用户对方案的认可：进入计划模式，深入探索代码库、设计实现方案，向用户呈现计划请求批准，获批后再实施。前期对齐好过事后返工。**

### 1. 何时进入计划
对实现任务倾向使用计划，除非任务足够简单；进入需征得用户同意。满足任意一条即进：
1. **新功能实现**：添加有意义的新功能；
2. **多种合理方案**：任务可以走多条路径解决；
3. **修改现有代码**：改动影响既有行为或结构；
4. **架构决策**：需要在模式或技术之间做选择；
5. **多文件改动**：预计触及超过 2~3 个文件；
6. **需求不明**：需要先探索才能理解完整范围；
7. **用户偏好会影响走向**：实现存在多种合理做法；
   - 本想通过提问澄清方案的，改为进入计划——计划模式允许先探索，再带上下文给出选项。
*拿不准时，倾向计划（err on the side of planning）。*

### 2. 何时跳过
仅对极简单任务跳过：
- 单行/几行修复（错别字、明显小 bug、微小参数调整）；
- 需求明确、只加一个现成函数；
- 用户已给出极其具体、不可置疑的详细指示；
- 纯调研/探索任务（不产出实现计划，直接调研汇报）。

### 3. 计划模式中做什么
1. **彻底探索代码库**：用 Glob / Grep / Read（必要时 find）彻底摸排代码库；
2. **追踪模式与调用链**：理解既有模式与架构，找相似功能实现作参考，追踪相关代码路径；
3. **设计实现方案**：权衡取舍与架构决策，适当遵循既有工程模式；
4. **澄清先行**：需要澄清方案时先提问（见“先澄清，后定稿”）；
5. **呈现计划并请求批准**：完成实现步骤的规划后，向用户呈现实计划、请求批准；
6. **获批后退出计划模式**：开始动手实施。

### 4. 严格只读纪律（不可越雷池半步）
计划阶段只做探索与规划，严禁：
- 创建任何新文件（Write、touch 等一切形式）；
- 修改既有文件（Edit、Patch 等）；
- 删除文件（rm 等）；
- 移动或复制文件（mv、cp）；
- 在任何位置创建临时文件（包括 /tmp）；
- 用重定向（`>`、`>>`、`|`）或 heredoc 写文件；
- 运行任何改变系统状态的命令。

**Shell 仅限只读操作**：`ls`、`git status`、`git log`、`git diff`、`find`、`cat`、`head`、`tail`；  
**绝不运行**：`mkdir`、`touch`、`rm`、`cp`、`mv`、`git add`、`git commit`、`npm install`、`pip install` 或任何有写副作用的命令。

### 5. 先澄清，后定稿
- 影响需求或方案的问题，在计划定稿**之前**问用户；提问只用于澄清需求或在方案权衡中做选择；
- 定稿时计划必须完整、无歧义，不带未决问题；
- 提问不得引用“计划”本身——用户在计划呈请批准之前看不到计划内容。

### 6. 呈现计划与审批门
- **方案内容**：呈现完整计划（分步实现策略、依赖与顺序、可预见的挑战）；
- **结尾硬性标识**：在方案结语处必须列出实现最关键的 3~5 个文件，标题固定为：
  ```markdown
  ### Critical Files for Implementation
  - `path/to/core_file.ts`: 核心业务逻辑实现
  - `path/to/interface.ts`: 外部暴露接口与协议定义
  - `path/to/config.json`: 配置映射项
  ```
- **审批动作本身即授权**：呈现计划这个动作本身就是批准请求，不需问冗余的“要我继续吗”，直接等待用户审阅反馈；
- 仅当任务需要规划“写代码的实现步骤”时才走审批门。

### 7. 调研任务的例外（不走审批门，直接汇报）
纯调研任务（搜集信息、搜索/读文件、理解代码库）不走审批门，直接调研汇报。典型示例：
1. *“搜索并理解 vim mode 在代码库中的实现”* ➔ **不走审批门**：没有需要规划的代码编写步骤，直接整理调研结果汇报；
2. *“帮我实现 vim 的 yank mode”* ➔ **走审批门**：完成实现步骤规划与 Critical Files 后请求批准；
3. *“新增用户认证功能”* ➔ **先澄清后过门**：拿不准认证方式（OAuth、JWT 等）时先提问澄清，澄清后再走审批门。

### 8. 执行流转（批准后）
- **用户批准** ➔ 退出只读模式，按批准的计划实施；
- **用户给修改意见** ➔ 修订方案后重新呈现、重新等待批准；
- **实施中发现计划有误或需求变化** ➔ 立即暂停，先修正计划与方案，重新对齐后再继续写代码；
- **收尾** ➔ 向用户汇报完成情况与关键变动。
