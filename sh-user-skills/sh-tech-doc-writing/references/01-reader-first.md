# 读者视角与 LLM 二次加工

本文件是所有文档类型共享的总原则，写任何文档前先读这个。

## 为什么「读者视角」是第一原则

一个真实场景：作者用 AI 辅助写了份技术方案，评审人反馈「红色标注的这两部分完全不需要，都是 LLM 结合你的上下文的思维链条」——作者觉得重要，是因为他知道全部背景；读者觉得多余，是因为那些内容只在「作者的思考过程」里有意义，不在「读者的决策信息」里有意义。

判断一段内容该不该进文档，唯一标准是：**它帮读者做了什么决策或理解了什么事实**。如果不是，删。

## 读者画像决定内容取舍

| 读者 | 他要什么 | 他不关心 |
|------|---------|---------|
| 评审的资深工程师 | 为什么这么设计、有什么风险、备选方案 | 字段级实现细节 |
| 下游对接方 | 接口在哪、表结构是什么、怎么联调、错误码 | 你的内部模块划分 |
| 老板 / PM | 多久做完、里程碑、投入产出、风险 | 技术细节 |
| 半年后接手的新人 / 自己 | 当年为什么这么选（ADR）、链路全貌 | 当下的临时讨论 |

一份好文档 = 让这四类人**各自快速找到各自要的章节**。这就是文档要分章节、章节名要直白的原因：读者是在「查」，不是在「读」。

## LLM 二次加工清单：四删、四改、四补、一核

### 删（Delete）

1. **推导与思维链条**：「首先我们分析……其次……综上，我建议……」→ 删掉过程，只留结论（备选对比表 + 选择理由）。
2. **会话痕迹**：「好的，下面是……」「如你所见」「接下来我们可以」「你觉得怎么样」→ 全部删除。
3. **重复内容**：同一观点换着说法出现多次 → 保留最清楚的一次。
4. **与读者无关的细节**：完整代码、完整 schema 复制粘贴、内部实现琐碎 → 换成一句话概括 + 链接。

### 改（Rewrite）

1. **口语 → 书面**：「搞个」「弄一下」「大概是」→「设计」「实现」「约」。
2. **模糊指代 → 明确名词**：「这个方案」→「采集服务的异步抓取方案」。
3. **对话体 → 客观陈述**：「我觉得应该」→「评估结论是」。
4. **术语统一**：同一概念全文只用一个叫法（定了叫「素材」就别混用「材料/内容」）。

### 补（Add）

1. **真实数据**：量级、QPS、表大小估算（没有就标 ⚠️ 待补充，绝不编造）。
2. **真实名词**：实际的服务名、表名、字段名、仓库链接。
3. **背景链接**：依赖的前序方案、需求单、相关系统文档。
4. **元信息**：作者、评审人、日期、状态（草稿/评审中/已定稿）、变更记录。

### 核（Verify）

1. 数字是否与实际一致（量级、估时、里程碑日期）。
2. 结论是否仍然成立（和用户确认过最新口径吗）。
3. 接口/表定义是否与代码或最新设计一致（复制粘贴的旧定义是事故来源）。

## 好坏对比示例

**坏**（思维链 + 会话体，读者不知道你在跟谁说话）：

> 考虑到我们需要对公域素材进行采集，我首先分析了可能的方案。方案一是直接爬取页面，方案二是用官方 API。经过思考，直接爬取可能存在合规风险，页面结构也经常变，所以我觉得应该用官方 API 为主、页面解析兜底。你觉得这样行吗？

**好**（结论先行 + 权衡沉淀成表）：

> 采集链路采用**官方 API 优先、页面解析兜底**的双通道设计。
>
> | 方案 | 优点 | 缺点 | 结论 |
> |------|------|------|------|
> | 官方 API | 合规、结构稳定 | 有配额限制 | ✅ 主通道 |
> | 页面解析 | 无配额限制 | 合规风险、结构易变 | 兜底通道（API 超配额时降级启用） |

区别不在于信息量，而在于：坏版本要求读者陪你走一遍思考，好版本直接给读者可用的结论和理由。

## 发布前十问

1. 删掉所有「过程性」文字后，文档是不是反而更清楚了？
2. 文档里有没有任何一句话，是只有和你聊过天的人才看得懂的？
3. 每个章节的第一句话，是不是该章节的结论？
4. 数字都是具体的吗？有没有「比较大」「很快」「近期」？
5. 架构图/链路图/流程图，该有图的地方有图吗？
6. 为什么这么设计，写了吗？备选方案列了吗？
7. 下游要的接口清单和表结构，能 30 秒内翻到吗？
8. 异常、降级、回滚，各有一句话吗？
9. 排期含联调和测试吗？里程碑有验收标准吗？
10. 元信息（作者/日期/状态/变更记录）齐了吗？
