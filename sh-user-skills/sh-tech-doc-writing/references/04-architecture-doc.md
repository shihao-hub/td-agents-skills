# 架构设计文档：C4 模型 + ADR + arc42

三者分工：**C4 解决「图怎么画」**（视图），**ADR 解决「决策怎么记」**（沉淀），**arc42 是大型系统的完整模板**（12 章，平台/中间件级才需要全套）。

## 一、C4 模型：四层缩放画架构图

核心思想是**地图缩放**：读者先看全景，再逐层放大。专治「一堆框线没人看得懂」的架构图。

| 层级 | 图名 | 回答的问题 | 什么时候用 |
|------|------|-----------|-----------|
| C1 | 系统上下文图 | 系统在世界的位置、和谁打交道 | 老板/新人/评审的第一张图，必画 |
| C2 | 容器图 | 技术栈和职责如何分布（服务/DB/队列） | 技术方案的主图，必画 |
| C3 | 组件图 | 某个服务内部的构件 | 服务内部设计时画 |
| C4 | 代码级（类图） | — | 实践中很少画，交给代码本身 |

- 「容器」指独立运行单元：Web 应用、后端服务、Serverless 函数、数据库、消息队列。
- 技术方案里通常 C1 + C2 就够了；C3 只在某个服务内部复杂时补。

## 二、ADR（架构决策记录）：决策的沉淀

**为什么需要**：半年后没人记得为什么选了 PostgreSQL；新人来了想推翻；同一个坑换个项目再踩一遍。ADR 用最小成本把「为什么」留下来。

**Nygard 五字段模板**：

```markdown
# ADR-007: 素材采集采用官方 API 优先策略

## 状态
已接受（2026-08-25）

## 背景
合规风险评审要求；目标平台页面结构平均每月变动；官方 API 有配额，
配额依赖商务谈判，存在上限风险。

## 决策
我们将采用官方 API 作为主通道、页面解析作为超配额时的兜底通道。

## 后果
正面：合规风险可控、结构稳定、维护成本低。
负面：吞吐受配额限制；需要实现双通道和降级逻辑（约 +5 人日）。
```

规范：

- 编号递增（ADR-001、ADR-002……），和代码放同一仓库。
- 状态只有几种：提议 / 已接受 / 被取代（注明被 ADR-XXX 取代）。
- 「决策」用完整句子写「我们将……」，不写「可以考虑」。
- 后果必须写负面——只写好处的 ADR 没有可信度。

**什么时候写 ADR**：引入或替换基础设施（MQ、数据库、缓存）、重大选型、对外契约变更、明显的性能/一致性取舍。

## 三、arc42（了解即可）

12 章模板：引言与目标 / 约束 / 系统上下文 / 架构策略 / 构件视图 / 运行视图 / 部署视图 / 横切概念 / 架构决策 / 质量场景 / 技术风险 / 术语表。

适用：平台型系统、多团队共享的长生命周期系统。普通业务方案用 C1/C2 图 + 章节内嵌决策表即可，不要套全套 arc42——模板比内容还多是反模式。

## 四、架构文档与方案文档的关系

- **方案文档**：一次性，面向评审，服务于「做不做、怎么做」的决策。
- **架构文档**：持续维护，面向长期，服务于「系统现在长什么样、为什么」。

正确做法：方案定稿后，把其中的架构图（C1/C2）和 ADR **抽出来**沉淀到架构 wiki/知识库；方案文档本身归档。不要让架构知识的唯一载体是一年前的方案文档。

## 架构图反模式

- 一张图塞 30 个框，标注密密麻麻——分层（C1→C2→C3）解决。
- 没有图例，实线虚线混用不知道什么含义。
- 图里只有系统没有数据流向——每条线标上「传什么」。
- 图和文字描述的链路对不上（图更新了文字没更新，或反之）。
