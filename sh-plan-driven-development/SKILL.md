# Plan-Driven Development：计划驱动的规划与执行

## 版本信息

| 项 | 值 |
|---|---|
| 版本 | 2.4.0 |
| 创建 | 2026-08-24 |
| 更新 | 2026-09-19 |

本 skill 的机制提炼自一份真实 plan mode 系统提示词（2026-08 流出版），原文摘录存于 `references/` 目录，仅供研究对照，工作流本身不依赖它。与该原版的一处有意差异：原版把计划写入产品机制托管的专用 plan file，本 skill 默认把计划落盘到项目自己的 `plans/` 目录，文件即审批对象与执行依据（见"核心理念"）。

## 核心理念

Plan mode 的本质是一条纪律：**批准之前只读不写（计划文件本身除外），批准之后计划是唯一事实来源**。

- 计划阶段动手写代码是最常见的失败模式——需求还没确认，代码就已经锁死了实现方向。
- 计划不是一次性的产物。执行过程中它必须与代码保持同步（已落盘时勾选 checkbox、更新结构、追加任务；未落盘时在阶段汇报中明确说明修订），否则它很快沦为废纸，后续阶段就失去了依据。
- 计划要写到"代码级具体"：函数签名、struct 字段、接口 JSON 都要真实可落地。模糊的计划（"设计好扫描模块"）在执行时还要重新设计一遍，等于没计划。
- **默认落盘**：计划文件是规划阶段的产出物，默认写入 `plans/` 约定位置（见"计划落盘位置与编号"），与 spec 流程默认产出三文档一致。落盘≠批准：文件出现后停在审批门，批准前除计划文件外一律只读。用户明确要求"不落盘、只在对话里看"时尊重，此时对话呈现的计划退为审批对象与执行依据。
- **计划不进会话**：完整计划只存在于计划文件中，**不在对话里全文展示**——长文档在会话里没法读，往上翻全靠滚动条。没有写权限时向用户请求切换模式，有写权限直接落盘；对话里只允许出现"模式切换请求"和落盘后的一屏摘要。仅当用户明确要求"不落盘、只在对话里看"时才把全文写进对话（唯一例外）。

## 何时进入计划

**倾向计划**："If unsure whether to use it, err on the side of planning"——拿不准要不要计划时，就计划。前期对齐的成本远低于返工。

满足**任意一条**即应走本流程：

1. **新功能实现**：有意义的新功能（"加个登出按钮"——放哪？点击后发生什么？）
2. **多种合理方案**：可达成同一目标的多条路径（缓存用 Redis、内存还是文件？）
3. **修改现有行为**：影响已有逻辑或结构的变更
4. **架构决策**：需要在模式/技术间做选择（实时更新用 WebSocket、SSE 还是轮询？）
5. **多文件改动**：预计触及 2-3 个以上文件
6. **需求不明**：需要先探索才能确定范围（"让应用变快"）
7. **用户偏好会影响走向**：本来想用提问澄清方案的，改为进计划——计划模式可以先探索再带着上下文给选项

**可跳过计划**的简单任务：单行/几行修复（错别字、明显小 bug）、需求明确且只需加一个函数、用户已给出非常具体的指示、纯调研类任务（不涉及写代码规划）。

**冲突裁决**：一条任务同时命中触发条件与跳过条件时（如"用户给出了具体指示"但存在多种合理方案），以**是否存在方案分歧**为准——有分歧就进计划。跳过仅当三条**全部**满足：单文件、预计改动 <50 行、无方案分歧。

## 任务域三分法：本 skill 管什么、不管什么

开发类任务之外的工作不套本流程。按下表判定，判不清时回到"倾向计划"原则，但先过一遍这个表：

| 任务域 | 判定特征 | 走什么流程 |
|---|---|---|
| **开发类** | 要产出/修改代码或脚本，且非平凡（见上方七条件） | 本 skill：plans/ 落盘 + 审批门 + 阶段执行 |
| **运维执行类** | 按已有 runbook/手册执行的操作（部署、切换、启停服务），有明确既定步骤 | runbook + 对话内呈现步骤 → 批准 → 执行 → 验证；不建 plans/ |
| **事故响应类** | 系统坏了要救（崩溃、卡顿、数据损坏），时间敏感 | 只读诊断 → 对话内方案（含损失评估）→ 批准 → 执行；事后视价值补 postmortem 或追溯计划 |

注意：运维用的脚本依然是"脚本"——凡涉及设计取舍（多种实现路径、参数选择、失败处理策略），就属**开发类**，走本 skill。"它是运维用的"不是豁免理由。

## 工作流

### 阶段 A：计划（read-only，绝不动业务代码）

**A1. 只读研究**

严格禁止：创建文件、修改文件、删除/移动/复制文件、在包括临时目录在内的任何地方建临时文件、用 `>` `>>` `|` 等重定向写文件、运行任何改变系统状态的命令。Shell 只允许只读操作（`ls`、`git status`、`git log`、`git diff`、`find`、`cat` 等）。

用 glob/grep/read 完成以下确认，不要凭记忆假设：

- 项目现有目录结构、代码风格、已有模块——新计划要顺着现有约定长出来
- 技术栈与依赖：计划里引用的库是否已在 go.mod / package.json / pyproject.toml 中？没有的依赖要在"技术依赖"章节声明
- 相似功能的已有实现，可以直接复用的模式优先复用

**A2. 澄清问题**

向用户提 2-4 个真正影响方案的问题，典型如：范围边界（哪些不做）、产品形态（CLI/Web/库）、特殊约束（性能/平台/兼容）。用户没说清且会影响计划的需求，在这一步问掉，不要脑补进计划。这一步必须在定稿计划**之前**完成——带着未决问题出计划，用户批准的将是一份含糊的计划。

**A3. 起草计划**

把完整计划按下方模板写入 `plans/{NN}-{feature_name}.md`（取号与命名规则见"计划落盘位置与编号"；用户明确指定了其他文件名或位置时，以用户指定为准）。计划文件是批准前唯一允许的写文件动作，其余一律只读。按写权限分三种情形：

- **有写权限**：直接落盘，**不在对话消息中完整呈现计划全文**（见"核心理念：计划不进会话"）。
- **无写权限（环境 Plan Mode 等只读约束）**：不写文件、也不展示计划全文，向用户输出**模式切换请求**（对齐 spec 流程），说清三件事——① 落盘计划需要写文件权限；② 计划将写入的完整路径与文件名；③ 有异议请一并告知。用户切换模式并示意继续后再落盘（时序见"与环境级 plan mode 的关系"）。
- **用户明确要求"不落盘、只在对话里看"**：跳过写文件，计划全文在对话中呈现，退为审批对象与执行依据（唯一允许全文进对话的情形）。

**A4. 摘要并等待批准（审批门）**

计划文件落盘后，在对话中给**一屏摘要**：计划文件路径、项目定位一句话、Phase 划分与总估时、关键决策点——然后**停在审批门等待批准**。摘要只承担"指路"职责（告诉用户去看哪个文件、重点是什么），不复述计划内容；**审批对象是计划文件本身**，用户打开文件审阅。**落盘 + 摘要这个动作本身就是审批请求**——不要在摘要后再问"这个计划可以吗？需要我调整吗？"这类问题，那是把审批门降格成了普通提问。用户要么批准（进入阶段 B），要么给修改意见（回到 A3，计划文件随修订同步更新）。**未获批准不得进入阶段 B。**

仅对话呈现（用户明确要求不落盘）的例外情形下，摘要之外需全文呈现，对话计划即审批对象。

### 阶段 B：执行（用户批准后）

**B1. 逐 Phase 执行**

- 严格按 Phase 顺序执行，任务编号全局递增（跨 Phase 不重复），方便引用
- 已落盘（默认）：每个任务完成后立即把计划文件里的 `- [ ]` 改为 `- [x]`
- 未落盘（用户明确要求只在对话中时）：在每个 Phase 汇报（B3）中逐条说明任务完成情况

**B2. 活文档原则**

实现中发现计划有误或需求变化时：**先更新计划（已落盘则改计划文件的数据结构/接口/阶段任务，未落盘则在对话中明确说明修订内容），再改代码**。顺序不能反——代码先行会让计划失真，后续 Phase 就失去了依据。新发现的任务追加进对应 Phase 的任务列表（落盘时补进 checkbox 列表）。

**B3. 阶段验收**

每个 Phase 结束，对照该 Phase 的"验收标准"逐条自检，向用户汇报结果后再进入下一 Phase。验收不通过的项要么修完要么明确说明原因。

**B4. 收尾**

全部完成后：向用户做整体汇报（完成了什么、验收情况、遗留项），并更新计划文件页脚的"最后更新"日期与版本号（无计划文件、仅在对话中执行时跳过）。

### 与环境级 plan mode 的关系

运行环境可能自带 plan/build 模式切换（系统提醒层面的只读约束）。对齐方式：

- 环境只读期（plan mode）＝本 skill 的阶段 A：做只读研究（A1/A2），**不要试图写任何文件，也不要把计划全文贴进对话**
- A3 到落盘那一步且没有写权限时，输出模式切换请求（仿 spec 流程），参考措辞：

  > 需要你切换模式：落盘计划（写 `<完整路径>/<NN>-<feature>.md`）需要写文件权限，当前处于 Plan Mode（只读），无法创建任何文件。请退出 Plan Mode / 切换到可写入模式，然后告诉我继续，我会落盘计划文件并给出摘要，等你批准后再开始执行。如有异议请一并告知。

- 环境放行后：落盘计划 → A4 摘要 → 审批门
- 两套审批门取**交集**：环境批准与用户批准都过了才动业务代码；环境已放行但用户未批准时，停在 A4 审批门不动

### 补救：未走流程但已执行

任务没走本流程但已执行完，事后发现设计决策有长期价值（下次还会用到、跨会话要接手）时：**追溯补一份计划**写入 `plans/`，文件名加 `-retro` 后缀（如 `plans/03-dst-crash-recovery-retro.md`），页脚版本标注 v1.0-retro，内容聚焦"当时为什么这么决策"（任务已完成，不写 checkbox 任务清单）。纯执行、无决策价值的不补。

## 计划落盘位置与编号

计划是**单文件**，不建子目录：一份计划一个 `.md` 文件，平铺在 `plans/` 下（形如 `plans/01-xxx.md`）；与 spec 流程的目录形态 `specs/xxx/yyy`（一个编号目录装 requirements/design/tasks 三份文档）刻意区分。该结构约定是通用的，不绑定任何仓库或项目形态；`plans/` 的具体落点由项目现有目录结构决定（见下）。

- **文件名**：`plans/{NN}-{feature_name}.md`，如 `plans/01-ecommerce.md`。`{feature_name}` 为功能名的英文单词小写、以 `-` 分割（如 `user-auth`；用户用中文描述时，由你拟对应的英文短词）
- **`plans/` 放哪里**（落位前必须先看现场——先扫项目结构，禁止不看结构直接取默认）：按三步判定：
  1. 项目或用户已声明"文字类产物归 `docs/`"的约定（写在 AGENTS.md/README 里，或用户在对话中明说）→ `docs/plans/`
  2. 项目已有 `docs/` → 判其语义：**项目文档中心**（收纳说明、手册、计划等文字产物）→ `docs/plans/`；**知识参考库**（学习笔记、外部资料）→ 项目根 `plans/`
  3. 语义判不清 → 问用户一句再落位，不自行默认

  落位后，同一项目的所有计划文件始终放在同一个 `plans/` 下
- **编号规则**（对齐 specs 的约定，作用于文件名而非目录）：
  - 取号：扫描 `plans/` 下所有文件名形如 `^\d+-` 的计划文件，取最大编号 +1；`plans/` 为空或不存在时从 `01` 开始。无数字前缀的旧文件（如 `plans/roadmap.md`）忽略、不参与计算、保留原样不改名
  - 零填充：个位数补零（`01`–`09`），`10`–`99` 为两位，超过 99 自然进位为三位（`100+`）
  - 同号冲突：目标编号已被占用时，顺延取下一个未被占用的编号
  - 99 上限：新编号将达到 `100` 及以上时，先向用户提示一次"计划数量已达到 99 个"；用户仍要求创建则照常 +1 继续——提示仅作告知，不阻断
  - 编号在 `plans/` 的所有文件之间全局递增，一个项目一个序列；与 `specs/` 的编号相互独立、互不影响（同一项目可两者并存）
  - **取号发生在落盘那一刻**，不是进入工作流就取号——仅在对话中、不落盘的计划不占用编号；从已有计划文件继续工作时按原文件名定位，编号规则只作用于新建计划
- **用户指定优先**：用户明确给出文件名或位置（如"文件名就叫 dev-plan.md"、"存到 docs/roadmap.md"）时，以用户指定为准，不强行套 `plans/` 约定。**注意区分两种"指定"**：用户指定**计划文件**的名字/位置 → 计划照写，只是换地方；用户指定**交付物**（脚本、README 等）的位置/形式 → 不构成对计划文件的豁免，`plans/` 照常落盘，除非用户明确说"不要计划文件/不落盘"

## 计划模板

落盘文件使用此模板，落盘位置与文件名见"计划落盘位置与编号"。起草时按此骨架逐节填充，**不适用整节删除，不要留空壳**；仅在用户明确要求不落盘、对话呈现的例外情形下，末尾页脚（最后更新/作者/版本）可省略。标 ◇ 的章节按项目形态选用：

````markdown
# <项目名> 开发计划

## 项目概述
一句话定位 + 核心需求（3-5 条 bullet，尽量来自用户原话，不自行发明范围）

## 项目结构
目录树，每个文件一行职责注释；只列要新建/改动的文件，不列无关文件

## 核心数据结构
代码级类型定义：真实字段、真实类型、真实 tag（json/yaml 等），直接可以抄进代码的程度

## 对外接口设计（◇ 按形态选用其一或组合）
### Web API（项目含 HTTP 服务时）
端点表格（方法/路径/说明）+ 关键端点的请求/响应 JSON 示例
### CLI 设计（命令行工具时）
命令/子命令/参数/退出码表格 + 使用示例
### 前端界面设计（项目带 UI 时）
页面布局（导航/列表/表单/状态展示）、交互流程、UI 技术栈
### 其他形态（库/定时任务/导入脚本……）
用等价方式描述"外部如何看待和使用这个系统"：公开函数签名、触发方式、输入输出

## 核心模块设计
每个模块一节，包含：职责 / 依赖 / 关键函数签名 / 核心逻辑
（对比规则、执行顺序、错误处理策略这类容易含糊的点在这里写死）

## 实现步骤（分阶段）
Phase 1..N，每个 Phase：
- 3-6 个任务（checkbox，编号全局递增）
- **验收标准**（必备，不可省略）：可操作、可验证的"完成"定义

Phase 划分原则：按"可验证的增量"划分，让每个 Phase 结束都有可运行/可检查的东西，
而不是按技术层切（如"先把所有 struct 写完"那种 Phase 是反模式）。

## 技术依赖
依赖清单 + 每个依赖为什么需要

## 关键技术点
带理由的技术决策：选 A 不选 B 的原因、关键实现片段（如哈希对比、原子写入、并发保护）

## 预计时间
每 Phase 估时表 + 总计

## 后续扩展（二期）
明确划出本期范围之外的 roadmap，防止计划膨胀

## 注意事项
性能 / 安全 / 跨平台 / 错误处理等风险点，每条带应对思路

---
**最后更新：** <日期>
**作者：** AI & User
**版本：** v1.0
````

## 写作原则

1. **代码级具体**：函数签名、struct 字段写到执行时不需要再设计的程度。
2. **每 Phase 必有验收标准**：写成可操作的检查项（"访问 http://localhost:8000 显示任务列表"），不写"功能正常"这种无法验证的话。
3. **决策带理由**：关键技术点记录"为什么"，跨会话接手或执行中动摇时不用重新推导。
4. **任务粒度 0.5-2 小时**：太大说明还没想清（继续拆），太小是浪费计划篇幅。
5. **不猜**：影响方案的不确定点进 A2 澄清，不要以假设的形式写进计划。
6. **条件章节按形态取舍**：纯 CLI 工具不写"API 设计"和"前端界面"；Web 后端不写"CLI 设计"。判断标准是"外部怎么用这个系统"，选对应子模板。
7. **一期/二期分界清晰**：诱惑性但非核心的功能全部推到"后续扩展"。

## 与 sh-spec-driven-development 的分工

- 本 skill：**单文档**计划（默认落盘为 `plans/{NN}-{feature_name}.md`，批准后执行并勾选 checkbox），计划与执行一体的轻量流程，适合工具、中小型项目。
- spec 流程：requirements.md / design.md / tasks.md **三文档**，存放在 `specs/{NN}-{feature_name}/`，适合需求复杂、需要正式评审的项目。
- 用户没指定时默认本 skill；用户说出 "spec"、"三份文档"、"requirements/design/tasks" 时走 spec。

## 常见坑

- **批准前手痒写代码**：plan mode 的核心纪律就是这条，研究阶段只允许读——批准前唯一允许写的文件是 A3 的计划文件本身。成熟的实现会在 plan mode 下直接移除写入工具来兜底，本 skill 靠自律，更要当心重定向符和"顺手建个临时文件"这类隐蔽写入。
- **该计划的任务不计划**：plan mode 的通行原则是"err on the side of planning"。看起来简单的需求（"加个删除按钮"）往往涉及位置、确认弹窗、API、错误处理、状态更新——满足触发条件就进计划流程。
- **计划写完就扔**：落盘后 checkbox 不勾、结构改了不同步；未落盘时执行偏离计划也不说明——计划失去"唯一事实来源"作用，B2 不是可选项。
- **落盘后不等批准**：落盘只是产出审批对象，不是批准本身——写完计划文件必须停在审批门，未获批准绝不动业务代码。
- **Plan Mode 下全量刷计划**：只读期把几千字计划全文贴进对话——审批对象错位，用户没法读，往上翻全靠滚动条。正确做法：只读期只研究和澄清，A3 到落盘一步发模式切换请求，落盘后靠计划文件审批 + 一屏摘要（见"核心理念：计划不进会话"）。
- **用提问代替审批门**："计划 OK 吗？"不该作为普通问题出现——展示计划即请求批准，用户回复批准/修改意见即可。
- **纯调研任务套计划流程**："帮我理解 X 的实现"是研究任务，不产出实现计划，直接调研汇报即可，不要走进计划/审批流程。
- **把"指定交付物"当"豁免计划"**：用户说"脚本放 xx 目录、再配个 README"≠ 不要计划文件——交付物位置和计划文件是两回事，计划照落 `plans/`。
- **运维/救火任务硬套计划**：救火走"诊断→方案→执行"，别让落盘流程拖慢响应；但救火中产出的新工具脚本（如自动回档器）属开发类，火灭了之后该补计划就补。
- **数据结构写伪代码**：执行时还要重新设计字段和 tag，计划的价值直接减半。
- **验收标准不可验证**："界面正常"无法自检，"点击同步按钮后进度条从 0 到 100 且任务状态变为 completed"才可以。
- **Phase 按技术层切**：每个 Phase 应交付可验证的增量，而不是某一类文件的集合。
