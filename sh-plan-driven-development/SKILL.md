# Plan-Driven Development：澄清 → 计划 → 批准 → 执行

## 版本信息

| 项 | 值 |
|---|---|
| 版本 | 1.3.0 |
| 创建 | 2026-09-21 |
| 更新 | 2026-09-21 |

本 skill 的机制提炼自两份真实生产级提示词：编排（orchestrator）侧提供阶段门控与子代理调度纪律，规划（planner）侧提供只读约束、结构化澄清与任务拆解规则（2026-09 提取，已去除全部产品专属机制与工具名，适配对话式 agent 环境：子代理可用可不用，规则不变）。落盘与编号约定对齐 sh-spec-driven-development / sh-claude-plan-mode。

## 核心理念

四段式纪律：**澄清 → 计划（只读）→ 批准 → 执行**。

- 复杂任务先澄清、再计划、获批准、后动手。计划一旦批准就是唯一事实来源：不重新计划，只针对意外阻塞提针对性问题。
- **规划期严格只读**：从开始澄清到计划获批，只允许读文件、搜索、跑只读命令，不做任何修改（计划文件本身除外）。用户在规划期要求"直接改 / 先实现一小部分"时，用固定话术拒绝："我在规划阶段，只读不改；先把计划定下来，批准后立刻动手。"
- **计划默认落盘**：计划定稿即写入 `plans/{NN}-{feature_name}.md` 单文件（不建子目录），**文件是审批对象与执行依据**；对话只承载一屏摘要与门，不刷计划全文——长文档在会话里没法读。用户明确要求"不落盘、只在对话里看"时尊重，此时对话呈现的计划退为审批对象与执行依据（唯一例外）。
- **计划门是硬停止点**：发出摘要与 `[OPTION: Go | Go All | Cancel]` 后立即结束回合——不调工具、不做调研、不开始任何执行工作。等待批准期间做的每一件事都在破坏门控。
- **判断复杂性看内在复杂度，不看步骤数量**。一个任务可以有很多步骤但依然简单（查点资料 → 提一个 PR）——直接做。别把单一连贯任务变成仪式。
- **澄清有节奏**：问题分组投喂，一轮最多三个，拿到回答再问下一组。
- **计划是活文档**：执行期的每个 checkpoint 同步回计划文件（勾选、追加结论），文件始终反映最新事实——跨会话接手时它是唯一依据。

**硬性关卡**：计划落盘本身**不构成执行授权**。落盘后必须停在审批门，执行只能由用户在对话中明确选择 **Go** 或 **Go All** 启动；含糊回应或没有回应都不算批准，必须等待。绝不能在用户批准前开始执行任何任务——包括"先做无害的第一步""先把环境准备好"这类看起来无害的铺垫。

## 何时计划（裁决规则）

**显式计划请求永远赢，任何语言都算**："计划一下"、"plan this"、"break this down"、"拆解这个任务"、"先出个方案"、"map out a strategy"。命中即必须走完整流程：再小的任务也拆出聚焦任务、以验证收尾，绝不直接开答或直接执行。

没有显式请求时，**三条全中**才计划：

1. 多个相互区分的依赖阶段（阶段之间有先后依赖）
2. 跨多个文件/系统
3. 存在有用的中间方向检查点（中途让用户把一次关是值得的）

**直接执行**（不需要计划）的清单：读取/问答/命令/查询类、中小型编辑、单文件或机械性改动、处理少量 review 意见、任何"唯一自然的检查点就是完成"的一次聚焦通过。几次工具调用本身不构成计划理由。

进入计划后：先做只读的范围调研（scoping research）——**必读项目约定文件**（README、AGENTS.md、贡献指南、项目内规范/约定类文件），它们规定改动必须怎么做、怎么测、怎么提交，是计划的硬约束；再读依赖清单与构建配置，拿到项目**真实的构建/测试命令**；读任务会碰到的源文件与相近功能的既有实现——然后进入澄清。**计划获批之后不再允许"再调研一轮"**——那是重新计划的变体。

## 澄清阶段

计划的质量取决于澄清的质量。规则：

1. **先复述**：用自己的话 1-2 句复述用户想要什么，再开始提问——复述错了，后面全错。
2. **结构化提问**，固定格式：

```
[1]: 这个面板需要支持移动端吗？
a. **仅桌面** - 实现最简单，交互不受限
b. **响应式** - 多一套断点样式，工作量约 +30%
c. **其他** - 自由回答

（回答任意子集即可，如 "1=a"，也可以直接给自己的答案）
```

3. **每轮最多 3 个问题**，问完就停、等回答；用户的回答**追加进计划**（它们是需求的组成部分），再基于回答组织下一组问题。
4. **该问什么**：边缘情况、使用体验、技术约束、成功标准。根据已有回答调整后续问题——上一轮的答案常常让下一轮的问题变得多余。
5. **收敛即停**：澄清出现自然结论就进入计划，不为问而问；通常 2-3 轮内收敛，仍在发散说明需求本身没定，让用户先想清楚。
6. **调研输入**：计划前需要研究的技术点，问用户三件事——还要研究什么主题、有没有推荐的资源（文件/网站/工具）、用户已有哪部分知识可以直接贡献。

## 计划格式（强约束）

计划由两部分组成：**计划文档**（做什么、为什么）+ **执行编排**（何时做、何时停）。

### 计划文档

```
📋 Plan for: "Migrate auth module to new API"

**问题陈述**：要解决什么问题、范围边界在哪
**需求**：澄清阶段确认的需求（含用户的原话决策）
**背景**：调研发现与相关现状
**方案**：高层设计，如何满足需求；复杂结构配 mermaid 图

**任务分解**：
Task 1: <目标一句话>
  - 文件：<要新建/修改的真实路径，多个全部列出>
  - 实现：<关键步骤/指导>
  - 验证：<项目真实的构建/测试命令 + 预期结果>
  - Demo：<完成后能演示什么>
Task 2: ...
```

任务分解规则（拆解时逐条对照）：

- 每个任务以 `Task N:` 开头，顺序编号，N 全局唯一
- 每个任务五要素：**目标**（清晰的实现目标）、**文件**（要新建/修改的真实路径——不许写"相关文件"这类模糊指代）、**实现**（指导性步骤）、**验证**（项目真实的构建/测试命令 + 预期结果）、**Demo**（这个任务完成后能演示的工作功能——说不出 Demo 的任务是验收不了的任务）
- **验证必须是真验证**：用调研阶段拿到的项目真实测试/构建命令，并写明预期结果。反例：❌"grep 确认新函数存在"；正例：✅"跑改动模块的单元测试并确认全部通过"。命令没报错不等于功能正确；验证行没写预期结果的视为不合格
- **测试驱动 + 可运行增量**：按测试驱动的顺序构建每个组件；每个任务必须交付一个可运行、可演示的功能增量；优先最佳实践、增量推进、尽早测试，任何阶段不允许复杂度大跳变
- **衔接成线**：每个任务建立在前面的任务之上，最后以"把所有东西接起来"收尾；**不允许遗留未接线的孤儿代码**

### 执行编排

任务分组成 Stage：

```
Stage 1: <标题>
  - Task 1、Task 2（并行）

Stage 2: <标题>
  - Task 3
  ...

Stage N（最后一个）: 验证
  - 全量测试、确认没破坏任何东西
```

- Stage 之间**顺序**执行，Stage 内任务**并行**（有子代理就批派发，没有就顺序做）
- 每个 Stage 独立可验证；**最后一个 Stage 必须是验证**
- 限制单 Stage 复杂度而不是 Stage 数量：5-8 个简单 Stage 没问题，别塞凑数的；不要把 Stage 挂在长轮询上干等

`[OPTION: Go | Go All | Cancel]` 是**对话门**，出现在对话摘要的最后一行：恰好一次、其后无任何内容；它与通用的 `[OPTIONS: …]` 选项行是**不同标签**，一条消息里不得同时出现；不写入计划文件。

## 计划落盘位置与编号

计划是**单文件**，不建子目录：一份计划一个 `.md` 文件，平铺在 `plans/` 下（形如 `plans/01-ecommerce.md`）——与 spec 流程的目录形态 `specs/{NN}-{name}/`（一个编号目录装三份文档）刻意区分。

- **文件名**：`plans/{NN}-{feature_name}.md`。`{feature_name}` 为功能名的英文单词小写、以 `-` 分割（如 `user-auth`）；用户用中文描述时，由你拟对应的英文短词
- **取号**：扫描 `plans/` 下所有文件名形如 `^\d+-` 的计划文件，取最大编号 +1；`plans/` 为空或不存在时从 `01` 开始。无数字前缀的旧文件（如 `plans/roadmap.md`）忽略、不参与计算、保留原样不改名
- **零填充**：个位数补零（`01`–`09`），`10`–`99` 为两位，超过 99 自然进位；新编号将达到 `100` 及以上时先向用户提示一次，用户仍要求则照常 +1——提示仅作告知，不阻断
- **同号冲突**：目标编号已被占用时，顺延取下一个未被占用的编号
- **取号发生在落盘那一刻**：仅在对话中、不落盘的计划不占用编号；从已有计划文件继续工作时按原文件名定位，编号规则只作用于新建计划
- **`plans/` 放哪里**（落位前必须先扫项目结构，禁止不看结构直接取默认）：① 项目或用户已声明"文字类产物归 `docs/`"→ `docs/plans/`；② 已有 `docs/` 时判语义：项目文档中心 → `docs/plans/`，知识参考库 → 项目根 `plans/`；③ 语义判不清 → 问用户一句再落位。同一项目的所有计划文件始终放在同一个 `plans/` 下
- **编号在 `plans/` 的所有文件之间全局递增**，与 sh-claude-plan-mode **共用同一目录、同一序列**；`plans/` 与 `specs/` 的编号相互独立
- **用户指定优先**：用户明确指定计划文件名/位置时以其指定为准；但用户指定的是**交付物**（脚本、README 等）的位置/形式时，不构成对计划文件的豁免，`plans/` 照常落盘
- **落盘文件形态**：计划文档 + 执行编排两段原文，Task 行与 Stage 内任务清单转为 `- [ ]` checkbox（执行期勾选），Stage 标题升为 `## Stage N`；末尾加页脚（最后更新 / 作者 / 版本）
- **无写权限**（环境只读约束）：不写文件、也不把计划全文贴进对话充数，输出模式切换请求——说清需要写文件权限、将写入的完整路径；用户切换模式后再落盘走门

## 审批门

**选项语义：**

- **Go** —— 执行下一个 Stage，之后在每个 Stage 前暂停再批
- **Go All** —— 自动执行全部剩余 Stage，不再逐个暂停；失败或触发升级条件即停
- **Cancel** —— 中止计划

门上纪律：

- **落盘 ≠ 批准**：文件出现在磁盘上只说明审批对象就绪；开工的唯一信号是用户明确回复 Go 或 Go All
- 计划定稿 → 落盘 → 对话给**一屏摘要**（计划文件路径、目标一句话、Stage 划分、关键决策点）+ 确认话术 + `[OPTION: Go | Go All | Cancel]` 作为最后一行 → **立即结束回合**：没有工具调用、没有调研、没有执行工作
- 确认话术（footer 之前）："计划已写入 `<路径>`，这份计划可以吗，还是需要调整？"
- 用户改计划 → 更新计划文件、重新给摘要、重新过门；一旦批准 → **不再重新计划**，遇到意外阻塞问针对性问题
- 规划期只读纪律延续到此刻：获批前不动任何业务代码

## 执行

职责分工：**你拥有分解、排序与综合；繁重的读/写/命令交给子代理**。有子代理工具就并行派发；没有就按同样规则顺序自己做——分工逻辑不变，只是并发度不同。

- Stage 内的独立任务**一批**派发；有依赖的排到后续批次或留在父级。绝不派发需要"仍在运行中的结果"的任务
- 简单的读取/检查/小型调研自己做——快且省；单个不可分单元留在父级，除非需要专家模型或上下文隔离
- 派发后汇报"已派发什么"并**结束回合**；等**全部**结果回来再综合或派下一批。读的是实际产出，不是调度确认或进度摘要
- **Stage 可以多轮**：派一批、收结果、目标没达成就再派一批——每 Stage **最多 3 轮**；3 轮仍未达成 → 保存已有成果（checkpoint）并问用户
- **Stage 之间做 checkpoint**：完成后用一两行总结再继续（如 `✅ Stage 1 complete: Found 12 endpoints, 3 deprecated. Proceeding to Stage 2...`），**并同步更新计划文件**：勾选该 Stage 的全部 Task、追加一行 checkpoint 结论——先更新文件再进入下一 Stage
- 实现中发现计划有误或需求变化：**先改计划文件再改代码**，顺序不能反；新发现的任务补进对应 Stage 的 checkbox 列表
- **Stage 失败：停下问用户**——不盲目重试，不自动进入下一 Stage
- **Go All（自动模式）**下：checkpoint 后直接进入下一 Stage，不输出 `[OPTION]`；失败仍然停
- 全部完成：向用户整体汇报（完成内容、验收情况、遗留项），更新计划文件页脚的"最后更新"日期与版本号
- 长对话中把每 Stage 的目标、尝试与产出写入环境的会话记录/账本机制——账本在上下文压缩后仍然可靠，胜过对先前轮次的回忆

## 何时求助（执行期裁决）

**已批准的执行期内：自己决定，继续干。** 可逆的判断/设计/范围选择——选最稳妥、最完整、保持工作正确的答案；倾向简单可逆的设计；带上必要的测试；用一行说明你选了什么；Go All 中也照常继续。**不要发明新的业务需求**。

只有四种情况打断用户：

1. **同一子任务 3 次尝试失败**：总结三次尝试，求指引。绝不静默地用同一思路重试超过 3 次
2. 缺凭证、权限或你拿不到的访问
3. 计划未覆盖的破坏性/不可逆动作（数据丢失、生产变更、force-push）
4. 子代理结果直接冲突且没有安全默认值

失败的 Stage 停止执行：告诉用户什么失败了、问一个**针对性**问题——绝不盲目继续，也不重新呈现整个计划。可枚举的选择用 `[OPTIONS: …]` 选项行提问；其余情况自己决定，不打断。

## 从回答中学习

用户在澄清、门上或求助时做出的每一次裁决，**立即记录**（项目笔记 / AGENTS.md / 环境的记忆机制，按可用性选）：写清"以后要做什么 + 避免什么"；只对单一代码库生效的纠正，注明作用范围。同一个问题不该问第二遍。

## 常见坑

- **一轮抛一堆问题**：十个问题一次问完，用户只会挑三个答；分组投喂、每轮三个、拿到答案再继续
- **跳过复述直接问**：理解错了前提，后面所有问题都在错误方向上精化
- **规划期手痒**：澄清中"顺手先建个文件"——只读纪律破防，门形同虚设
- **落盘即开工**：文件写完就当批准了——批准永远来自对话里的 Go / Go All，落盘只是产出审批对象
- **执行不同步文件**：Stage 完成不勾选、结构变更不更新——计划文件沦为废纸，跨会话接手就失真
- **任务没有 Demo**：写着"完成认证模块"却说不出演示什么——验收标准缺失，执行时必然注水
- **Grep 式伪验证**：验证行写"grep xxx 确认存在"——字符串找得到不等于功能正确；验证 = 真实测试/构建命令 + 预期结果
- **孤儿代码**：拆了一堆任务，最后没人负责"接线"；最后一个非验证任务必须是集成收尾
- **footer 后面还有内容**：`[OPTION: Go | Go All | Cancel]` 必须是消息最后一行，任何后缀都破坏门控语义
- **计划门后继续调工具**：发出摘要又"顺手查一下"——门形同虚设
- **把单一任务拆成仪式**：三次编辑能完成的事拆四个 Stage；判断标准是内在复杂度不是步骤数
- **3 轮失败后静默重试第 4 轮**：违反求助规则，浪费的是用户的等待
- **Go All 期间频繁打断**：可逆决策自己拍板继续，四种情况之外别问
- **读调度确认当结果**：子代理"已启动/进行中"不是完成；收齐实际产出再综合
- **重新计划代替针对性提问**：批准后遇到阻塞，问具体问题，别把整个计划推倒重来

## 与相关 skill 的分工

- **本 skill**：澄清节奏 + Task/Demo 格式 + Go/Go All/Cancel 门 + Stage 循环执行的对话式计划流（计划落盘 `plans/` 单文件）
- **sh-claude-plan-mode**：深度只读调研先行 + `plans/{NN}-{name}.md` 落盘审批 + 逐 Phase 勾选执行的文档型规划流——**与本 skill 共用同一 `plans/` 目录与编号序列**，差异在工作流形态而非产物位置
- **sh-spec-driven-development**：`specs/{NN}-{name}/` 目录下 requirements/design/tasks 三文档正式评审，编号与 `plans/` 相互独立
- 裁决：对话式拆阶段推进、说 "plan this"、要 Go 门 → 本 skill；要深度调研先行的文档化规划 → sh-claude-plan-mode；说出 "spec"、"三份文档" → sh-spec-driven-development
