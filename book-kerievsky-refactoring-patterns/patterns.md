# Patterns & Techniques —《重构与模式》（Refactoring to Patterns）

每条重构手法均遵循：**何时用（When to use） / 怎么做（How） / 代价与权衡（Trade-offs）**。按全书主题维度分组，保留中英对照与原书编号。

## 一、创建模式（Creation，Ch 6）

### 用 Creation Method 替换构造函数（Replace Constructor with Creation Method, 6.1）
- **何时用**：类中有多个构造函数，调用方难以通过同名构造函数区分意图；或需要添加参数签名相同但用途不同的新构造逻辑；存在"死构造函数"。
- **怎么做**：
  1. 找出全包含构造函数（Catch-all Constructor，必要时先应用"链构造函数 11.1"）；
  2. 提取出表达意图的公共静态方法（Creation Method），搬移至目标类；
  3. 将所有外部调用替换为该 Creation Method；
  4. 将类外无引用的构造函数收紧为 `private` 或 `protected`。
- **权衡**：意图表达力极大增强，突破构造函数同名及签名重载限制；缺点是非标准实例化方式（与裸 `new` 并存时风格需统一）。

### 将创建知识搬移到 Factory（Move Creation Knowledge to Factory, 6.2）
- **何时用**：创建类的知识和配置参数散落于多个协作类中，出现“创建蔓延”（Creation Sprawl）；或者需要集中管理创建逻辑与运行时配置选项。
- **怎么做**：
  1. 确保产品类已有 Creation Method；
  2. 创建专用 Factory 类（如 `NodeFactory`）；
  3. 将 Creation Method 搬移到 Factory 中（必要时转为非静态实例方法）；
  4. 客户代码转为持有并配置 Factory 实例，通过 Factory 生产产品；
  5. 汇拢其他类中参与创建的散落配置与解析数据。
- **权衡**：创建职责高度内聚，解除调用方与产品类的紧密绑定；若可以直接 `new`，引入 Factory 会增加类数量和间接层。

### 用 Factory 封装类（Encapsulate Classes with Factory, 6.3）
- **何时用**：同一包结构中存在多个实现同一公共接口的具体类，客户代码不需要（也不应该）了解这些具体子类的存在。
- **怎么做**：
  1. 在具体子类的顶层超类/接口上提炼公共静态 Creation Method；
  2. 将具体子类的构造函数声明为包级私有（default）或私有；
  3. 客户代码面向通用接口编程，完全通过 Factory 获取子类实例（范例：`java.util.Collections.unmodifiableList`）。
- **权衡**：践行“面向接口编程”，极大精简外部可见 API 表面积；缺点是新增具体子类必须修改 Factory，当变动极其频繁时可能形成修改瓶颈。

### 用 Factory Method 引入多态创建（Introduce Polymorphic Creation with Factory Method, 6.4）
- **何时用**：继承层次中的兄弟子类（或超类与子类）具有几乎相同的流程逻辑，仅在对象实例化步骤有所差异（如测试用例套件只有 `new DOMBuilder` 与 `new XMLBuilder` 的区别）。
- **怎么做**：
  1. 在子类相似方法中将对象创建提炼为统一签名的实例化方法；
  2. 将包含流程的通用方法上移至公共超类，并结合“形成 Template Method 8.1”；
  3. 超类中将该实例化方法声明为抽象（或提供默认实现），各子类覆写它以提供具体对象。
- **权衡**：消除继承层次内的方法级重复；缺点是约束所有子类必须返回相同接口类型，且偶尔可能被迫传递子类并不需要的统一参数。

### 用 Builder 封装 Composite（Encapsulate Composite with Builder, 6.5）
- **何时用**：构建复合树（Composite）的过程冗长、易错（创建节点、挂载父子、指针回溯），或客户代码与特定的树实现强耦合（如直接绑定 W3C DOM API）。
- **怎么做**：
  1. 创建生成器（Builder），对外提供语义化的扁平添加接口（如 `addChild`、`addSibling`、`addToParent`）；
  2. Builder 内部维护当前节点指针与父级栈结构，代劳复杂的挂载与回溯细节；
  3. 提供最终提取产物的方法（如 `toXml()` 或返回根节点）。
- **权衡**：将树结构的构建代码量压缩数倍，屏蔽底层节点树的实现细节；缺点是 Builder 内部状态机需要细致处理树游标与异常挂载。

### 内联 Singleton（Inline Singleton, 6.6）
- **何时用**：滥用 Singleton 导致全局状态泛滥、对象间产生隐式时间耦合、单元测试难以并行与隔离。
- **怎么做**：
  1. 识别真正需要该实例的客户类；
  2. 将 Singleton 的实例通过构造函数或方法参数显式传入客户类（依赖注入）；
  3. 当所有客户都通过参数获取实例后，将 Singleton 的静态访问器与私有构造函数消除，恢复为普通类。
- **权衡**：彻底根除全局隐式耦合，恢复对象的可测试性；代价是需要在协作对象链中显式传递引用。

## 二、简化模式（Simplification，Ch 7）

### 组合方法（Composed Method, 7.1）
- **何时用**：方法内部逻辑冗长、复杂，无法在一分钟内直观理解；或同一方法内混杂了高级业务步骤与底层细微操作（抽象层次不一致）。
- **怎么做**：
  1. 使用卫语句（Guard Clauses）替换嵌套的条件判断，快速失败并提前退出；
  2. 将魔法数字、常量和复合逻辑表达式分别提取为命名良好的函数；
  3. 不断提炼小函数，直到主方法仅由同一细节层面上、清晰表达“意图”的方法调用构成。
- **权衡**：代码自解释度极高；缺点是小方法激增，对于不习惯阅读跳转的开发者需要适应。

### 用 Strategy 替换条件逻辑（Replace Conditional Logic with Strategy, 7.2）
- **何时用**：计算或算法方法中充斥着庞大的 `switch/case` 或 `if-else` 分支，用于切换不同的计算变体；或者算法变体存在正交组合导致子类数量爆炸。
- **怎么做**：
  1. 建立抽象 Strategy 接口/基类，声明计算方法；
  2. 为每一个条件分支提取具体的 ConcreteStrategy 类，搬移算法逻辑；
  3. 在上下文（Context）类中保留 Strategy 引用，将具体计算委托给 Strategy；
  4. 支持在上下文实例化或运行时注入不同的 Strategy。
- **权衡**：彻底解耦算法变体与上下文，运行时支持无缝热插拔算法；代价是类文件增多，上下文与 Strategy 之间需要明确数据传递边界。

### 将装饰功能搬移到 Decorator（Move Embellishment to Decorator, 7.3）
- **何时用**：主类的核心职责中侵入了大量的可选、装饰性或边缘功能（如压缩、加密、缓存、解码），导致核心逻辑被稀释。
- **怎么做**：
  1. 确立主类与装饰器的公共接口（Component）；
  2. 创建抽象 Decorator，持有一个 Component 引用并将所有调用默认委托给它；
  3. 将特定的装饰逻辑移入 ConcreteDecorator，在委托前后执行增量行为；
  4. 客户代码按需层层包裹（嵌套）对象。
- **权衡**：遵循单一职责原则，支持动态正交叠加特性；代价是被修饰类接口方法不能过多，否则 Decorator 转发成本高，且调试时调用栈嵌套较深。

### 用 State 替换状态改变条件语句（Replace State-Altering Conditionals with State, 7.4）
- **何时用**：对象根据内部状态字段在多个方法中执行复杂的状态转换条件分支，状态机逻辑散落且容易遗漏非法转移。
- **怎么做**：
  1. 提取抽象 State 基类，声明所有与状态相关的行为方法；
  2. 为每个状态创建 ConcreteState 子类，将该状态下的行为与转换逻辑搬入其中；
  3. 在 Context 中保留当前 State 对象，状态转换时将 Context 指向新的 ConcreteState。
- **权衡**：状态转换规则显式化、局部化，新增状态无需修改现有状态类；代价是状态类成倍增加，微小状态机使用会引入过多间接层。

### 用 Composite 替换隐含树（Replace Implicit Tree with Composite, 7.5）
- **何时用**：代码通过字符串拼接、数组嵌套或格式化语法隐式构造树状数据（如手写拼接 XML/JSON/HTML 字符串），极度脆弱且难以校验与操作。
- **怎么做**：
  1. 引入标准 Composite 节点类（包含标签名、属性、子节点列表等）；
  2. 提供 `add()`、`render()` 等树操作与渲染方法；
  3. 将手写拼接过程替换为对 Composite 对象的节点树构建。
- **权衡**：树结构类型安全，易于遍历、修改与多态渲染；代价是比纯字符串拼接占用稍多的内存。

### 用 Command 替换条件调度程序（Replace Conditional Dispatcher with Command, 7.6）
- **何时用**：系统根据请求指令码在中央调度器（Dispatcher）中编写庞大的条件分支分发请求，调度器随着指令增多而急速膨胀。
- **怎么做**：
  1. 声明统一的 Command 接口（包含 `execute()` 方法）；
  2. 为每个条件分支提取 ConcreteCommand，搬移具体执行逻辑；
  3. 调度器使用映射表（Map/Registry）以指令键查找并调用对应的 Command。
- **权衡**：调度逻辑从 $O(N)$ 条件分支退化为 $O(1)$ 查找，完全符合开闭原则，易于支持撤销/重做或异步队列；代价是新增指令类。

## 三、泛化模式（Generalization，Ch 8）

### 形成 Template Method（Form Template Method, 8.1）
- **何时用**：两个或多个子类中的方法执行相似的骨架算法步骤，但在细节步骤实现上存在微小差异。
- **怎么做**：
  1. 在各子类中对差异步骤应用提炼函数，确保提取出的方法拥有相同的签名；
  2. 将包含算法主流程的方法上移至公共超类（此即 Template Method）；
  3. 将差异步骤声明为超类的抽象方法（或默认钩子方法），由子类具体覆写。
- **权衡**：彻底消除继承结构中的高层流程重复（好莱坞原则：“别打电话给我们，我们打给你”）；代价是子类受到超类算法骨架的严格制约。

### 提取 Composite（Extract Composite, 8.2）
- **何时用**：系统中有多个类在表示容器或复合结构，它们的子节点管理（增加、删除、查找）代码高度重复。
- **怎么做**：
  1. 提炼出统一的 Component 接口与抽象 Composite 容器基类；
  2. 将通用的子节点管理逻辑与委托遍历机制统一上移到抽象 Composite 中；
  3. 让具体的树节点或容器继承该基类。
- **权衡**：统一家谱管理机制，避免各类各自为政实现半吊子的树管理。

### 用 Composite 替换一/多之分（Replace One/Many Distinctions with Composite, 8.3）
- **何时用**：客户代码由于区别对待“单个对象”与“对象集合（群组）”而充斥着分流条件分支（如同时存在 `processItem` 与 `processItems`）。
- **怎么做**：
  1. 让叶子对象与容器对象实现相同的公共接口；
  2. 容器对象的多态方法内部通过遍历子节点实现；
  3. 客户端无论面对单件还是组合件，一律通过统一接口调用。
- **权衡**：消除所有区分单一与群组的冗余分支；缺点是类型系统不再强行保证调用方传入的是单件还是多件。

### 用 Observer 替换硬编码的通知（Replace Hard-Coded Notifications with Observer, 8.4）
- **何时用**：主体对象在状态发生变化时，需要向多个协作对象发送通知，且这些通知逻辑被硬编码在主体核心逻辑中，阻碍主体的独立演进。
- **怎么做**：
  1. 提取 Observer 接口与主体（Subject）通知注册机制（`addObserver/notifyObservers`）；
  2. 将硬编码的调用点改为向所有注册的观察者广播事件；
  3. 接收通知方实现 Observer 接口，按需注册到主体中。
- **权衡**：主体与监听方达成广播级解耦；缺点是通知顺序不可控，且容易由于遗漏反注册造成内存泄漏。

### 通过 Adapter 统一接口（Unify Interfaces with Adapter, 8.5）
- **何时用**：客户代码需要多态地操作多个类，但这些类由于历史原因实现各异、接口互不兼容。
- **怎么做**：
  1. 确立统一的客户目标接口（Target）；
  2. 创建 Adapter 类包裹原有类，在 Adapter 内部将目标接口方法映射转化为被包装类的原生调用。
- **权衡**：无需修改原有类即可达成多态协作；代价是新增包装对象层。

### 提取 Adapter（Extract Adapter, 8.6）
- **何时用**：一个类由于直接适配了多个异构系统/第三方库，导致其内部充斥着与业务无关的翻译适配代码。
- **怎么做**：
  1. 将每个外部系统的适配转换代码分别提炼出独立的 Adapter 类；
  2. 业务主类仅面向适配接口，将具体转换交由外部注入的 Adapter。
- **权衡**：业务核心彻底绝缘第三方 API 污染。

### 用 Interpreter 替换隐式语言（Replace Implicit Language with Interpreter, 8.7）
- **何时用**：系统需要支持极其灵活多变的查询条件组合（如复合查询、规格校验），传统条件拼接或方法重载无法应对组合爆炸。
- **怎么做**：
  1. 建立表达式抽象语法树（AST），提取统一的 `Expression` 接口（通常含 `evaluate()` 或 `interpret()`）；
  2. 实现叶子表达式（Terminals，如字段比对）与复合组合表达式（Non-terminals，如 `AndExpression`、`OrExpression`、`NotExpression`）；
  3. 运行时组合表达式树并统一求值。
- **权衡**：极高的查询表达组合自由度；代价是需要维护一套轻量 AST 体系，语法极其复杂时建议直接采用正式解析器。

## 四、保护模式（Protection，Ch 9）

### 用类替换类型代码（Replace Type Code with Class, 9.1）
- **何时用**：系统使用裸数字（`int`）或裸字符串（`String`）表示类型代码，缺乏编译期类型安全，容易传入非法值或与其他类型代码混淆。
- **怎么做**：
  1. 创建专属的类型类（Type Class），将其构造函数设为私有；
  2. 在类内部定义各合法类型的公共静态不可变常量实例；
  3. 所有参数、字段与返回值由原始类型升级为该类型类。
- **权衡**：编译期强类型保障，非法值绝缘；在现代语言中多以枚举（Enum）或密封类（Sealed Class）达成。

### 用 Singleton 限制实例化（Limit Instantiation with Singleton, 9.2）
- **何时用**：一个类必须严格保证在整个系统中只有唯一实例（如硬件总线驱动、共享资源管理器），且直接实例化会导致状态损坏或资源枯竭。
- **怎么做**：
  1. 将类的构造函数设为私有；
  2. 提供静态变量保存唯一实例，并暴露全局唯一的获取函数（如 `getInstance()`）；
  3. 配合双重检查锁定或静态内部类保证线程安全性。
- **权衡**：严格受控的资源访问；警惕其退化为隐式全局状态，非必要建议优先通过依赖注入单例作用域实现。

### 引入 Null Object（Introduce Null Object, 9.3）
- **何时用**：客户代码中充斥着大量的 `if (foo == null)` 判空防守，且在对象为空时的行为是默认的无操作（No-op）或安全降级。
- **怎么做**：
  1. 确立该类型的接口；
  2. 创建实现该接口的 `NullObject` 具体子类，在所有方法中实现良性中性行为（不抛异常、返回零值或静默退出）；
  3. 在无值或查询失败时返回 `NullObject` 实例而非 `null`。
- **权衡**：彻底抹杀客户代码中的防御性判空，避免 NPE；缺点是可能掩盖系统真实的逻辑缺失错误。

## 五、聚集操作（Accumulation，Ch 10）

### 将聚集操作搬移到 Collecting Parameter（Move Accumulation to Collecting Parameter, 10.1）
- **何时用**：方法在复杂的递归结构、树状节点或多步骤循环中累积信息，导致方法签名被迫层层向下传递各种散乱的累积变量。
- **怎么做**：
  1. 引入专门的结果累积容器对象（如 `StringBuilder`、`List` 或专属结果类）；
  2. 将容器对象作为单一参数传入各递归或调用节点；
  3. 各方法只需向容器追加内容，由调用发起方最终从容器提取全量结果。
- **权衡**：简化递归方法签名，消除重复中间结果的拼装；容器对象状态可变，需注意线程安全性。

### 将聚集操作搬移到 Visitor（Move Accumulation to Visitor, 10.2）
- **何时用**：复合树结构（Composite）稳定不变，但经常需要对整棵树执行各种异构的聚集计算或报告生成（如打印树、统计节点容量、类型校验），若将这些逻辑都写在节点类中会导致节点类严重膨胀。
- **怎么做**：
  1. 声明 `Visitor` 接口，为每种具体节点类型提供 `visitConcreteNode(Node)` 方法；
  2. 节点类声明 `accept(Visitor)` 并通过双分派（Double Dispatch）调用 `visitor.visit(this)`；
  3. 将特定的遍历聚集算法完整封入具体的 `ConcreteVisitor` 类中。
- **权衡**：新增算法极其轻松，节点结构高度内聚纯净；缺点是树节点层次一旦需要新增节点类型，会导致所有现存 Visitor 全面被迫修改。

## 六、实用重构（Pragmatic Refactorings，Ch 11）

### 链构造函数（Chain Constructors, 11.1）
- **何时用**：类中多个重载构造函数之间存在大量重复的代码初始化逻辑，字段赋值散落各处。
- **怎么做**：
  1. 找出包含全部初始化逻辑的全包含构造函数（Catch-all Constructor）；
  2. 让所有其他轻量构造函数通过 `this(...)` 将调用串联委托给全包含构造函数，仅传递缺省参数值。
- **权衡**：消除构造重复，为应用“用 Creation Method 替换构造函数 6.1”提供基石。

### 统一接口（Unify Interfaces, 11.2）
- **何时用**：准备应用 Decorator、Composite 或 Adapter 前，目标协作类之间的接口签名、参数列表存在细微差异。
- **怎么做**：
  1. 分析差异，使用改变函数声明等小步重构，逐步对齐方法名与入参结构；
  2. 提炼公共接口或抽象基类让各目标类共同实现。
- **权衡**：为更高阶的设计模式演进扫清接缝障碍。

### 提取参数（Extract Parameter, 11.3）
- **何时用**：方法内部直接硬编码了某个依赖对象或具体配置，阻碍了该逻辑向 Strategy、Decorator 等可插拔模式演进。
- **怎么做**：
  1. 将硬编码实例化的对象提取为方法参数或构造函数参数；
  2. 由外部调用者在装配阶段传入具体实例。
- **权衡**：打破死板的硬编码依赖，为多态组合提供注入点。
