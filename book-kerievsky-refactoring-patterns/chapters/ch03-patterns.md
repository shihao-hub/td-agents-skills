# 第3章 模式

> 源：OCR 原文行 1396–1864（忠实压缩摘要，仅供知识库使用）

## 核心论点

### 3.1 何谓模式（What is a Pattern?）
- 模式运动源于建筑师 Christopher Alexander 的《A Timeless Way of Building》和《A Pattern Language》。
- 按 Alexander 定义：模式是"某一环境 + 该环境中反复出现的因素系统（forces）+ 使因素自我协调的空间配置（解决方案）"三者的关系；作为语言的元素，模式是指示如何反复应用该配置的规则。
- 简言之，模式既是事物（存在于世界中），又是产生该事物的过程与规则；既是过程，又是事物。
- 软件界的模式目录（如《设计模式》、Fowler 的 PEAA）并非孤立模式，通常讨论模式之间的替代关系；仿效 Alexander 模式语言的著作还有 XP、DDD 等。

### 3.2 模式痴迷（Pattern Fever / Overdesign）
- 模式痴迷指对模式过度痴迷以至于"无法不在代码中使用模式"，为体验或名声而强行塞入模式；新手到资深程序员都可能染上（书中以模式化的 HelloWorld 为讽刺例子）。
- 学习模式的过程中几乎不可能完全避免模式痴迷，多数人靠犯错学习，作者本人也不例外。
- 真正的模式之乐来自睿智地使用模式：重构使注意力集中在去除重复、简化代码、清晰表达意图上；当模式通过重构演进到系统中时，过度设计的机会很小。

### 3.3 实现模式的方式不止一种
- 每个模式描述反复出现的问题及其解决方案的要素，解决方案可反复应用但具体方式各异。
- 《设计模式》中每个模式只配一幅结构图，程序员常误把结构图当作唯一实现方式；Vlissides 强调：结构图只是例子，不是规范。
- 例如 Composite 的一个精简实现（TagNode）与结构图几乎毫无相似之处——只写必要部分、取最精简形式，是演进设计实践的一部分。
- 非基于模式的实现可以演进为基于模式的实现，并可继续重构以简化模式实现。

### 3.4 通过重构实现、趋向和去除模式
- 涉及模式的重构有三个方向：重构实现（refactoring to）、重构趋向（refactoring towards）、重构去除（refactoring away from）模式；目的始终是更好的设计，而非实现模式本身。
- 有些模式必须完全实现才有收益（Composed Method、Template Method——趋向不足以去除重复）；有些则趋向即有改进（Decorator、Command，可中途停止）。
- 实现/趋向后必须评估设计是否确实改善；若没有，应返回或改向——如内联 Singleton 去除 Singleton、用 Builder 封装 Composite 让客户改与 Builder 交互、将聚集操作搬移到 Visitor 替代 Iterator 代码。

### 3.5 模式是否会使代码更加复杂
- 案例表明：对模式不熟悉的程序员（John）会认为模式化重构后的代码"太复杂"，而熟悉者（作者、Bobby）认为更简单清晰——对模式的熟悉程度决定性地影响人们对模式化重构的评价。
- 一般而言，实现模式应有助于去除重复、简化逻辑、说明意图、提高灵活性。
- 应该让团队学习模式，而不是因觉得复杂而弃用；但确实有些模式实现会使代码过分复杂，此时应返回或进一步重构。

### 3.6 模式知识（Pattern Knowledge）
- 不懂模式就很难演进出优秀设计；模式凝聚前人智慧，重用这些智慧极为有益（类比：莫扎特组合既有音乐形式创作出伟大作品）。
- 仅有模式知识还不够，必须明智地使用——这正是全书主题；JUnit 的演进过程证明 Kent Beck 与 Erich Gamma 是在重构中实现和趋向模式，而非把模式硬塞进设计。
- 推荐获取方式：读好书 + 组建每周一次的模式学习小组（作者 1995 年创建的纽约城设计模式学习小组至今活跃；另见其 Pools of Insight 模式语言）。

### 3.7 使用模式的预先设计（Up-Front Design with Patterns）
- 1996 年案例：为赢取一个音乐电视公司网站合同，团队先做了大规模预先设计（BDUF），以 Command 模式为核心、配简单 Interpreter 让客户自行配置行为；预先设计对赢得合同和项目成功是决定性的。
- BDUF 的典型问题：需求会改变/删除/延迟，或花太多时间提出超出所需的复杂设计；但预先设计在某些商业情形（先出方案拿合同）不可替代。
- 1996 年后作者很少再用"使用模式的预先设计"，改为演进系统、按需重构实现/趋向/去除模式；Command 模式是少数例外（易实现且明显需要）。
- 结论：预先设计应在设计人员工具箱中占一席之地，但要极少且审慎地采用。

## 关键概念/术语表（中英对照）

| 中文 | 英文 | 说明 |
|---|---|---|
| 模式 | Pattern | 环境、反复出现的因素系统与使因素自我协调的空间配置三者间的关系 |
| 模式语言 | Pattern Language | 由模式组成的精巧知识网络（Alexander） |
| 因素/作用力 | forces | 内外作用力，其冲突构成问题 |
| 空间配置 | spatial configuration | 建筑学意义上的解决方案 |
| 模式痴迷 | Pattern Fever / Pattern Obsession | 对模式过于痴迷，无法不在代码中使用模式 |
| 大规模预先设计 | Big Design Up-Front (BDUF) | 编码前完成大规模设计文档的方式 |
| 重构实现模式 | Refactoring to (a pattern) | 通过重构完全实现模式 |
| 重构趋向模式 | Refactoring towards (a pattern) | 向模式方向重构，可中途停止 |
| 重构去除模式 | Refactoring away from (a pattern) | 从设计中移除某模式 |

## 实践要点清单
- 目的是更好的设计，不是实现模式；每次重构后评估设计是否真的改善，没有就返回或改向。
- 结构图只是例子不是规范；实现参与者命名应贴合领域，权衡要素变化时实现可以与结构图差异很大。
- 取模式的最精简实现，只编写必要部分。
- 区分"必须实现才有收益"（Template Method、Composed Method）与"趋向即有改进"（Decorator、Command）的重构。
- 别因"看起来复杂"拒绝模式化设计——先学习模式再评价；但也警惕某些实现确实过度复杂，此时重构返回。
- 组建模式学习小组，每周学习一个模式；只读好书（Weinberg）。
- 预先设计（尤其 Command 模式）仅在赢合同/设计易实现且明显需要时极少且审慎使用，其余情况靠演进。
