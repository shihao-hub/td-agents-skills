# 第4章 代码坏味

> 源：OCR 原文行 1865–2083（忠实压缩摘要，仅供知识库使用）

## 核心论点

### 重构的前提：识别坏味
- 重构（改善既有代码设计）要求先知道什么代码需要改善；大原则是三类问题：**重复、不清晰、复杂**。
- Fowler 与 Beck《重构》第 3 章给出 22 种代码坏味（如依恋情结 Feature Envy、基本类型偏执 Primitive Obsession、夸夸其谈未来性 Speculative Generality），提供了快速探讨设计问题的词汇。
- Kerievsky 检视这 22 种坏味中哪些可用本书重构解决，并新发现 5 种坏味（条件逻辑太复杂、不恰当的暴露、解决方案蔓延、组合爆炸、怪异解决方案），全书重构共处理 **12 种坏味**（表 4-1 给出坏味→重构映射；[F] 标记源自《重构》）。

### 坏味的共同治理思路
- 最好通过相关的（模式导向）重构去除坏味，本章各节为"何时使用哪个重构"提供指导。
- 许多坏味相互关联：如怪异解决方案往往意味着不易察觉的重复代码；解决方案蔓延与霰弹式修改本质是同一问题，只是发现方式不同（前者靠观察，后者靠实践）。

## 第4章 12 种代码坏味完整清单（中英对照 + 定义 + 指向的重构）

1. **重复代码 Duplicated Code**[F]（4.1）
   - 定义：软件中最常见的坏味，既有完全相同的明显重复，也有表面不同但本质相同的结构或处理步骤的微妙重复。
   - 重构方向：形成 Template Method（子类层次中的重复）；用 Factory Method 引入多态创建；链构造函数（构造函数重复）；用 Composite 替换一/多之分、提取 Composite；通过 Adapter 统一接口（接口不同导致的重复处理逻辑）；引入 Null Object（重复的空对象条件逻辑）。

2. **过长函数 Long Method**[F]（4.2）
   - 定义：过长的函数妨碍逻辑共享、降低可理解性；作者主张函数应在 10 行以内，多数只有 1–5 行。
   - 重构方向：组合方法（Composed Method，通常配合提炼函数）；将聚集操作搬移到 Collecting Parameter；用 Command 替换条件调度程序（大 switch 分派）；将聚集操作搬移到 Visitor；用 Strategy 替换条件逻辑（运行时选择算法版本）。

3. **条件逻辑太复杂 Conditional Complexity**（4.3，新）
   - 定义：条件逻辑最初简单无辜，但随新功能加入变得复杂且开销高昂。
   - 重构方向：用 Strategy 替换条件逻辑（选择计算的某个变形）；将装饰功能搬移到 Decorator（核心行为之外的特殊行为）；用 State 替换状态改变条件语句（复杂状态转换）；引入 Null Object（空对象处理逻辑）。

4. **基本类型偏执 Primitive Obsession**[F]（4.4）
   - 定义：代码过于依赖整数、字符串、数组等基本类型，缺乏更高层抽象；类往往能更简单自然地建模事物。
   - 重构方向：用类替换类型代码（类型安全 + 可扩展）；用 State 替换状态改变条件语句；用 Strategy 替换条件逻辑；用 Composite 替换隐含树（字符串隐式树结构）；用 Interpreter 替换隐式语言（基本类型组合的隐式语言）；将装饰功能搬移到 Decorator；用 Builder 封装 Composite（Composite 过于原始难用）。

5. **不恰当的暴露 Indecent Exposure**（4.5，新）
   - 定义：本不该被客户代码看到的方法或类却公开可见，违反 Parnas 的"信息隐藏"，让客户了解不重要或仅间接重要的代码，增加复杂度。
   - 重构方向：用 Factory 封装类——将构造函数设为非公开，由 Factory 生成实例。

6. **解决方案蔓延 Solution Sprawl**（4.6，新）
   - 定义：完成某职责的代码和/或数据散落在许多类中，通常是快速添加特性而未花时间改进设计所致；是霰弹式修改的孪生兄弟。
   - 重构方向：将创建知识搬移到 Factory（解决对象创建职责蔓延）。

7. **异曲同工的类 Alternative Classes with Different Interfaces**[F]（4.7）
   - 定义：两个相似的类却有不同接口；相似类通常应共享公共接口，但第三方库等情况下无法直接修改接口。
   - 重构方向：通过 Adapter 统一接口，为两个类生成公共接口。

8. **冗赘类 Lazy Class**[F]（4.8）
   - 定义："类如果功能有限，缺乏存在价值，就应该删除"；常见如缺乏存在价值的 Singleton，它使设计过分依赖全局数据，代价过高。
   - 重构方向：内联 Singleton。

9. **过大的类 Large Class**[F]（4.9）
   - 定义：实例变量过多往往说明职责太多；大类承载过多职责。
   - 重构方向：先以提炼类/提炼子类减肥，再用模式导向重构：用 Command 替换条件调度程序；用 State 替换状态改变条件语句；用 Interpreter 替换隐式语言。

10. **分支语句 Switch Statement**[F]（4.10）
    - 定义：switch（或等价的 if...else if... 链）本身无错，但当它使设计过度复杂或僵硬时成为坏味，应重构为更基于对象/多态的方案。
    - 重构方向：用 Command 替换条件调度程序（分解为一组无需条件逻辑即可查找调用的 Command）；将聚集操作搬移到 Visitor（分支语句保存不同接口实例的数据）。

11. **组合爆炸 Combinatorial Explosion**（4.11，新）
    - 定义：类的许多方法用不同的条件和数据"做同样的事情"，特殊情形越多方法越多，方法数组合爆炸（如按特定条件编写的一堆查询方法，背后是隐式查询语言）。
    - 重构方向：用 Interpreter 替换隐式语言，删除所有这些方法。

12. **怪异解决方案 Oddball Solution**（4.12，新）
    - 定义：同一系统中用不同方式解决同一问题，即不一致的解决方案，往往暗示不易察觉的重复代码。
    - 重构方向：先确定优先方案（使用率最低但确实更优者也可优先），通常先用替换算法[F]统一方案；若问题是各类接口不同导致无法一致通信，则通过 Adapter 统一接口，再删除重复处理逻辑。

## 实践要点清单
- 用"重复、不清晰、复杂"三原则定位需要改善的代码，再用 12 种坏味精确定位。
- 坏味 → 重构不是一对一：同一坏味按具体情形选择不同模式重构（如表 4-1）；优先用"相关的重构"去除坏味。
- 函数目标 ≤10 行、多数 1–5 行；不要因惧怕小函数调用开销而放弃小方法（不做不成熟优化，可用 profiler 验证，真有问题再重构性能）。
- 条件逻辑"几行且易懂"无辜；一旦控制多种变形/特殊行为/状态转换/空处理，就转向 Strategy/Decorator/State/Null Object。
- 遇到 switch 问问自己是否该上 Command、State、Strategy 或 Visitor。
- 怪异解决方案先"选型统一"（Substitute Algorithm），再考虑 Adapter 统一接口后收敛重复。
