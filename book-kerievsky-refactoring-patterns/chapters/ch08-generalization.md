# 第8章 泛化（Generalization）

> 源：《重构与模式》（Joshua Kerievsky, *Refactoring to Patterns*）中文版第8章，OCR 原文行 7131–9922。
> 泛化 = 把特殊代码转换成通用目的代码的过程。本章全部 7 个重构都会产生泛化代码。最常见动机：**去除重复代码**；其次是**简化或澄清代码**。

---

## 8.1 形成 Template Method（Form Template Method）

**问题**：子类中的两个方法以相同的顺序执行相似的步骤，但步骤不完全相同。
**解法**：把这些步骤提取成具有相同签名的方法来泛化这两个方法，然后上移这些泛化方法，形成 Template Method[DP]。

### 动机
- Template Method"一次性实现算法的不变部分，将可变行为留给子类实现"。当不变与可变行为混合在子类方法中时，不变行为会在子类中重复。
- 不变行为包括：① 被调用的方法及调用顺序；② 子类必须重写的抽象方法；③ 子类可能重写的钩子方法（hook，如具体方法）。
- 应使子类必须实现的抽象方法数量最小；Template Method 常调用 Factory Method；必要时可声明为 final（仅当客户代码完全依赖不变行为时）。
- 与 Fowler 的 Form Template Method [F] 本质相同；常与 Strategy 组合使用，得到几乎无重复的 Strategy 类。
- 优点：去除子类重复、清晰表达通用算法步骤、便于子类定制；缺点：子类需实现很多方法时增加设计复杂度。

### 做法
1. 在类层次中找到**相似方法**（similarmethod），用组合方法（7.1节）提取出**同一方法**（identicalmethod，签名+方法体都相同）和**唯一方法**（uniquemethod，签名+方法体不同）。判断标准：提取为唯一方法后，子类继承/重写它是否有意义？无意义则提取为同一方法。（领域知识常影响此决定。）
2. 函数上移[F]：把同一方法上移到超类。
3. 函数改名[F]：为唯一方法统一各子类中的签名，直到相似方法在每个子类完全相同（每次改名后编译+测试）。
4. 函数改名[F]：确保相似方法在各子类有相同签名。
5. 函数上移[F]：把相似方法上移到超类，并在超类为每个唯一方法声明抽象方法——此相似方法即成为 Template Method。编译+测试。
   - 变体：为特殊步骤建钩子方法（默认返回 1.0 之类的无操作值），由个别子类重写；缺点是不能很好表达公式、多数子类继承无意义行为。

### 适用信号 / 坏味道
- 同一层次多个子类中有按相同顺序执行相似步骤的方法；不变行为在子类间重复。

## 8.2 提取 Composite（Extract Composite）

**问题**：一个类层次结构中的多个子类实现了同一个 Composite。
**解法**：提取一个实现该 Composite 的超类（CompositeTag 之类，按其存储的类的类型命名）。
本质是提炼超类[F]的具体应用，专指把共有的 **Composite** 处理逻辑上移。

### 动机
- 子类常存储其他类的集合并含报告这些类信息的方法；当被存储的类恰在同一层次中时，可用 Composite 去除大量重复代码，简化子类，方便编写新子类。
- 若还有与 Composite 无关的可上移行为，则用提炼超类[F]而非本重构。
- 优点：去除重复的类存储逻辑与类处理逻辑；有效表达类处理逻辑的可继承性。

### 做法
1. 创建组合类（未来成为 Composite[DP] 的类），命名反映其存储的类型。编译。
2. 把每个**含有子结点的类**（childcontainer，含重复子结点处理代码的类）声明为组合类的子类。编译。
3. 找出所有子类中**完全重复**（方法体相同）或**部分重复**（方法体含共有+独有代码）的类处理方法；签名不一致时先函数改名[F]统一。
   - 完全重复：上移字段[F]把集合字段上移（必要时重命名，如 `children`），再函数上移[F]把方法上移；依赖构造函数初始化的代码一并上移。
   - 部分重复：先考虑替换算法[F]统一方法体（可则按完全重复处理）；否则提炼函数[F]提取共有代码并上移；若方法体步骤相同仅个别步骤不同，考虑形成 Template Method（8.1节）。
   - 若子类通过各自的取值方法访问子结点，编写统一的访问方法（如 `children()`）上移，再上移处理方法。每个重构后编译+测试。
4. 对其余可上移方法重复步骤3；若其他类通过含有子结点的类特有接口与之交互，改为使用组合类接口。编译+测试。

### 适用信号 / 坏味道
- 多个子类各自持有子结点集合字段，且各自实现几乎一样的遍历/输出方法（如 HTMLParser 中 LinkTag 与 FormTag 各有一份 `toPlainTextString()`）。

## 8.3 用 Composite 替换一/多之分（Replace One/Many Distinctions with Composite）

**问题**：类使用不同的代码处理单一对象与多个对象。
**解法**：用 Composite 使代码既可以处理单一对象又可以处理多个对象。

### 动机
- **一/多之分**：一个类有两个几乎一样的方法，唯一区别是处理单一对象 vs 对象集合。问题：① 重复代码；② 客户代码被迫按不同签名传不同类型，变得不一致、复杂；③ 结果需多次调用再手工合并（如无法表达 OR 条件，只能分别查询再 addAll）。
- 重构后：一个方法处理任意数量对象；客户代码统一调用；一次调用处理一棵对象树（如 OrSpec(AndSpec(ColorSpec,BelowPriceSpec), AndSpec(ColorSpec,AbovePriceSpec))）。
- 例外：若重复很少，实现 Composite 可能不值得；Composite 可能需要运行时类型检查（与集合相同）。
- 优点：去除重复、统一调用方式、支持更丰富的组合（OR/AND/NOT）；缺点：可能需运行时类型安全检查。

### 做法
（单一对象的方法称**单一对象方法**；接收集合的方法称**多对象方法**。）
1. 创建组合类：构造函数接收集合并提供访问方法。在多对象方法中实例化它，把对集合的引用改为经组合类的访问方法。编译+测试。
2. 对多对象方法中集合相关代码提炼函数[F]，声明为公共方法，再搬移函数[F]搬入组合类。编译+测试。
3. 此时两个方法几乎一样；用其他重构去除残余差异。编译+测试。
4. 改多对象方法为一行：调用单一对象方法并传组合类实例。需使组合类与单一对象方法参数类型共享接口/超类（把组合类声明为该类型子类，或提炼接口[F]）。编译+测试。
5. 多对象方法已只一行，将方法内联化[F]。编译+测试。
6. 对组合类应用封装集合[F]：加 `add(...)` 方法、构造函数改默认构造、访问方法返回不可变集合；更新所有调用者后删除接收集合的构造函数。编译+测试。

### 适用信号 / 坏味道
- 同一个类中存在 `selectBy(Spec)` 与 `selectBy(List specs)` 这类仅一/多之别的成对方法，内含重复遍历逻辑；客户需多次调用再合并结果。

## 8.4 用 Observer 替换硬编码的通知（Replace Hard-Coded Notifications with Observer）

**问题**：子类通过硬编码来通知另一个类的一个实例。
**解法**：去除这些子类，使其超类能够通知一个或多个实现了 Observer 接口的类。（例：JUnit 2.x 中 TestResult 子类硬编码通知各自 TestRunner，后重构为 TestResult 作为主题、TestRunner 实现 TestListener。）

### 动机
- 先理解何时**不需要** Observer：若通知者只需永远通知唯一接收者，紧耦合反而更简单（JUnit 早期如此）。
- 当需求变为可通知多个接收者或其他类的实例时，须改进设计。Observer 接口实现主题与观察者松耦合：观察者实现接口并注册到主题，主题遍历通知。
- 主题必须有 addObserver；若无删除观察者的需求，不必实现 removeObserver——不要死板照搬模式结构。
- 两个常见问题：**串联通知**（观察者又是主题，链式传播，调试困难，可用 Mediator[DP] 改进）；**内存泄漏**（观察者因被主题引用无法回收——记得从主题删除观察者）。
- 不要在需要之前受诱惑使用 Observer；需要时随时可从硬编码通知重构过去。
- 优点：松耦合、支持一或多个观察者；缺点：硬编码已够时反而增加复杂度；串联通知增加复杂度；观察者未删除会内存泄漏。

### 做法
（**通知者** notifier = 引用并给其他类发通知的类；**接收者** receiver = 注册并接收信息的类。目标：通知者的超类成为主题 ConcreteSubject，接收者成为观察者 ConcreteObserver。）
1. 若通知者代表接收者执行定制行为（如直接 println），搬移函数[F]把这些行为搬入接收者，使通知者只含通知方法。对每个通知者重复。编译+测试。
2. 在接收者上提炼接口[F]，只选被通知者调用的方法，产生**观察者接口**；其他通知者若还调别的方法，加入接口。编译。
3. 每个接收者实现观察者接口；每个通知者只通过该接口与接收者交互。编译+测试。
4. 选一个通知者，对其通知方法应用函数上移[F]（连同观察者引用及设置代码）——通知者的超类即成为主题。对所有通知者重复。编译。
5. 更新每个通知者的观察者，注册到主题并与主题交互，然后删除通知者。可能需对未初始化引用加 null 保护。编译+测试。
6. 重构主题：持有观察者集合而非单个引用；提供 addObserver；通知方法遍历通知所有观察者；观察者改用 addObserver 注册；删除旧构造函数。编译+测试。
   - 注：第6步（支持多个观察者）属于功能增强，是引入 Observer 的结果；行为不变的转换部分才是重构。

### 适用信号 / 坏味道
- 子类持有某个具体类的引用并在事件发生时硬编码通知它；当需要多个观察者或允许其他类观察时设计失灵。

## 8.5 通过 Adapter 统一接口（Unify Interfaces with Adapter）

**问题**：客户代码与两个类交互，其中一个类具有首选的接口。
**解法**：用一个 Adapter 统一接口（为"被适配者"做一个实现公共接口的适配器）。

### 动机
当以下条件都为真时有用：① 两个类所做事情相同/相似但接口不同（"异曲同工的类"坏味）；② 共享同一接口可让客户代码更简单直接紧凑；③ 无法轻易改变其中一个类的接口（第三方类库、被广泛依赖的框架、无源码，如 DOM 的 Element）。
简单情况可先尝试改名/搬移函数使接口相同；不可行时才做 Adapter。统一接口后可继续用形成 Template Method（8.1）、用 Factory Method 引入多态创建（6.4）去除客户代码中重复的处理逻辑。
优点：客户经统一接口与不同类交互，去除/减少重复、简化客户代码；缺点：当接口本可修改时会增加设计复杂度。

### 做法
1. 在具有首选接口的类上提炼接口[F]，生成**公共接口**；把该类中以自身类型为参数的方法参数改为公共接口。编译+测试。
2. 在使用被适配者的客户类上提炼类[F]，产生**原生适配器**（含被适配者字段 + 获取方法 + 设置方法或构造函数）。
3. 客户类中所有被适配者类型的字段/局部变量/参数改为适配器类型（调用处先经适配器取被适配者引用）。编译+测试。
4. 对客户代码中调用相同被适配者方法之处提炼函数[F]，产生**被适配者调用方法**（以被适配者作参数）。为每类调用重复。编译+测试。
5. 搬移函数[F]把被适配者调用方法搬入适配器，使其与公共接口对应方法尽量一致：若方法体需要客户代码中的值，避免作为参数（会破坏签名一致），改经适配器构造函数传入或传其他对象引用在运行时获取；实在不行则修订公共接口签名。编译+测试。
6. 适配器正式 implements 公共接口；适配器方法中适配器类型参数改为公共接口类型。编译+测试。
7. 客户代码中所有适配器类型的字段/局部变量/参数改为公共接口类型。编译+测试。（例：ElementAdapter 实现 XMLNode，使 XMLBuilder 与 DOMBuilder 代码可上移到 AbstractBuilder。）

### 适用信号 / 坏味道
- 客户代码与两个功能相似但接口不同的类交互，产生成对的相似处理逻辑；其中一方接口不可修改。

## 8.6 提取 Adapter（Extract Adapter）

**问题**：一个类适配了多个版本的组件、类库、API 或其他实体。
**解法**：为该组件/类库/API 的每个版本提取一个 Adapter。

### 动机
- 常见坏代码：类里塞满版本相关状态变量、重复方法、条件逻辑，以及"升级到版本 Y 时请删除这些代码！"的注释——而注释中的代码永远不会被删（怕有未知依赖）。
- 替代方案：为每个版本建一个单独的类（类名可含版本号），实现公共接口、只负责一个版本的适配，即 Adapter[DP]。客户程序可依运行时信息选择正确的 Adapter，便于从一个版本迁移到另一个。
- 作者喜欢 Adapter：隔离频繁变化的第三方/开源 API，掌握与外部代码交互的主动权。
- 注意"过度适配"：客户经由 Adapter 无法访问被适配者的某些所需行为时，需重新设计 Adapter。
- 版本相关逻辑散布各处是**解决方案蔓延**坏味的征兆；出现复杂性、传播的制约性或维护问题时才做此重构（勿过早）。
- **Adapter vs Facade**：Adapter 适配对象，Facade 适配整个子系统（常用于包裹遗留系统：识别子系统→写 Facade→新客户调用 Facade→用新技术重写各 Facade→测试一致性→切换客户→逐子系统推进）。
- 优点：隔离版本差异、每个类只适配一个版本、避免频繁修改；缺点：某重要行为若不在 Adapter 中，客户将无法执行。

### 做法
（若原代码是大量条件逻辑，可反复用多态替换条件式[F]为每版本建 Adapter；以下针对"已有一个支持多版本的负担过重的适配器类"的情况。）
1. 识别**负担过重的适配器**（overburdened adapter，适配了太多版本的类）。
2. 对其中一个版本，应用提炼子类[F]或提炼类[F]产生新适配器；复制或搬移该版本专用的实例变量与方法。可能需把某些私有成员放宽为 public/protected；可能经新构造函数初始化字段并更新调用者。编译+测试。
3. 重复步骤2，直到原类不含任何版本相关代码（原类可声明为抽象、方法抽象化）。
4. 用函数上移[F]、形成 Template Method（8.1）等去除新适配器间的重复（如 doQuery() 模板 + createQuery() Factory Method；统一 login() 签名，把差异参数改为经构造函数传入；必要时提炼接口[F]保留原类型名以少改客户代码）。编译+测试。
   - 变体——用匿名内部类适配：如 `Collections.enumeration(final Collection c)` 用匿名内部类把 Iterator 适配为 Enumeration。

### 适用信号 / 坏味道
- 单个类用版本布尔标志（如 `sd52`）、重复的同名方法和条件代码同时支持库/组件的多个版本；"以后删除"注释；解决方案蔓延。

## 8.7 用 Interpreter 替换隐式语言（Replace Implicit Language with Interpreter）

**问题**：类中的许多方法组合成了一种隐式语言的元素。
**解法**：为隐式语言的元素定义类，使可通过类实例组合形成易理解的表达式。

### 动机
- Interpreter[DP] 解释**简单**语言——语法可用少量类建模，通常用 Composite 结构组合语法类实例形成表达式。实现它只比 Composite 略复杂，关键是判断何时该用。
- **太复杂或太简单的语言都不该用**：复杂语言用解析器生成器（如 JavaCC）；极简语言不需要类。语法约需 10 个类时 Interpreter 有帮助——典型的对象/数据库搜索表达式（非终结表达式 and/not/or + 终结表达式 "$10.00"、"small"、"blue"）。
- **隐式语言**问题：如 ProductFinder 堆满 `byColor(...)`、`byColorAndBelowPrice(...)`、`byColorSizeAndBelowPrice(...)` 等查询方法，语言"存在但未说明"，导致重复代码和**组合爆炸**坏味。Interpreter 用较少的类支持任意组合、无重复。
- 常与 **Specification**[Evans] 和 **Query Object**[Fowler, PEAA] 模式配合；也支持行为的运行时动态配置（如由 UI 参数动态生成可解释的对象结构）。
- 优点：更好地支持语言元素组合、新组合不需新代码、运行时配置；缺点：定义语法与修改客户代码的开销；复杂语言工作量大；过简单的语言反而增加设计复杂度。

### 做法
（以 Specification/Query Object 场景为背景：大量对象选择方法遍历集合挑选对象。）
1. 找出依赖条件参数（如 `float price`）的对象选择方法，为该条件创建**具体规格类**（按功能命名，如 BelowPriceSpec），含字段与访问方法；在对象选择方法中实例化之，代码改为经访问方法取条件。多个条件则各建一个具体规格类。编译+测试。
2. 对条件语句提炼函数[F]产生返回 boolean 的 `isSatisfiedBy()`，搬移函数[F]移入具体规格类；再提炼超类[F]创建抽象**规格超类**（声明抽象 isSatisfiedBy）。编译+测试。
3. 对其余对象选择方法重复步骤1–2。
4. 对依赖多个查询条件的方法：创建**组合规格类**（如 AndSpec、NotSpec，构造函数传入具体规格，或数量多时提供 add(...)），把条件逻辑搬入其 isSatisfiedBy(...)；组合规格扩展规格超类。
5. 此时各对象选择方法除规格创建代码外完全相同：提炼函数[F]产生 `selectBy(Spec)`（返回对象集合），所有方法改为调用它。编译+测试。
6. 对每个对象选择方法应用使方法内联化[F]（客户代码改为自行组合 Spec 再调 selectBy）。编译+测试。

### 适用信号 / 坏味道
- Finder 类方法数量随查询条件组合**组合爆炸**增长；每个方法重复"遍历集合+条件挑选"的骨架；需要 AND/OR/NOT 等任意条件组合或运行时构造查询。
