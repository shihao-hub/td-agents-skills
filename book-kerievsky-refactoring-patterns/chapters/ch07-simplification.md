# 第7章 简化（Simplification）

> 来源：《重构与模式》（Joshua Kerievsky, *Refactoring to Patterns*）中文版第7章（原书 pp.121–163）。OCR 忠实压缩摘要；代码细节从略，保留动机、做法要点与适用信号。

绝大多数代码一开始并不简单。简化需要不断思考"复杂在哪里、怎样能更简单"，常常要通过考虑一种完全不同的解决方案来实现。本章重构展示简化方法、状态转换和树型结构的不同方案：

- 组合方法（7.1）：生成更优雅的方法，有效表达"实现什么"与"如何实现"。要尽量多应用。
- 用 Strategy 替换条件逻辑（7.2）：把因支持多种变化而复杂的算法分解成单独的类。算法不够复杂时反而会增加设计复杂度。
- 将装饰功能搬移到 Decorator（7.3）：适用于一个类中特殊状况或装饰逻辑过多的情况。
- 用 State 替换状态改变条件语句（7.4）：彻底简化复杂的状态转换逻辑。
- 用 Composite 替换隐含树（7.5）：简化树型结构的构造与使用。
- 用 Command 替换条件调度程序（7.6）：简化膨胀的条件调度逻辑。

---

## 组合方法（Composed Method）

**一句话**：你无法迅速理解一个方法的逻辑 → 把方法的逻辑转换成几个同一细节层面上的、能够说明意图的步骤。

### 动机
- Composed Method（Kent Beck, SBPP）是很小、很简单的方法，逻辑一眼可懂。实践中往往最初不会这样写，需要回头重构。
- Composed Method 由对其他方法的调用组成，其代码都处于细节的同一层面上；名字描述"实现什么功能"，方法体描述"如何实现"。这使代码易于使用、理解和扩展。
- 反例：一个方法里既混有高级别调用又混有底层细节（如 paintCard 里既画图又有条件判断细节），就不在同一层面。
- 缺点：可能产生过多小方法（可用提炼类 [F] 进一步拆分）；调试时逻辑散布在许多小方法中，不易定位实现；性能问题极少由它引起（需 profiler 确认）。

### 做法（指导原则 + 步骤要点）
原则：
1. 删除重复代码和死代码，减少方法代码量。
2. 表达意图：清楚命名变量、方法和参数。
3. 简化：尝试用其他写法重写，使代码尽可能简单。
4. 使用细节的同一层面：条件逻辑中若包含高级别方法调用，应把细节抽象到命名良好的方法中，与其他方法处于同一层面。

典型步骤（以 List.add 为例）：
- 用卫语句（guard clause）替代包裹全部代码的条件语句，实现提前出口；
- 将魔数提取为常量；
- 反复应用提炼函数 [F]，把越界检查、扩容、添加元素等分别提取成小方法（如 `atCapacity()`、`grow()`、`addElement()`），直到主方法只剩几个同层面的步骤调用；
- 提取过多导致无法起好名字时，用内联方法 [F] 放回并换一种分解方式。

### 适用信号 / 坏味道
- 方法逻辑无法迅速理解；一个方法内混有不同抽象层面的代码；代码重复、死代码、意图不清的命名。

## 用 Strategy 替换条件逻辑（Replace Conditional Logic with Strategy）

**一句话**：方法中的条件逻辑控制着应执行计算的哪个变体 → 为每个变体创建一个 Strategy，并让方法把计算委托到 Strategy 实例。

### 动机
- 复杂条件逻辑是最常导致复杂度上升的地方（Fowler）。算法逻辑逐渐增长时，Strategy [DP] 可管理由算法变体过多产生的复杂度。
- 分解条件式 [F]、组合方法虽可简化代码，但可能在类中堆积许多只处理算法特殊变体的小方法。此时把每个算法变体搬移到新类/子类更好——这是对象组合 vs 继承的选择：
  - 变体简单对应明确子类（尤其有类型代码控制时）→ 用多态替换条件式 [F]（基于继承）可能更合适；
  - 无类型代码、或需在运行时用一种计算类型替换另一种 → Strategy 更好（替换 Strategy 实例远比改变对象类型容易）；
  - 一个类需要用多种方法计算且不想让类层次被子类撑爆（如 Loan 需要资金计算×风险计算×调整后资金计算的子类组合爆炸）→ Strategy。
- 数据传递两种方式：(a) 把上下文（context，主类）引用传入策略——缺点破坏信息隐藏，优点新增公共方法即对所有策略可用（可用包级保护控制可见性）；(b) 通过参数直接传数据——耦合最小，但参数多时不可行（可引入参数对象 [F] 减少，或把仅个别策略用的数据经构造函数传入该策略）。
- 可结合用 Factory 封装类（6.3）屏蔽客户代码对策略实例化/装配的感知。
- 与 Decorator 的取舍见 7.3 节补充"Decorator 与 Strategy"。

### 做法
1. 确定上下文类（含大量条件逻辑的计算方法所在类）；创建策略类（可加 "Strategy" 后缀命名）。
2. 应用搬移函数 [F]：在策略类中声明计算方法，把上下文中的计算复制/搬移过去（连带只被计算使用的辅助方法），决定传上下文引用还是传数据；在上下文中保留简单的委托版计算方法，并保存策略引用的字段（避免每次 new）。编译、测试。
3. 应用提取参数（11.3）使客户代码能用具体策略实例装配上下文（委托不再硬编码）。编译、测试。
4. 在策略类的计算方法上应用用多态替换条件式 [F]：实现以子类取代类型码 [F]（条件逻辑确定计算类型时用该条件逻辑替代显式类型码），每次只产生一个子类；可能时把策略类声明为抽象类。编译、测试。

### 适用信号 / 坏味道
- 算法（计算方法）内含大量条件逻辑用于选择变体；辅助小方法堆积只为服务算法变体；需要在运行时切换算法；类因算法变体面临子类组合爆炸。

## 将装饰功能搬移到 Decorator（Move Embellishment to Decorator）

**一句话**：代码向类的核心职责提供装饰功能 → 将装饰代码搬移到 Decorator。

### 动机
- 新功能通常以装饰核心职责的形式加入旧类，却为主类带来新字段、新方法、新逻辑，仅仅为了满足偶尔执行的特殊行为。
- Decorator [DP]：把每个装饰功能放在单独的类中，包装被装饰对象；需要特殊行为时客户代码在运行时用装饰器包装对象（如 JUnit 的 RepeatedTest 装饰 TestCase 实现重复运行）。
- 前提与限制：
  - 被修饰类公共方法不能太多——Decorator 必须是"透明的包装"，需实现被装饰类的所有公共方法，方法多则产生大量无用代码（此时考虑 Strategy）；
  - 客户代码中 `instanceof` 类型检查会失效（Decorator 与被装饰者不同类型），但通常可改写客户代码不依赖类型；
  - 多个 Decorator 组合时顺序可能影响行为（如先加密后过滤词汇会互相干扰）；理想上各装饰器彼此独立，否则可封装安全组合并通过 CreationMethod 暴露；
  - 装饰功能若是保护逻辑，可考虑 Protection Proxy（6.3）（结构同 Decorator，意图不同）；
  - 不熟悉对象组合会觉得代码散落多类、难以理解与调试（调试需穿越装饰器）。
- 作者建议：倾向"重构趋向该模式"，勿在不必要时使用。

### Decorator 与 Strategy（补充）
两者都去除与特殊情况/可选行为相关的条件逻辑并把行为搬移到新类。区别在新类的使用方式：Decorator 在对象之外包装（可彼此包装），Strategy 在对象之内被使用。考虑点：
- Decorator 实例不可共享（每个只包装一个对象）；Strategy 可用 Singleton/Flyweight 轻松共享。
- Strategy 可自定义接口；Decorator 必须与被装饰类接口一致。
- Decorator 可透明地为共享同一接口的多个类添加行为；使用 Strategy 的类必须知道策略的存在。
- 对数据多/公共方法多的类，用 Strategy 常见；Decorator 用于装饰这类类会过重。

### 做法
- 前置：确定被修饰类，确认其公共方法不过多（否则精简方法或改用 Strategy）。
1. 确定或创建包装类型（Decorator:Component，接口或类），声明客户需要的被修饰类公共方法。已有包装类型应为被修饰类实现的接口或超类；含状态（字段）的类不合适（Decorator 会继承不需要的状态）。没有则用统一接口（11.2）和/或提炼接口 [F] 创建。
2. 找到添加装饰功能的条件逻辑（switch/if），应用用多态替换条件式 [F] 去除（通常先以子类取代类型码 [F]，CreationMethod 的返回类型须为包装类型；可能需要形成 Template Method [F]）。编译、测试。
3. 应用以委托取代继承 [F]：使每个委托类实现包装类型，委托字段类型为包装类型，决定装饰代码在委托调用之前还是之后执行；必要时调整可见性并重做统一接口；委托返回未装饰实例的方法要先装饰再交给客户。注意避免子类中调用超类方法的方法陷入无限递归。编译、测试。
4. 应用提取参数（11.3）+ 移除参数 [F]：把委托字段改为构造函数参数传入（而非内部实例化），尽量移除不必要参数。至此成为完整 Decorator。编译、测试。

### 适用信号 / 坏味道
- 类的核心职责中混杂特殊状况/装饰逻辑（如按需解码、去转义字符）；新增装饰功能导致横跨多个类的修改（解决方案蔓延：过多初始化逻辑 + 过多装饰逻辑）；相关类间重复的装饰逻辑。

## 用 State 替换状态改变条件语句（Replace State-Altering Conditionals with State）

**一句话**：控制对象状态转换的条件表达式过于复杂 → 用处理特殊状态和状态转换的 State 类替换条件语句。

### 动机
- 重构实现 State [DP] 的主要动机：对付过度复杂、散布在类中各处的状态改变条件逻辑。创建代表特殊状态和转换的 State 类；含状态改变的对象称为上下文（context），把状态相关行为委托到状态对象，通过引用不同状态对象在运行时实现转换。
- 收益：去除/减少条件逻辑，得到观察状态转换的更好的鸟瞰图；设计更易理解、扩展。
- 若转换逻辑本就易于理解（且将来不会增加状态），不必重构到 State（如简单四状态 SystemPermission 的初始版本）。重构前先试试提炼函数 [F] 等简单手段。
- 与 Fowler 的"用 State/Strategy 替换类型代码 [F]"不同：State 作用于需在一系列状态类实例间方便转换的类，Strategy 作用于把算法执行委托给一系列策略类的类；本书给出完整做法。
- 优化：无状态（无实例变量）的状态对象可通过上下文共享（Flyweight/Singleton）；仅在 profiler 指出实例化是瓶颈时才做。

### 做法
1. 上下文类中找出原始状态字段（被常量赋值/比较）。应用用类替换类型代码（9.1）使其类型变成一个类——状态超类。编译。
2. 为每个常量提炼子类（State:ConcreteState），更新超类常量引用相应子类实例；把状态超类声明为抽象类。编译。
3. 找出上下文中根据状态转换逻辑修改状态字段的方法，复制到状态超类（做最小修改使其可运行，常是传入上下文引用以便回调），上下文原方法体替换为委托调用。编译、测试。对每个此类方法重复。
4. 选一个上下文可进入的状态，识别哪些方法使它转换到其他状态；把这些方法复制到对应状态子类并删除无关逻辑（状态验证、转换到无关状态的逻辑）——如 PermissionRequested.claimedBy 简化为直接 `willBeHandledBy(admin); setState(CLAIMED)`。编译、测试。对每个状态重复。终止状态（如 GRANTED）无需实现转换方法，继承空实现即可。
5. 删除状态超类中步骤 3 复制来的方法体（空实现）。编译、测试。

### 适用信号 / 坏味道
- 大量 `state.equals(...)` 式的条件/布尔逻辑（如 isUnixPermissionRequestedAndClaimed）散布在类中；新增状态时条件逻辑迅速膨胀、难以遵循和扩展；同一方法要处理多个状态的合法性检查与转换。

## 用 Composite 替换隐含树（Replace Implicit Tree with Composite）

**一句话**：用原生表示法（如 String）隐含地形成树结构 → 用 Composite 替换这个原生表示法。

### 动机
- 隐含树：数据或代码未显式构造成树，却可用树表示（如手工拼接 XML 字符串；条件逻辑也可构成 and/not 树）。
- 动机是让代码更简单、更短小精悍：Composite（TagNode 之类）自动处理格式化与结束标签，客户不必重复这些工作。
- 对条件逻辑：只有存在相似条件逻辑增长时才有意义（如 ProductFinder 中 byColor、byColorAndBelowPrice、byColorSizeAndBelowPrice 不断复制 if 组合）。
- 基于数据的隐式树常 suffer 构造代码与树表示代码的紧耦合；重构到 Composite 解开它，但客户又与 Composite 耦合，有时需再加间接层（如客户有时用 Composite、有时用 DOM 生成 XML → 用 Builder 封装 Composite，6.5）。
- 树少、小、易管理时直接建隐式树即可；当处理隐式树变难或代码因此膨胀时才重构。也可权衡演化节奏：先快速用隐式树攻克其他难题，回头再重构到 Composite（当这些代码会被系统许多地方效仿时尤其值得）。

### 做法
两种等价做法：标准逐步重构，或测试驱动开发（TDD）；提炼类 [F] 无助于隐式树时选 TDD。
1. 识别隐式叶子（implicit leaf），创建对应叶子结点类（Composite:Leaf），可用提炼类 [F] 或 TDD；隐式叶子有属性时叶子结点也建相同属性，使其表示（含属性）与隐式叶子吻合。编译、测试。
2. 用叶子结点实例替换代码中的隐式叶子。编译、测试隐式树功能。
3. （如叶子不止一种）让所有叶子结点共享统一接口（提炼超类/提炼接口 [F]）。本节示例中一个通用 TagNode 可表示所有叶子，无需此步。
4. 识别隐式双亲（implicit parent），产生双亲结点类（Composite 本体）。客户须能通过构造函数或 add(...) 添加子结点；双亲统一对待所有子结点（经统一接口）；若客户不应区分叶子和双亲（参见 8.3），双亲也实现统一接口。
5. 用配置好叶子结点的双亲结点实例替换隐式双亲的每次使用。编译、测试。
6. 对剩余隐式双亲重复步骤 4–5，直到 getContents 等客户代码只创建并组装 TagNode、调用 toString() 输出。
- 注意：不要因此把 toXML() 放进领域对象——当同一领域对象需要多种 XML 表示时，表示应留在领域对象之外（多表示时还可考虑 Visitor，10.2）。

### 适用信号 / 坏味道
- 手工拼接字符串形成树结构（XML 生成中重复的格式化与结束标签代码）；构造代码与树表示紧耦合；相似的条件组合逻辑不断复制增长。

## 用 Command 替换条件调度程序（Replace Conditional Dispatcher with Command）

**一句话**：条件逻辑用来调度请求和执行操作 → 为每个动作创建一个 Command，存入集合，用获取及执行 Command 的代码替换条件逻辑。

### 动机
- 条件调度程序：执行请求发送和处理的一条条件语句（如 switch）。适合任务的条件调度程序只把少量请求发到少量处理逻辑、一屏内可看完——此时用 Command 替换并无益处。
- 重构到 Command 的两大理由：
  1. 缺少运行时灵活性：客户需要用新请求/处理逻辑动态配置调度程序，而所有发送/处理逻辑被硬编码在单一条件语句中；
  2. 代码体膨胀：调度程序随新请求的加入或处理逻辑复杂化变得巨大笨拙，仅提取方法帮助有限。
- Command [DP] 方案：每块请求处理逻辑放进一个"命令"类，含通用执行方法（execute()/run()）；用一个集合（Map，以命令名为主键）存储、获取命令实例，添加/删除/修改，调用执行方法。服务端 Web 系统常直接采用此模式作为标准请求分发方式。
- 关于 undo/redo：不确定是否需要时不预实现 Command（YAGNI）；需要时再重构实现并不难；除非代码正变得越来越难重构且日后需要 undo 的概率很大——那时提前实现像上保险。
- 缺点：条件调度程序已足够时会增加设计复杂度。

### 做法
1. 对条件语句的每段代码应用提炼函数 [F]，直到产生执行该行为的执行方法（execution method）。编译、测试。
2. 对其余请求处理代码重复，各自成为执行方法。
3. 创建具体命令：对每个执行方法应用提炼类 [F] 产生具体命令类（执行方法通常为公共；过于庞大难懂时先应用组合方法 7.1）。编译、测试。
4. 在具体命令中寻找重复代码，考虑形成 Template Method（8.1）去除。分析以下问题以设计通用执行方法：必须传什么参数？构造时可传什么？哪些信息可经回调参数获得？执行方法的最简签名是什么？应用提炼超类/提炼接口 [F] 产生命令（接口或抽象类）的早期版本。编译。
5. 使每个具体命令实现/继承该命令，把所有使用具体命令的客户代码更新为命令类型。编译、测试。
6. 创建命令映射（command map）：实例化每个具体命令，以唯一标识符（如命令名）为主键存入，运行时按键获取。具体命令很多时考虑 Plugin 模式（PEAA），用配置数据装载（命令类名列表或类目录）。编译。
7. 在含条件调度程序的类中，把调度请求的条件代码替换为"查找正确的具体命令并调用其执行方法"——该类成为 Invoker。

### 适用信号 / 坏味道
- 庞大的 if/else-if 链（好几页）按请求名分发到各自的大段处理逻辑（如 CatalogApp 的 executeActionAndGetResponse）；需要运行时动态注册/替换请求处理；每加一个请求就要改条件语句。
