# 第10章 聚集操作（Accumulation）

系统中很多代码用于聚集信息，本章重构的目标是改进在一个对象内或几个对象间聚集信息的代码。核心是 Collecting Parameter 模式 [Beck, SBPP]：一个对象被传入多个方法中收集信息，最后从中取回聚集结果。它与 Visitor [DP] 都能从多个对象聚集信息，区别在聚集方式：被 Visitor 访问的对象把自己传入 Visitor（双分派），而被 Collecting Parameter 访问的对象只是调用其上的方法提供信息。Visitor 更适合从许多接口各异的类中聚集大量不同信息，但实现更复杂、只适用于多对象场景，应先考虑 Collecting Parameter。Visitor 并不只用于聚集（还可向结构添加对象等），到 Visitor 的重构很少见，故本章只介绍聚集方向的两个重构。

---

## 将聚集操作搬移到 Collecting Parameter（Move Accumulation to Collecting Parameter，10.1）

**动机**
- 有一个很大的方法把信息聚集到局部变量中：把结果聚集进一个 Collecting Parameter，并将它传入被提炼出的方法。
- 常与组合方法（Composed Method，7.1）配合：把接收并写入 Collecting Parameter 的代码提炼成小方法，将大方法分解为几小块，每块处理一小部分聚集。
- 两种回调方式：对象回调 Collecting Parameter 上的方法传递数据，或对象把自己传给 Collecting Parameter 由其调用回调方法取数据。
- 适合从具有特定接口的特定类聚集数据；若要聚集的类数据各异、接口不同，则应改用 Visitor（10.2）。与 Composite [DP] 配合良好，可递归地从 Composite 结构聚集（JUnit 的 TestResult 即是典型 Collecting Parameter）。
- 实战背景：toString() 中字符串连接慢，简单换成 StringBuffer 会因递归产生大量 StringBuffer 实例，改用单一 StringBuffer 作为 Collecting Parameter，设计更简单、可读性更好、运行更快。
- 优点：帮助把大方法转换成更小、更简单的多个方法；使代码运行更快。

**做法**
1. 识别聚集方法（accumulation method，即把信息聚集成结果的方法），把结果改为可在方法间收集的类型（如 String 改为 StringBuffer）。
2. 在聚集方法中找到信息聚集的步骤，应用提炼函数 [F] 提炼为私有方法：返回类型 void，结果作为参数传入，方法内把信息写入结果。
3. 对每个聚集步骤重复步骤 2，直到原方法只剩三行：实例化结果；把结果传入第一个方法；从结果取回聚集的信息。
4. 对提炼出的 Composed Method 应用组合方法（7.1）。

**适用信号/坏味**
- 过长函数（Long Method）：一个很大的方法把信息聚集到局部变量，如递归遍历 Composite 生成 XML 的 toString()。
- 大方法难以分解为 Composed Method，因为不知道如何从各被调方法中汇出结果。

## 将聚集操作搬移到 Visitor（Move Accumulation to Visitor，10.2）

**动机**
- 一个方法从不同的类中聚集信息：把聚集工作搬移到一个能访问每个类的 Visitor 中。
- Ralph Johnson："大多数时候你并不需要 Visitor，但一旦需要，那就是真的需要。" 真正需要 Visitor 的情形：
  - 有很多运行在不同对象结构上的算法，且没有比 Visitor 更简单/简洁的方案——例如每个域类都堆满了多个 toXml() 表示方法（内部聚集方法），新增一种表示就要为每个域类加方法，且表示代码污染领域逻辑；
  - 有很多外部聚集方法，用 Iterator [DP] 遍历并对不同对象做频繁 instanceof 判断和类型转换来访问特殊接口——若能通过通用接口把互不相同的类变相似（异曲同工的类坏味），应先统一接口而非用 Visitor。
- 双分派：每个被访问类实现 `accept(Visitor)` 并回调相应的 `visitClassName(this)`，Visitor 可不经类型转换地调用类型特定方法，访问相同或不同继承结构中的类。
- 谨慎决策：先问 Visitor 是否真的带来更简单简洁的方案、是否会连带改善其他代码、有无更简单方案、现有代码是否已足够简单；也先考虑能否统一接口（11.2）避免 Visitor。类集合若频繁增长通常应避免 Visitor（每个新类要加 accept，每个 Visitor 要加 visit），但可调查是否只需访问子集、其余用超类的 accept。对"访问循环晦涩"和"破坏封装"的常见反对意见：前者取决于团队对模式的熟悉度；后者即使需要改几处可见性，代价也常低于不用 Visitor。
- 优点：调节多个算法适用于不同对象结构；访问相同/不同继承结构中的类；无需类型转换即可调用不同类的类型特定方法。缺点：可用通用接口变相似时会增加复杂度；新的可访问类需要新的 accept 方法且每个 Visitor 需加 visit 方法；可能破坏被访问类的封装性。

**做法**（分三种：外部聚集方法 / 内部聚集方法 / Visitor 替换）

**1. 外部聚集方法**（聚集方法在互不相同的类之外的"主类" host 中；主类若角色过多，先用用方法对象替换方法 [F] 提炼新主类）
1. 把聚集逻辑多次引用的局部变量转换成主类字段。
2. 对针对一个聚集源（accumulation source）的聚集逻辑应用提炼函数 [F]，提炼出的方法命名为 accept(...)，接收聚集源类型参数；对每个聚集源重复。
3. 在每个 accept(...) 方法体上提炼函数 [F]，产生 visitClassName() 方法（如 visitEndTag(EndTag)）。
4. 用搬移函数 [F] 把每个 accept(...) 搬到相应聚集源中，accept 接收主类类型参数。
5. 对聚集方法中每个 accept(...) 调用应用内联方法 [F]。
6. 对聚集源的超类/接口应用统一接口（11.2），使 accept(...) 可多态调用。
7. 泛化聚集方法，多态地调用每个聚集源的 accept(...)。
8. 在主类上应用提炼接口 [F]，产生声明各 visit 方法的访问者接口（visitor interface）。
9. 修改所有 accept(...) 签名改用访问者接口。主类此时即是一个 Visitor。

**2. 内部聚集方法**（聚集方法在互不相同的类内部，这些类通常属同一继承结构；基于 Roberts/Brant/Johnson 论文）
1. 创建一个新类作为访问者（名字中考虑用 visitor）。
2. 识别被访问者（visitee），在访问者中添加 `visitClassName(...)`：返回 void、接收被访问者参数；对每个将被聚集的类重复。
3. 在每个被访问者的聚集方法体上提炼函数 [F]，改为调用签名一致的接受方法（accept method）。
4. 各类的聚集方法已一致，用函数上移 [F] 搬到超类。
5. 用添加参数 [F] 为每个 accept 实现加访问者类型参数，聚集方法调用 accept 时传入新的访问者实例。
6. 在被访问者的接受方法上应用搬移函数 [F]，为访问者产生访问方法（accept 调用 `visitor.visitXxx(this)`）；对每个被访问者重复。

**3. Visitor 替换**（既无内部也无外部聚集方法，但换成 Visitor 设计更好）
1. 创建具体访问者；出现第二个具体访问者时，在第一个上提炼超类 [F] 形成抽象访问者，被访问者消息签名改收抽象访问者（不上移具体特有的数据/方法）。
2. 识别被访问者，在具体访问者中添加 visitClassName(...)。
3. 在每个被访问者中添加 accept(抽象/具体访问者)，方法体回调相应 visit 方法并传入自身。
4. 对每个被访问者重复 2–3，形成访问者框架。
5. 在具体访问者中实现获取聚集结果的公共方法，结果初始为空或 null。
6. 在聚集方法中定义并实例化具体访问者字段；为每个被访问者添加 accept 调用并传入访问者；聚集方法改用访问者的结果（此步测试会失败）。
7. 实现每个 visit 方法体（把聚集代码复制进来并调整：确保各 visit 能从被访问者取到所需数据/逻辑；两个以上 visit 共用的字段在访问者中声明并初始化；无法从被访问者获得的数据由构造函数参数提供）。
8. 尽量删除聚集方法中的旧代码。
9. 聚集方法应迭代对象集群、为每个对象调用 accept 并传入访问者；为集群相关类/超类/接口应用统一接口（11.2），使迭代无需区分对象类型。

**适用信号/坏味**
- 分支语句（Switch Statements）坏味：聚集方法中大量 instanceof + 类型转换。
- 异曲同工的类（Alternative Classes with Different Interfaces）且无法用通用接口统一时。
- 域类堆满 toXml/toX 等表示逻辑（内部聚集方法），或存在多个雷同的外部聚集方法。
