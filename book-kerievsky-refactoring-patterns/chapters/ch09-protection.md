# 第9章 保护（Protection）

本章重构的目标是保护代码：改进对现有代码的保护，或服务于标准重构动机（减少重复、简化澄清代码）。三个重构分别保护字段免受不正确赋值（用类替换类型代码）、限制实例化数量（用 Singleton 限制实例化）、避免 null 引发的错误（引入 Null Object）。

---

## 用类替换类型代码（Replace Type Code with Class，9.1）

**动机**
- 字段的类型（如 String/int）无法保护它免受不正确赋值和非法等同性比较；拼错的字符串常量不会造成编译错误，却会使对象进入非法状态且状态转换逻辑无法将其救回。
- 主要动机是类型安全：用类（Type-Safe Enum 模式 [Bloch]）限制可赋给字段/变量的值，所有赋值与比较都必须通过类型安全的类常量。
- 语言级枚举并不能使本重构过时：类可以继续添加行为（如"用 State 替换状态改变条件语句"（7.4）的第一步必须基于本重构而非枚举）。
- 优点：更好地避免非法赋值和比较；缺点：比不安全类型要求更多代码。

**做法**
1. 识别类型不安全字段（原生/非类类型，被一系列类型不安全常量赋值或比较），对其应用自封装字段 [F]。
2. 创建一个新类，按将要存储的类型命名，暂不提供构造函数。
3. 为每个用于赋值/比较的常量值，在新类中创建对应的 `public final static` 实例常量。若要防止客户添加新常量，声明私有构造函数或将类标记为 final。
4. 在原类中创建类型为新类类型的字段，并为其创建设置方法。
5. 在所有对类型不安全字段赋值的地方，添加对类型安全字段的相似赋值语句（使用新类常量）。
6. 修改类型不安全字段的获取方法，使其从类型安全字段取值（新类常量需能返回正确值，如通过 toString() 返回名字）。
7. 删除类型不安全字段、其设置方法及所有对设置方法的调用。
8. 将所有对类型不安全常量的引用替换为新类中的相应常量；获取方法改为返回新类类型；确保等同性逻辑对新类实例正确工作（必要时自行实现 equals）。
9. 删除不再使用的类型不安全常量。

**适用信号/坏味**
- 字段用 String/int 等类型代码表示状态、类别，被一组常量赋值/比较。
- 存在拼错常量字符串却编译通过、导致非法状态的风险；该字段控制运行时行为时尤其危险。

## 用 Singleton 限制实例化（Limit Instantiation with Singleton，9.2）

**动机**
- 代码创建了一个对象的多个实例，导致内存占用过多、性能下降；用 Singleton 替换多个实例。
- 不要做不成熟的优化：因"Singleton 让代码更高效"而使用它是"Singletonitis"，应先看内联 Singleton（6.6）。只有在充分理由存在时才重构到 Singleton：
  - 用户持续抱怨性能；
  - 性能分析程序（profiler）指出可以通过避免反复实例化某对象来改进性能；
  - 希望被共享的对象不含状态，或仅含可共享的状态。
- 优点：改进性能、随处可访问（但这常是设计缺点）；缺点：对象含有不可共享状态时本重构无效。

**做法**
前置条件：确认对象无状态或只含可共享状态。
1. 用"用 CreationMethod 替换构造函数"（6.1）的做法把构造函数转为 CreationMethod（即使只有一个构造函数），返回类型为该多实例类；更新所有调用者。
2. 声明单件字段（singleton field）：类中私有的、静态的、类型为多实例类的字段；如可能，直接初始化为该类的一个实例（若需运行时参数则只声明不初始化）。
3. 令 CreationMethod 返回单件字段；若只能迟实例化（lazy instantiation），在 CreationMethod 中基于传入参数实现迟实例化。
4. 对其余多实例类重复；之后用 profiler 验证收益，若无改进宁可撤销、使用普通对象。

**适用信号/坏味**
- profiler 显示频繁实例化无状态对象（如 State 模式中每次状态转换都 new 一个 State 对象）拖累性能/内存。
- 想控制一个类可被实例化的对象数量。

## 引入 Null Object（Introduce Null Object，9.3）

**动机**
- 代码中到处是处理 null 字段/变量的重复检查逻辑（`if (x != null) x.doSomething(); else ...`），使代码难理解、难扩展，且不能保护忘记写 null 检查的新代码。
- Null Object 模式 [Woolf]（Bruce Anderson 称之为 active nothing；Fowler 视其为 Special Case 的示例）：让字段/变量在为"空"时引用一个提供"什么也不做/默认/无害行为"的对象，从而对它的所有调用都安全，无需再检查 null。窍门是在正确时机赋正确的对象。
- 约束：引入 Null Object 后代码量应减少或不变；若比原有 null 逻辑显著增加代码行数，说明不需要它（Erich Gamma 的检验法）。
- 实现方式：通常用子类或实现接口实现 Null Object。子类方式的风险：超类新增公共方法时必须记得在 Null Object 中重写，否则继承到超类实现导致运行时意外；接口方式可去除此风险。
- 优点：无需重复 null 逻辑即可避免 null 错误、通过最小化 null 测试简化代码；缺点：系统不太需要 null 测试时反而增加设计复杂度；程序员不知道 Null Object 存在时会写多余 null 测试；子类式 Null Object 使维护变复杂。
- 注意：Null Object 的存在不能保证没人再写 null 逻辑；若客户期望某种情况下真的返回 null 并有重要处理代码，可能产生意外行为。

**做法**（针对"字段/变量可能在 null 时被引用"这一通用情况；其他情况见 Fowler 的引入 Null Object）
源类（source class）指希望避免 null 的类。
1. 在源类上应用提炼子类 [F] 创建 null 对象；或让新类实现源类已实现的接口（接口不存在时先应用提炼接口 [F]）。
2. 寻找 null 检查（非 null 则调用源类实例方法、为 null 则执行特定行为）；在 null 对象中重写被调用的方法，实现该特定行为。
3. 对与源类相关的其他 null 检查重复步骤 2。
4. 找出出现 null 检查的类，用 null 对象实例初始化其中的字段/局部变量——在对象寿命的最早时刻（如紧跟实例化处）执行；不影响之后赋真实对象的代码。
5. 在这些类中删除所有 null 检查。
6. 对每个含 null 检查的类重复步骤 4–5。
7. 若系统创建了很多 null 对象实例，用 profiler 评估是否需要"用 Singleton 限制实例化"（9.2）。

**适用信号/坏味**
- 多个类中散布相同的 `if (field != null)` 检查，皆因某字段在赋真实值之前就可能被引用（如初始化窗口期内 handler 尚未配置好）。
- 真实案例：Java AWT 中组件对布局管理器的 null 检查，本可用 NullLayout 作为默认布局管理器消除。
