# 排障复盘：四段心路

## 这个 skill 解决什么问题

用户解决了一个技术问题后，常想听的其实是定位过程本身：你怎么思考的、在哪走了弯路、凭什么最后找到解法。

三种常见的失败输出：

1. **流水账**：罗列"先 grep、再看 log、然后 npm"——只有动作没有思维，没人看得下去。
2. **事后诸葛亮**：把试错包装成"我一开始就知道了"，丢掉复盘里最值钱的部分。
3. **只给补丁不讲因果**：说不清"什么改动、经什么机制、变成什么现象"。

一句话：**复盘还原的是思维迭代，不是命令日志。**

## 四段结构

按以下四段输出，每段都不能省，碰壁尤其不能省：

### 1. 做了什么

- 现场是什么：用户的原始现象/报错，环境与触发时机。
- 取证抓到了什么：关键日志、关键配置现状。提炼核心发现，不贴大段输出。

### 2. 怎么想的

- 第一反应套的是哪个经验或模型（如"这是典型的多仓隔离问题"、"这是权限缺失"）。
- 当时凭什么觉得它说得通——把当时的证据链摆出来。

### 3. 在哪碰壁

- 哪个事实击穿了假设：用户的一句反问、一个反常的时间点、一条矛盾的日志。
- 反思漏了什么维度（比如只看静态配置、漏掉变更历史；只看代码、漏掉外部系统）。
- 思维怎么转的向：从哪条排查路线切换到哪条。

### 4. 怎么解决

- 完整因果链讲透：`[初因] → [底层机制] → [连锁反应] → [表象]`。
- 为什么这么改是根治，而不是打补丁。
- 一句话 Takeaway：下次遇到同类诡异问题，先看什么。

## 红线

1. **禁止流水账**：不许出现"第 1 步调 X 工具、第 2 步调 Y 工具"。把操作提炼成探索动作（如"比对子项目与全局环境"、"翻语言服务器启动日志"）。
2. **必须真实呈现试错**：走过弯路、猜错方向、被用户纠正，都要如实写——碰壁是复盘里最值钱的部分。
3. **亮出认知差**：「原来以为 vs 实际真相」对比越鲜明，复盘越有洞察力。
4. **说人话**：像老工程师在白板前给搭档画推导脉络，不用学术腔词组。
