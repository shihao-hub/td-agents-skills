# Plan Mode

## 三条硬性要求（用户指定，优先级最高）

1. **计划不进会话**：完整计划直接写入计划文件，会话里只给路径 + 一屏摘要，绝不全文输出。无写权限时不贴全文，改为向用户请求切换模式（说清需要写文件权限和目标路径）。
2. **命名参考 sh-plan**：计划文件为 `plans/{NN}-{feature_name}.md`，编号沿用 sh-plan-driven-development 的约定——取 plans/ 下现有最大编号 +1，个位数补零。
3. **批准前不执行**：计划落盘后停在审批门，用户明确批准之前不写任何业务代码。

## 何时进入计划

非平凡的实现任务默认进计划。满足任意一条即进：

1. **新功能实现**：有意义的新功能
2. **多种合理方案**：同一目标可走多条路径
3. **修改现有行为**：影响已有逻辑或结构
4. **架构决策**：需要在模式/技术间选择
5. **多文件改动**：预计触及 2-3 个以上文件
6. **需求不明**：需要先探索才能确定范围
7. **用户偏好会影响走向**：本想提问澄清方案的，改为进计划——先探索，再带上下文给选项

可跳过的简单任务：单行/几行修复（错别字、明显小 bug）、需求明确只加一个函数、用户已给出非常具体详细的指示、纯调研类任务（不产出实现计划）。

拿不准时，倾向计划（err on the side of planning）——前期对齐的成本远低于返工。

## 计划阶段（read-only）

唯一允许的写文件动作是计划文件本身。严格禁止：创建/修改/删除/移动/复制文件、在任何地方建临时文件（含 /tmp）、用 `>` `>>` `|` 或 heredoc 写文件、运行任何改变系统状态的命令。Shell 只允许只读操作（`ls`、`git status`、`git log`、`git diff`、`find`、`cat`、`head`、`tail`）。

流程：

1. **探索**：用 Glob / Grep / Read 读代码，理解现有架构与约定，找相似功能实现作参考
2. **澄清**：影响方案的问题在计划定稿**之前**问用户；计划必须完整、无歧义，不带未决假设
3. **落盘**：把完整计划写入 `plans/{NN}-{feature_name}.md`；无写权限时发模式切换请求，不在会话里贴全文
4. **摘要**：会话中只给计划文件路径 + 一屏摘要，然后停在审批门

计划内容（源自 Plan 子代理的 Required Output）：

- 分步实现策略、依赖与顺序、可预见的挑战
- 结尾列出实现最关键的 3-5 个文件（`### Critical Files for Implementation`）

## 审批门

- 落盘 + 摘要这个动作本身就是批准请求；审批对象是**计划文件本身**，用户打开文件审阅
- **不要用提问代替审批门**：不问"这个计划可以吗？需要我调整吗？"——那正是落盘+摘要该完成的事
- 用户批准 → 进入执行；用户给修改意见 → 先更新计划文件，重新等待批准

## 执行阶段（批准后）

- 按计划实现；每完成一项，把计划文件里的 `- [ ]` 勾成 `- [x]`
- 发现计划有误或需求变化：**先更新计划文件，再改代码**
- 收尾：向用户汇报完成情况

## 调研任务的例外

"搜索并理解 X 的实现"这类纯调研任务不产出实现计划、不进审批门，直接调研汇报；"帮我实现 X"才走完整流程。

## 出处

机制逐条取自 `references/claude-code-originals.md` 的逐字摘录（EnterPlanMode / ExitPlanMode / AskUserQuestion 定义与 Plan 子代理提示词，2026-08 抓包自第三方仓库 asgeirtj/system_prompts_leaks，非官方发布），剥离了产品工具名与历版自研扩展，另叠加"三条硬性要求"。
