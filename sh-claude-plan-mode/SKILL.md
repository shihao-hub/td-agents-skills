# Plan Mode

在动代码之前先取得用户对方案的认可：进入计划模式，探索代码库、设计实现方案，向用户呈现计划请求批准，获批后再实施。前期对齐好过事后返工；用户欣赏在其代码库被显著改动前受到征询。

## 何时进入计划

对实现任务倾向使用计划，除非任务足够简单；进入需征得用户同意。满足任意一条即进：

1. **新功能实现**：添加有意义的新功能
2. **多种合理方案**：任务可以走多条路径解决
3. **修改现有代码**：改动影响既有行为或结构
4. **架构决策**：需要在模式或技术之间做选择
5. **多文件改动**：预计触及超过 2-3 个文件
6. **需求不明**：需要先探索才能理解完整范围
7. **用户偏好会影响走向**：实现存在多种合理做法
   - 本想通过提问澄清方案的，改为进入计划——计划模式允许先探索，再带上下文给出选项

拿不准时，倾向计划（err on the side of planning）。

## 何时跳过

仅对简单任务跳过：

- 单行/几行修复（错别字、明显小 bug、小调整）
- 需求明确、只加一个函数
- 用户已给出非常具体、详细的指示
- 纯调研/探索任务（不产出实现计划，直接调研汇报）

## 计划模式中做什么

1. 用 Glob / Grep / Read（必要时 `find`）彻底探索代码库
2. 理解既有模式与架构，找相似功能实现作参考，追踪相关代码路径
3. 设计实现方案：权衡取舍与架构决策，适当遵循既有模式
4. 需要澄清方案时先提问（见"先澄清，后定稿"）
5. 完成实现步骤的规划后，向用户呈现计划、请求批准
6. 获批后退出计划模式，开始实施

### 只读纪律

计划阶段只做探索与规划，严禁：

- 创建任何新文件（Write、touch 等一切形式）
- 修改既有文件（Edit 等）
- 删除文件（rm 等）
- 移动或复制文件（mv、cp）
- 在任何位置创建临时文件（包括 /tmp）
- 用重定向（`>`、`>>`、`|`）或 heredoc 写文件
- 运行任何改变系统状态的命令

Shell 仅限只读操作：`ls`、`git status`、`git log`、`git diff`、`find`、`cat`、`head`、`tail`；绝不 `mkdir`、`touch`、`rm`、`cp`、`mv`、`git add`、`git commit`、`npm install`、`pip install` 或任何文件创建/修改。

### 先澄清，后定稿

- 影响需求或方案的问题，在计划定稿**之前**问用户；提问只用于澄清需求或在方案权衡中做选择
- 定稿时计划必须完整、无歧义，不带未决问题
- 提问不得引用"计划"本身——用户在计划呈请批准之前看不到计划内容

## 呈现计划与审批门

- 呈现完整计划（分步实现策略、依赖与顺序、可预见的挑战，结尾列出实现最关键的 3-5 个文件，标题 `### Critical Files for Implementation`）
- 呈现计划这个动作本身就是批准请求：不问"这个计划可以吗？""要我继续吗？"——那正是审批门要做的事
- 仅当任务需要规划"写代码的实现步骤"时才走审批门

## 调研任务的例外

纯调研任务（搜集信息、搜索/读文件、理解代码库）不走审批门，直接调研汇报。示例：

1. "搜索并理解 vim mode 在代码库中的实现" —— 不走审批门：没有需要规划的实现步骤
2. "帮我实现 vim 的 yank mode" —— 完成实现步骤规划后走审批门
3. "新增用户认证功能" —— 拿不准认证方式（OAuth、JWT 等）时先提问澄清，澄清后再走审批门

## 执行（批准后）

- 用户批准 → 按批准的计划实施
- 用户给修改意见 → 修订计划后重新呈现、重新等待批准
- 实施中发现计划有误或需求变化 → 先修正计划再继续写代码
- 收尾：向用户汇报完成情况

## 出处

机制逐条对齐 `references/claude-code-originals.md` 的逐字摘录（进入/退出计划模式的工具定义、提问澄清注记、规划子代理提示词），本文隐去原文的产品与工具名；溯源与英文原文见该文件。
