# Chapter 5: 弯曲，或折断（Bend or Break）

## Core Idea
 life 就像生命体：能弯（适应变化）才能不折断。通过最小化耦合（得墨忒耳法则）、把细节赶出代码（元数据）、解除时间上的耦合（并发/服务）、解耦事件（发布订阅/MVC）、用黑板协调工作流，让系统在需求变化时依然存活。

## Frameworks Introduced
- **函数的得墨忒耳法则**：某对象的任何方法只应调用属于以下情形的方法——它自身、传入该方法的参数、它创建的对象、它直接持有的组件对象；适用时机：发现"简单改动会波及无关模块"、开发者害怕改代码、单元测试链接命令比测试本身还长时；怎么做：写"羞怯"代码、用委托做总承包装，必要时权衡性能（可像反规范化一样有意识地违反）。
- **元数据驱动的应用**：为一般情况编程，把具体情况放在代码库之外的元数据中；适用时机：商业规则/政策/工作流经常变化时；怎么做：声明式配置（算法、数据库、UI 风格、业务规则都作为配置），用纯文本表示，长期运行的服务支持运行时重载配置。
- **饥饿的消费者模型**：用集中式工作队列 + 多个独立消费者任务取代中央调度器，各消费者完成一项就回来抓下一项；适用时机：需要负载均衡、各组件处理速度不一的分布式/并发架构；怎么做：全异步请求 + 队列，使各组件在时间上解耦。
- **发布/订阅协议**：Publisher 追踪登记的 Subscriber，事件发生时逐个 notify；变体包括对等式、软件总线、广播式；适用时机：对象状态变化需通知多个未知数量的观察者时；怎么做：对象登记只接收所需事件，避免巨型 case 分发。
- **MVC（Model-View-Controller）**：模型与视图、控制器分离，模型对视图/控制器无直接了解；适用时机：同一数据需多种呈现（不限于 GUI——视图是对模型的解释，控制器是协调机制）；怎么做：定义模型抽象 + 多个视图订阅，甚至组成模型-查看器网络。
- **黑板系统**：知识消费者与生产者在共享空间中匿名、异步交换数据（read/write/take/notify，元组空间）；适用时机：数据到达次序不定、分布式采集、规则随新事实触发的复杂工作流（如抵押审批、语音识别）；怎么做：把事实与推断张贴到黑板，规则引擎订阅触发，按区域组织分区。

## Key Concepts
- **时间耦合**：方法调用次序上隐含的依赖（A 必须在 B 之前调用），使系统不灵活。
- **并发与次序**：时间的两个设计维度——事情同时发生，以及事情在时间中的相对位置。
- **响应集（response set）**：一个类各方法直接调用的函数总数；响应集越大越易出错。
- **物理解耦**：文件、目录与库之间的物理依赖；逻辑设计与物理设计必须协同进行，循环依赖极难挽回。
- **元数据**：关于应用如何运行、使用什么资源的数据；运行时而非编译时访问。
- **事件（event）**："刚发生了某件有趣的事"的消息，用于通知状态变化而不增加耦合。
- **UML 活动图 / 同步条**：捕捉工作流、找出可并行动作的表示法。
- **元组空间（tuple space）**：以键/值对 + 模板匹配存取对象的黑板式共享空间（Linda、JavaSpaces、TSpaces）。

## Mental Models
- 当发现改动会波及无关模块时，用"得墨忒耳法则"检查调用链是否越过了不该越过的对象。
- 当需求/政策常变时，用"元数据驱动"思考——问自己：这段是抽象还是细节？细节能移到代码外吗？
- 当用户逐次描述流程时，画活动图找"本来可以并行却没并行"的动作。
- 当多方以未知次序贡献信息时，用"侦探黑板"隐喻：各方互不知晓，只看板、贴事实。

## Anti-patterns
- **链式调用 a.getB().getC().doX()**：增大响应集，被触碰的第三方对象一变就全断。
- **只启动时读配置**：改配置必须重启应用；长期运行服务应支持热重载。
- **巨型 case/多路 if 分发事件**：要求发送者了解所有接收者，违反 DRY 与正交性。
- **构造器与初始化分离、依赖"还没人调用我"**：并发下对象可能在任意时刻被调用，必须始终处于有效状态。
- **像 strtok 那样隐藏内部静态状态**：非线程安全且有时序陷阱，接口应无"意外"。
- **渡渡鸟代码**：没有元数据的代码无法适应变化——不适应的物种会灭绝。

## Key Takeaways
1. 每写一个方法调用链，问：我是否在"穿过"别人的对象？改用委托或直接持有的组件。
2. 把业务规则、时间周期、UI 风格做成配置而非代码；细节越晚定越好、越"软"越好。
3. 用活动图分析工作流，最大化并发度；把组件设计成队列背后的独立服务。
4. 假设代码终将被并发调用：保护全局/静态状态，保证对象任何时刻都处于一致状态。
5. 用事件 + 发布/订阅解耦模型与视图；视图不必是 GUI，可组成模型-查看器网络。
6. 复杂、乱序、规则驱动的工作流优先考虑黑板 + 规则引擎，而不是硬编码工作流。
