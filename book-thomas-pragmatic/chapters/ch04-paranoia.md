# Chapter 4: 注重实效的偏执（Pragmatic Paranoia）
## Core Idea
完美的软件不存在，所以连自己也要防：用合约明确权利与责任，用断言验证"不可能"，用异常处理意外，用对称的配平管理资源——尽早让错误暴露。

## Frameworks Introduced
- **按合约设计（DBC，Design by Contract）**：例程合约 = 前条件（调用者必须保证，例程决不会被违规调用）+ 后条件（例程保证完成时的状态，禁止无限循环）+ 类不变项（返回调用者时必须为真）。适用时机：任何模块接口设计，尤其是继承体系（子类至少满足父类合约，可放宽输入、加强保证）。怎么做：在基类声明一次合约，让检查自动沿继承传递；语言不支持时用注释或预处理器（iContract/Nana）。
- **断言式编程**：对"这决不会发生"的每个念头加 assert 检查。怎么做：断言检查决不应发生的事（非错误处理）、条件不得有副作用、发布版保持开启、只关掉确实影响性能的那几个。
- **死程序不说谎 / 早崩溃**：无法存活的状态下尽快终止并留下现场（栈踪迹），比带病运行污染数据好。
- **资源配平（Balance Resources）**：分配资源的例程/对象负责释放；嵌套分配时以分配的相反次序释放、以相同次序申请（防死锁）；C++ 用栈对象/wrapper/auto_ptr，Java 用 finally；无法配平的动态结构用语义不变项明确归属，或引用计数。
- **循环不变项**：对循环目标的一般化陈述，循环前后及每次迭代后为真，作为微型合约证明结果有效。

## Key Concepts
- **前条件**：调用前必须为真的需求；违反不归被调方管，用户输入验证不属于它。
- **后条件**：例程承诺完成时的世界状态；必须会终止。
- **类不变项**：从调用者视角始终为真的条件；内部处理中可暂时破坏。
- **语义不变项**：不可违反的需求法则（如"出错时偏向消费者"，宁可不处理也不重复记账），须与易变的政策区分。
- **谁负责检查**：前条件由调用者在幕后检查通过后例程才可见参数——把保证输入正确的负担交还调用者。
- **异常 vs 错误返回**：文件该在而不在 → 异常；本来就可能不存在 → 错误返回。移走所有处理器程序仍能运行，说明异常被滥用了。
- **错误处理器**：登记后按错误类别回调的例程，可替代或配合异常（如包装 RMI 远程对象）。
- **配平检查**：用包装类追踪分配/释放，在主循环等稳态点断言资源量未增长。

## Mental Models
- 当别人可能对你不利时，用防御性驾驶——当写代码涉及他人输入时，用 DBC 连自己也不信任。
- 当发现自己在想"这不可能发生"时，用断言把它钉死。
- 当怀疑某错误是"异常情况"时，用"移走所有异常处理器它还工作吗"来检验。
- 当资源生命周期跨函数时，用"谁分配谁释放"或有始有终的封装对象。

## Anti-patterns
- **发布时关闭断言**：假定测试找全了 bug；实际等于不用保护网走钢丝。
- **断言中放有副作用的代码或必须执行的逻辑**：assert 可能被编译掉，副作用会改变程序行为。
- **把异常当正常控制流**：级联 goto、破坏封装、例程与调用者紧耦合，意大利面式代码。
- **错误处理淹没正常逻辑**：层层 if(ret != OK) 嵌套；应集中到一处。
- **跨函数共享资源句柄（全局 cFile 式耦合）**：条件分支跳过释放例程就会泄漏；分配与释放必须对称。
- **契约当成可选装饰**：不做这些陈述就回到靠巧合编程。

## Key Takeaways
1. 设计接口时先写下前条件、后条件、不变项——哪怕只写成注释，也迫使需求走到前台。
2. 前条件严格（对接受的东西挑剔），后条件保守（允诺的尽可能少）。
3. 发现"不可能"已发生时立即崩溃并留下现场，不要带着坏数据继续跑。
4. 断言开着交付；真有性能问题只关个别检查。
5. 异常只留给意外事件；可预期的失败用错误返回。
6. 资源分配与释放在同一处配平；多资源按相反次序释放、相同次序申请。
7. 定期检查长期运行程序的资源用量没有随循环增长。
