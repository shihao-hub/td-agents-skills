# Chapter 6: 当你编码时（While You Are Coding）

## Core Idea
编码不是机械地把设计翻译成代码——每一分钟都需要决策。不主动思考的代码是靠巧合运作的；要深思熟虑地编程、估算算法速率、持续重构、为测试而设计，并且绝不使用自己不理解的生成代码。

## Frameworks Introduced
- **靠巧合编程（的自我诊断）**：代码"能工作"但你不知道为什么；适用时机：任何"看起来能工作，最好别再动"的时刻；怎么做：区分实现的偶然（依赖未文档化的错误/边界条件）与语境的偶然（依赖环境、语言版本等无保证的前提），只依靠已文档化的行为，用自己的断言测试假定。
- **Big-O 估算**：用 O 表示法给算法的时间/内存设上限，忽略低阶项与常数系数；适用时机：写含循环或递归的代码时下意识核查；怎么做：常识判阶——顺序语句 O(1)、二分法 O(lg n)、单循环 O(n)、嵌套循环 O(m×n)、分而治之 O(n lg n)、排列组合 O(n!)；再用变化输入规模实测绘曲线验证。
- **重构（Fowler 法则）**：在不改变外部行为的前提下重新设计内部结构；适用时机：发现重复（DRY 违反）、非正交设计、过时知识、性能问题时——立刻做；怎么做：1) 重构不加功能；2) 先有良好测试并频繁运行；3) 小步前进、每步后测试；剧烈改动接口时让其老客户编译失败以便快速定位。
- **针对合约的单元测试**：单元测试 = 检验模块是否履行其合约（前条件、后条件、边界值）；适用时机：设计每个模块/例程时；怎么做：先测子组件合约，再测依赖它们的模块合约，失败即可聚焦问题层；测试代码放在易找处（模块内或专用子目录），兼作使用示例与回归基础。
- **测试装备（test harness）**：标准化测试基础设施；功能：setup/cleanup、选择个别或全部测试、输出比对、标准化故障报告、测试可任意深度组合（xUnit/JUnit 风格）。

## Key Concepts
- **实现的偶然**：仅因代码当前的写法才成立的行为，依赖未文档化的错误或边界条件。
- **语境的偶然**：依赖语言版本、环境、调用次序等无保证前提的巧合。
- **O 表示法**：对算法所需资源的上限近似，"阶为……"；缺点是看不出常数因子差异。
- **园艺隐喻**：软件更像园艺而非建筑工程——需不断修剪、移栽、拔草，即重构。
- **软件 IC**：组件应像芯片一样可组合，前提是每个组件都被设计为可测（BIST/TAM 的软件等价物）。
- **即兴测试**：调试中临时写的测试；调试结束时必须正式化并加入单元测试。
- **测试窗口**：部署后观察运行中系统内部状态的机制——规范日志、热键、内嵌 HTTP 调试面板。
- **向导代码**：向导生成的骨架代码，与你的功能逐行交织，成为"你的代码"——你不理解它就无法维护。

## Mental Models
- 当代码"看起来能工作"时，用"雷区士兵"模型：戳几下没炸不代表没有雷——先问"我为什么它能工作"。
- 当纠结两个算法时，用"数据规模 × 曲线形状"思考：输入从 1000 涨到 100 万会怎样。
- 当不想撕掉半能用的代码时，用"肿瘤"隐喻：现在切除小而便宜，等它扩散更贵更危险。
- 当测试感觉麻烦时，想"软件 IC"：芯片出厂前就带自检，组件拼接才有信心。

## Anti-patterns
- **"它现在能工作，最好别再画蛇添足"**：多余的调用只会更慢、更脆，且未文档化行为可能随库升级改变。
- **未验证的假定**：假定 X 是 Y 的原因却不证明——测试里充满虚假因果；不要假定，要证明（断言）。
- **以时间紧为由跳过重构**：现在欠的债以后要连本带利还，因为届时依赖更多、更难改。
- **随机输入测排序、小数据测性能**：理论与现实脱节——唯一作数的计时是真实环境中处理真实数据的速率。
- **把即兴测试随手扔掉**：出过问题的代码还会再出问题。
- **用 guru 设计的向导就自动成为 guru**：不理解向导代码 = 靠巧合编程，且向导是"单行道"。

## Key Takeaways
1. 每次代码"意外地"工作，停下来弄清原因；不能解释的能工作就是巧合，迟早炸。
2. 写下循环/递归时立刻估阶；不确定就变输入规模实测并画曲线，兼顾小 n 下简单算法可能更快。
3. 发现重复、不正交、知识过时、性能问题——立刻小步重构，每步有测试兜底。
4. 设计模块时同时设计其合约测试；测试放易找处，兼作文档与回归资产。
5. 调试结束把即兴测试正式化；建设测试文化——测试是技术，更是文化。
6. 用向导生成的代码逐行读懂才算你的；否则要么理解它，要么自己写。
