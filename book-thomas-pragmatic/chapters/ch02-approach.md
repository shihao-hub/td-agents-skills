# Chapter 2: 注重实效的途径 (A Pragmatic Approach)

## Core Idea
用 DRY 消除知识的重复、用正交性消除组件间的依赖，再配合可撤消性、曳光弹、原型、领域语言与估算，构建灵活、可变化、可估计的软件。

## Frameworks Introduced
- **DRY 原则**：系统中的每一项知识都必须具有单一、无歧义、权威的表示。适用时机：一切设计、编码、文档与流程——重复不止发生在代码里。怎么做：识别四类重复（强加的/无意的/无耐性的/开发者之间的），用代码生成器与元数据消除强加的，用规范化与计算字段消除无意的，靠纪律消除偷懒复制，靠论坛、资料管理员与代码复查消除人与人之间的。
- **正交性（Orthogonality）**：组件间互不依赖——改变其一不影响其他。适用时机：系统设计、团队划分、引入第三方库、编码与测试。怎么做：分层与自足组件；测试法——"显著改变某功能需求，多少模块受影响？"答案应为 1；编码上保持解耦（得墨忒耳法则）、避免全局数据与 Singleton、避免相似函数；团队正交性用"每次改动需涉及几人"衡量。
- **曳光弹开发（Tracer Bullets）**：先打通一条贯穿所有组件的端到端最小路径，再逐轮增量充实。适用时机：需求含糊、技术陌生、环境将变的新项目。怎么做：选一个最小用例，把 UI/逻辑/后端全部连起来跑通，向用户演示并调整准星；曳光代码是用过要保留的骨架，与"用过就扔的原型"相反。
- **原型制作（Prototyping）**：用可丢弃的便宜材料回答具体风险问题。适用时机：架构、新功能、外部数据、第三方组件、性能、UI 等有风险的点。怎么做：忽略正确性、完整性、健壮性、风格，只聚焦要回答的问题；明确告知所有人代码将丢弃，防其被误部署。
- **估算五步法（Estimating）**：理解提问内容 → 建立系统模型 → 分解组件 → 给参数赋值（抓主导参数）→ 计算，并用单位传达精确度（1–15 天用"天"，8–30 周用"月"）。适用时机：任何可行性判断与工期承诺。怎么做：先问语境要多准；优先借鉴做过类似事情的人；记录估算并复盘误差；进度只能靠增量开发、随代码迭代进度表。

## Key Concepts
- **DRY**：每项知识单一、无歧义、权威的表示；违反时可参数化、缓存但须把影响局部化（用访问器封装）。
- **正交性**：来自几何的不相依赖/解耦性；带来高生产率（M×N 组合）与低风险（改动局部化、易测试、不锁死供应商）。
- **可撤消性（Reversibility）**：把决策"写在沙滩上而非刻在石头上"，用抽象接口与元数据隔离数据库、架构、部署等关键选择。
- **领域语言（Domain Language）**：用应用领域的词汇、语法、语义编程的小型语言，分数据语言与命令语言、独立与嵌入式，可用 BNF + 解析器生成器实现。
- **强加的重复（Imposed Duplication）**：环境（多表示、文档与代码、语言限制）似乎迫使的重复，可用过滤器/生成器让转换成为主动的构建步骤来消除。
- **无意的重复（Inadvertent Duplication）**：设计失误导致冗余（如 Line 类的 length 可由 start/end 推出），应规范化设计。
- **启动杂役 → 催化剂**：跨团队无法启动时，先做出可见成果吸引参与（与 Ch1 石头汤同源）。

## Mental Models
- 当需求模糊、在黑暗中开发时，用曳光弹：先打一发能看见弹道的完整子弹，靠即时反馈修正，而非一次精确计算。
- 当要验证高风险的具体疑点时，用原型：轻木加胶带的汽车模型用来回答问题，不是用来上路。
- 当有人要求"永远确定"的技术决策时，用沙滩上的字：假设它会变，为其保留退路。
- 当拿不准系统是否正交时，用直升机反例：每个控制器都有次级效应、动一处要全身补偿，就是非正交的噩梦。

## Anti-patterns
- **无耐性重复**：复制相似代码、硬编码魔数图省事——省几秒，损失几小时（Y2K 惨败的根源之一）。
- **开发者之间的重复**：上万份各自为政的社会保障号验证代码；不交流、不复用，重复多年不被发现。
- **把关键决策刻在石头上**："你说过要用 XYZ 数据库！"——没有隔离第三方、没有可撤消设计，被迫全线重编码。
- **把原型当产品部署**：原型有欺骗性的完整外观，未声明"用完即扔"就会被出资人要求上线。
- **大爆炸式集成/一次性进度承诺**：真空里逐模块编码最后才拼装，或项目开始前就给出必须遵守的单一工期数字。
- **过度简单的领域语言**：如 sendmail 配置——易解析但晦涩难懂；应用可读性更好的语法，初期投入换长期维护收益。

## Key Takeaways
1. 写下任何知识前先问：它是否已有权威表示？能否由单一来源生成其余（schema→代码、文档→测试）？
2. 设计完组件做"改动影响数模块"测试，答案不是 1 就解耦——少用全局数据，让对象自己改状态。
3. 新项目先打通一条端到端曳光弹路径并让用户看到，再并行充实各组件。
4. 做原型前声明它是丢弃代码；曳光代码则相反，要写得能保留。
5. 留意你无法控制的事物的属性（电话号码当顾客标识符？），让关键选择可撤消、可配置。
6. 估算先问要多准确，用合适的单位报数；不确定就说"我等会儿回答你"。
7. 进度估算随每轮增量开发迭代提炼，不凭空猜迭代次数。
