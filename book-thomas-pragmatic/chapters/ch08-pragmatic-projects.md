# Chapter 8: 注重实效的项目（Pragmatic Projects）

## Core Idea
把个体的注重实效原则放大到项目级：团队按功能组织并保持一个声音，一切重复流程自动化，测试无情且自动，文档与代码同为模型的视图，成功以温和超出用户期望来衡量——最后为自己的作品签名。

## 提示清单（Tips）
- **提示 60：围绕功能、而不是工作职务进行组织**（Organize Around Functionality, Not Job Functions）
- **提示 61：不要使用手工流程**（Don't Use Manual Procedures）
- **提示 62：早测试，常测试，自动测试**（Test Early. Test Often. Test Automatically.）
- **提示 63：要到通过全部测试，编码才算完成**（Coding Ain't Done 'Til All the Tests Run）
- **提示 64：通过"蓄意破坏"测试你的测试**（Use Saboteurs to Test Your Testing）
- **提示 65：测试状态覆盖，而不是代码覆盖**（Test State Coverage, Not Code Coverage）
- **提示 66：一个 bug 只抓一次**（Find Bugs Once）
- **提示 67：把英语当作又一种编程语言**（Treat English as Just Another Programming Language）
- **提示 68：把文档建在里面，不要拴在外面**（Build Documentation In, Don't Bolt It On）
- **提示 69：温和地超出用户的期望**（Gently Exceed Your Users' Expectations）
- **提示 70：在你的作品上签名**（Sign Your Work）

## Frameworks Introduced
- **按功能组织团队**：小团队各自负责最终系统的一块内聚功能（可以是数据库层、帮助子系统），内部按能力自组织，团队间以承诺互相负责；配行政主管做大使/资源调度/交叉检查正交性。适用时机：组建或重组开发团队；怎么做：套用组织代码的同一套技术（合约、解耦、正交性）来组织人。
- **自动化层级**：编译→生成代码→回归测试→夜间完整构建（签出、标注版本、产生分发映像、make test）→最终构建（make final，须重测全部）→内容驱动的网站生成与批准流程（如源码内 *Status: needs_review* 标记）。适用时机：任何重复出现的项目活动；怎么做：shell/make/cron/Perl，脚本入源码控制，无人照管运行。
- **无情测试的矩阵**：测什么（单元/集成/验证校验/资源耗尽与恢复/性能/可用性）× 怎样测（回归、现实+合成数据、解耦 GUI 与逻辑、破坏员、覆盖分析）× 何时测（签入前、随构建、定期计划）。适用时机：项目级测试策略；怎么做：发现逃逸的 bug 立即补一个自动化测试，从此每次都抓它。
- **可执行文档/模型-视图文档法**：选定权威信息源（模型），文档、schema、API 文档、打印/网页/幻灯片都作为自动生成的视图。适用时机：同一信息出现在代码、规范、手册多处；怎么做：纯文本+标记语言，从模型导出各视图，随构建自动更新。

## Key Concepts
- **首席水情监测员（chief water tester）**：持续监视范围扩大、缩水的时间表、新特性等环境渐变的指定角色。
- **项目品牌**：给项目取名+标识，让团队对外一个声音、有身份感（对外统一，对内鼓励热烈辩论）。
- **资料管理员/工具构建员**：协调文档代码仓库、发现重复；构建使苦差自动化的工具。
- **回归测试**：与已知值对比，确保今天的修复没破坏昨天能工作的代码。
- **状态覆盖 vs 代码覆盖**：执行过每行 ≠ 覆盖程序所有可能状态（两参数函数即百万状态）。
- **Stroop 效应**：误导性命名（getData 其实写盘）让大脑持续混淆——命名即文档。
- **注释写"为何"**：代码已说明"怎样"；注释记录权衡、被弃方案；变更历史归源码控制。
- **管理期望 → 共享期望**：不是居高临下地控制用户希望，而是共同理解；曳光弹与原型是载体。

## Mental Models
- 当流程第二次以相同方式执行时，用"转动钥匙的自动启动器"模型把它自动化。
- 当测试策略被质疑时，用"捕鱼网"模型：单元网抓小鱼，集成网抓鲨鱼，逃走的要补网。
- 当评估项目成败时，用"创纪录利润股价仍跌"模型：成功存在于旁观者（出资人）眼中。
- 当交付临近时，用"廉价洋娃娃"模型：用户对交付物早有感情投入，忽视它注定失败。

## Anti-patterns
- **质量官员制**：把质量责任委派给一个人；质量只能来自全员贡献。
- **煮青蛙团队**：默认"别人在处理""领导一定批准了"，对重大改动集体健忘。
- **递归 make 的隐式依赖**：单次调用看不到跨调用依赖，易漏编译或做无用功。
- **误导人的文档**：网站上过时信息比没有信息更糟；文档只是快照，应在线+日期戳。
- **"管理期望"式居高临下**：控制而非协作，失去信任。
- **地盘意识/匿名代码**：签名变成采邑与借口；应以所有权自豪+尊重他人代码来平衡。

## Key Takeaways
1. 团队不留破窗户，围绕功能分组并设两道检查找出团队间降低正交性的交叉。
2. 构建必须一条命令从空目录到分发映像；夜间完整构建跑全部测试。
3. 签入前跑测试；测试失败=编码未完成；bug 被抓到一次就写进永久自动化测试。
4. 用破坏员故意引入 bug 验证测试网有效；追求状态覆盖而非行覆盖。
5. DRY 应用到文档：单一权威模型，导出 API 文档、网页、手册等多种视图并自动发布。
6. 温和地超出期望：工具提示、快捷键、安装器等低成本高好感特性，但不破坏系统。
7. 在作品上签名：签名是质量的保证，前提是黄金法则与相互尊重。
