# Chapter 7: 在项目开始之前（Before the Project）

## Core Idea
项目开工前的关键工作——需求、解题、时机、规范与方法学选择——全部是"挖掘"而非"收集"：真实需求深埋在假定与政治之下，真正的约束需要被识别而非想象；同时不要让任何方法论或过细的规范取代你自己的批判性判断。

- **提示 59：昂贵的工具不一定能制作出更好的设计**（Expensive Tools Do Not Produce Better Designs）

## Frameworks Introduced
- **Cockburn 用例模板**：目标驱动的用例记录，含特征信息（目标/范围/级别/前后条件/参与方/触发）、主要成功情境、扩展、变更、相关信息（优先级/履行指标/频度）、进度表、未决问题。适用时机：与用户共同捕捉需求时；怎么做：用模板作备忘录与会谈议程，捕获非功能需求与异常，支持层次嵌套与交叉链接。
- **"找到盒子"解题法**：列出所有可能途径（再荒谬也不排除），逐项论证为何不可行，把约束分类排序，先在最严格的约束下求解。适用时机：看似不可能解决的谜题；怎么做：先问"有更容易的方法吗？这真的是问题吗？必须这样做吗？必须做吗？"
- **原型驱动的启动检查**：用概念验证原型来检验启动疑虑。适用时机：反复感到勉强却分不清是拖延还是直觉；怎么做：很快感到无聊→只是拖延，放弃原型直接开发；原型暴露出前提错误→直觉是对的，及时止损。

## Key Concepts
- **需求 vs 政策 vs 实现**：需求是语义不变项（"只有得到授权的用户可以访问"），政策是会变的当前做法（应文档化并超链接），实现（列表框）只有在用户坚持时才是需求。
- **规定过度（over specification）**：好需求文档保持抽象；需求不是架构、不是设计、也不是用户界面。
- **需求蔓延（requirement creep）**：靠度量追踪每项新特性及其对进度的影响来遏制。
- **项目词汇表（project glossary）**：全项目统一专用术语，避免同名异义/异名同义。
- **真正的约束 vs 先入之见**：解难题的关键是区分二者，绝对约束必须尊重，表象约束要挑战。
- **规范螺旋（specification spiral）**：在规范上再叠规范、回报递减甚至为负，迟迟不肯编码。
- **紧身衣效应**：不留解释余地的设计剥夺了开发者在编码中发现机会的技艺空间。
- **有时接口就是系统**：成功的工具要适应使用者的双手（Brian Eno 的混音台反例）。

## Mental Models
- 当用户描述"怎么做"时，用"需求之坑"思维追问"为什么"，挖出底层商业需要。
- 当问题看似无解时，用"戈尔迪斯结"思维重述需求，让问题本身消失。
- 当启动新模块犹豫不决时，用"跳水运动员"直觉模型：疑虑反复出现就先建原型验证。

## Anti-patterns
- **把用户界面陈述当需求**：会导致硬编码政策，政策一变就得改代码。
- **Y2K 式短视**：重复当时的商业实践（两位年份）且违反 DRY，没有建 DATE 抽象。
- **两英寸厚的需求文件夹**：无人阅读、墨迹未干即过时；应发布为超文本 Web 文档。
- **方法学漂流**：像海难者不断抓住最新时尚；工具产出不因其昂贵而更可信。
- **匿名地"翻译"需求**：形式方法的图只是设计者自己的解释，用户并未真正检查。

## Key Takeaways
1. 挖需求：找出用户"为何"做某事，把政策与需求分开存放，用元数据实现授权类需求。
2. 花几天成为用户（接支持电话、蹲交易所），既获得洞见又建立信任。
3. 维护 Web 化的项目词汇表与超文本需求文档，出资人看高层、开发者可下钻。
4. 新特性必须报告其对进度的影响，用度量揭示"只是再加一个"已是本月第 15 个。
5. 解不开时先找盒子：列全途径、论证排除理由、先满足最严格约束。
6. 规范写到能交接即可，回报递减就停；用原型和曳光弹代替更多层规范。
7. 批判地吸收各方法学的精华，融成自己持续改善的工作习惯——你是主人。
