# 速查表（Cheatsheet）— 作者的判断规则

## 决策规则（When X → do Y, because Z）

| 情形 | 做法 | 因为 |
|---|---|---|
| 看到烂设计/坏代码（破窗户） | 立即修，或隔离到"加窗"待办 | 第一扇不修，团队心理上放弃质量 |
| 想推动团队改变 | 自己先做出示范（石头汤） | 展示价值比说服有效 |
| 需求模糊 + 技术新颖 | 打曳光弹：最薄端到端通路 | 每发校准方向，胜过纸上弹道 |
| 拿不准某方案可行性 | 做一次性原型回答具体问题 | 便宜地消除风险；但绝不进生产 |
| 同一段知识出现两次 | 判定巧合重复 vs 实现强加；前者消除（DRY） | 重复必然失同步腐化 |
| 设计模块 | 追问：改这个需求要动几个文件？ | 正交性是解耦的度量 |
| 写函数 | 声明前置/后置条件+不变式（合约） | 错误早暴露，接口自文档 |
| 错误不可恢复 | 早崩溃并留诊断信息 | 死程序不说谎，别污染数据 |
| 链式调用 a.b().c().d() | 重构为只与直接朋友对话 | 得墨忒耳法则，降低耦合 |
| 行为因环境而异 | 配置化：细节进元数据 | 换行为不发版 |
| 代码"能跑"但不知为何 | 停下来搞懂，否则不交付 | 不要靠巧合编程 |
| 发现坏味道/过时设计 | 早重构、常重构，小步+测试 | 拖延即付利息 |
| 修好一个 bug | 立刻写回归测试 | 一个 bug 只抓一次 |
| 任何手工流程做第二遍 | 自动化它 | 手工必漂移、不可重复 |
| 用户提"需求" | 追问为什么，挖真需求 | 嘴上说的是方案不是需求 |
| 要承诺进度 | 给校准过的估算区间并随代码迭代 | 点承诺制造意外 |

## 快速判定（Tells & Smells）

- **有人接了烫手任务就沉默** → 破窗户效应已开始，先修环境再谈士气
- **同一逻辑在两处手工同步** → DRY 违规
- **改一处要全量回归** → 非正交，按合约+解耦切
- **日志里吞掉的异常** → 假装它不会发生；改为断言或早崩溃
- **"先跑起来再说，反正没崩"** → 巧合编程
- **测试通过率 100% 但没人敢改代码** → 只有代码覆盖没有状态覆盖
- **文档和代码对不上** → 文档拴在外面了；建进 CI
- **承诺 3 个月实际 6 个月** → 没有迭代估算（Tip 19）

## 阈值与默认

- 知识组合：**每年 ≥1 门新语言，每季度 ≥1 本技术书**
- 估算单位校准：能承诺的粒度 = 15 天内"天"，再大用"周/月"并声明误差
- 断言：开发期全开；性能关键路径生产可关，但不变式破坏必须 fail fast
- 重构时机：见到就动手（趁早），不等"以后统一大扫除"

## 一页版：70 条提示分类速览

- **态度（1-9）**：关心技艺 / 不找借口 / 修破窗户 / 做催化剂 / 记住大图景 / 够好即可 / 定期投资知识 / 批判分析
- **沟通（10）**：说什么和怎么说同样重要
- **设计与实现（11-19）**：DRY / 易复用 / 正交 / 无最终决策 / 曳光弹 / 原型 / 领域语言 / 估算 / 迭代进度
- **工具（20-29）**：纯文本 / shell / 编辑器 / 源码控制 / 修问题不指责 / 别恐慌 / 怀疑自己 / 文本操纵语言 / 元编程
- **防御（30-35）**：不完美 / 合约 / 早崩溃 / 断言 / 异常只用于异常 / 有始有终
- **柔性架构（36-43）**：最少耦合 / 配置不集成 / 元数据 / 并发分析 / 服务化 / 并发设计 / MVC / 黑板
- **编码时（44-50）**：不靠巧合 / 算法阶 / 测估算 / 重构 / 为测试设计 / 无情测试 / 别用不理解的向导代码
- **项目前（51-59）**：挖需求 / 像用户思考 / 抽象长寿 / 词汇表 / 找到盒子 / 准备好才开始 / 做胜于描述 / 别做形式方法奴隶 / 工具≠设计
- **项目（60-70）**：自动化 / 早常自动测试 / 状态覆盖 / bug 只抓一次 / 英语也是编程语言 / 文档内置 / 温和超期望 / 签名
