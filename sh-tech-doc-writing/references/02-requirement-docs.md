# 需求分析文档 与 需求设计（PRD）

## 两者的区别（先分清，别混写）

- **需求分析**：我们要解决什么问题（Why / What）。对象是**问题空间**。产出给产品、研发、测试对齐用。
- **需求设计（PRD）**：做成什么样、什么算成功（产品形态层面）。对象是**解决方案的用户视图**。产出给全团队执行用。
- 常见错误：PRD 里出现表结构和接口设计（那是技术方案的事）；需求分析里直接跳到怎么做（那是越层）。

## 一、需求分析文档

国际标准是 ISO/IEC/IEEE 29148（前身 IEEE 830 的 SRS）。日常不必套全套标准八股，推荐精简骨架：

```
# XX 需求分析
1. 背景与问题
   现状是什么、痛点是什么、为什么现在做（不做的代价）
2. 目标与非目标
   目标要可衡量；非目标 = 看起来该做但明确不做的（防止范围蔓延）
3. 用户与场景
   谁在什么场景下使用（用户故事，见下）
4. 功能需求
   用户故事列表 + 每条的验收标准（Given/When/Then）
5. 非功能需求
   性能 / 容量 / 时效 / 安全 / 合规——必须量化
6. 依赖与约束
   上下游依赖、技术约束、资源约束
7. 待确认问题
   模糊点、争议点，标注影响面，留给评审拍板
```

### 用户故事写法

格式：**作为〈谁〉，我想要〈什么〉，以便〈价值〉。**

质量自检用 INVEST 原则：Independent（独立）、Negotiable（可协商）、Valuable（有价值）、Estimable（可估算）、Small（足够小）、Testable（可测试）。

验收标准用 Given/When/Then：

> **故事**：作为投放优化师，我想要批量导入达人邮箱，以便快速发起账号匹配。
> **验收**：Given 上传含 1000 行邮箱的 Excel，When 点击导入，Then 系统在 10 分钟内完成解析并返回逐行结果（成功/失败原因），失败行可下载错误报告。

### 非功能需求必须量化

| 模糊写法 ❌ | 量化写法 ✅ |
|-----------|-----------|
| 支持大量数据 | 日增 50 万行，单表年增长 < 2 亿行 |
| 响应要快 | 列表查询 P99 < 500ms |
| 尽快出结果 | 匹配任务 30 分钟内完成 90% |

## 二、需求设计（PRD）

### 经典方法：Amazon PR/FAQ（逆向工作法）

适合**新产品、新方向、价值不明的项目**。做法：先写出产品上线当天的「新闻稿」，再倒推现在要做什么。它强制你从最终受益者视角描述成果——和「读者视角」是同一个思想。

PR（新闻稿）结构：标题 → 副标题 → 导语 → 问题 → 解决方案 → 负责人引言 → 用户如何开始 → 用户引言 → 行动号召。

FAQ 部分：把所有利益相关方会挑战的问题提前自问自答（配额够吗？合规吗？和现有 X 什么关系？）。

### 常规迭代型 PRD 骨架

适合成熟产品的功能迭代：

```
# XX PRD
0. 变更记录（日期 / 人 / 改了什么）
1. 背景与目标（目标带可衡量指标：导入耗时从 2 天降到 10 分钟）
2. 用户故事与优先级（P0 必须有 / P1 应该有 / P2 可以有）
3. 功能详述（按模块；交互流程用图；边界场景必写）
4. 边界与异常场景
   超预期输入（100 万行的文件？格式错的？）、权限、空态、并发操作
5. 非功能需求（量化）
6. 数据埋点与成功指标（上线后怎么验证目标达成）
7. 依赖与排期要求（期望上线时间、强依赖项）
8. 待确认问题
```

### PRD 常见错误

- 只写正常流，不写边界与异常（空态？传错文件？没权限？）——研发和测试会来回问你。
- 需求和实现混写（出现表结构、接口路径）。
- 没有优先级，或全是 P0——等于没有优先级。
- 目标不可衡量（「提升体验」），上线后无法验证成败。
- 埋点缺失，做完不知道效果。
