# 排期设计与里程碑设计

## 一、排期：WBS（工作分解结构）

核心原则：**先分解，后估算**。拍一个总数再倒着凑，是延期的主要来源。

### 分解标准

- 叶子任务 = 可独立验收的工作包，粒度 **1–3 天**。
- **100% 原则**：WBS 必须覆盖全部工作——联调、测试、灰度、文档、上线演练都要有，漏项 = 必然延期。
- 每个任务标依赖，**外部依赖**（等第三方接口、等评审、等资源）单独高亮——这是延期主因，要在排期表里显式存在。

### 估算

- 每个任务三段估时：**开发 + 联调 + 测试**。只估开发是最常见的坑。
- 不确定的任务用三点估算：(乐观 + 4×正常 + 悲观) / 6。
- 整体排期加 15–20% buffer，并标注 buffer 用途（集成风险/需求变更），不要藏在每个任务里。

### 排期表模板

| 模块 | 任务 | 负责人 | 开发 | 联调 | 测试 | 依赖 | 日期区间 |
|------|------|--------|------|------|------|------|---------|
| 素材采集 | 抓取 Worker + 重试队列 | 后端A | 5d | 2d | 2d | 平台 API 权限 ⚠️外部 | 9/1–9/9 |
| URL 校验 | 规则引擎 + 校验 API | 后端B | 3d | 1d | 1d | — | 9/1–9/5 |
| track 打点 | 链接生成 + 打点接收 | 后端A | 3d | 1d | 1d | URL 校验完成 | 9/10–9/15 |

时间线呈现：WBS 管「做什么」，甘特图管「什么时候」——排期表 + 一张简单时间线图（飞书 mermaid gantt 支持）即可，不必上重型工具。

## 二、里程碑：可验收的交付物，不是日历事件

**定义：里程碑 = 时间 + 可验证的交付物 + 验收标准。**

| 写法 | 评价 |
|------|------|
| M1（9/15）：完成开发阶段 ❌ | 无法验收，形同虚设，「完成」由谁说了算？ |
| M1（9/15）：采集链路跑通——可从 URL 导入 1000 条素材，后台可查询、可导出 ✅ | 能 demo、能验证、能宣布完成 |

### 里程碑对应架构演进的稳定状态

每个里程碑应该是系统的一个「可用状态」，而不是「工作量完成了百分之 X」：

```
M1 单机链路跑通（功能闭环：能导入、能查询）
M2 全量接入 + 监控告警（可观测：出问题能知道）
M3 灰度 + 容灾演练（可上线：出问题能恢复）
```

### 验收标准写法

验收标准要能被第三方核验：能 demo / 查询到指定数据 / 监控面板可用 / 回滚演练通过 / 压测报告达标。

### 里程碑表模板

| 里程碑 | 时间 | 交付物 | 验收标准 | 依赖 |
|--------|------|--------|---------|------|
| M1 | 9/15 | 采集+校验链路 | URL 导入 1000 条素材成功并可在后台查询 | API 权限到位 |
| M2 | 9/30 | 全量 + 监控 | 打点链路端到端核对误差 < 1%；告警接入值班 | M1 |
| M3 | 10/15 | 灰度上线 | 10% 流量灰度 3 天无 P2 以上故障；回滚演练通过 | M2 |

## 三、常见坑（每条都来自真实延期案例）

- **排期不含联调测试** → 必然延期，三段估时是底线。
- **任务粒度太粗**（「后端开发 15 天」）→ 无法跟踪进度，风险暴露太晚。
- **里程碑没有验收标准** → 永远「快完成了」，无法宣布完成也无法暴露延期。
- **外部依赖不标注** → 卡住了才发现，提前一周暴露就能提前一周解决。
- **全串行排布** → 可并行的不并行，人力闲着等上游。
- **老板要压缩排期** → 砍范围（先上 P0 功能），不砍测试；范围可以换时间，质量不能换。
