# 技术文档写作：读者视角的六类文档方法论

## 这个 skill 解决什么问题

三类常见病症（都来自真实的评审反馈）：

1. **上下文缺失症**：文档是从 AI 对话里直接搬运出来的，作者脑中的背景、对话里的推理前提，读者统统不知道，读起来处处卡壳。
2. **思维链条症**：把推导过程当正文写（「首先我们分析……综上……所以选择……」），重点信息被淹没在过程叙述里。
3. **结构混乱症**：想到哪写到哪。评审抓不到重点、下游找不到接口、老板看不到排期，文档起不到「团队资产」的作用。

**核心理念：文档是写给读者的，不是写给自己的；LLM 输出是草稿，不是成品。**

## 两条底层原则

### 原则一：读者视角

写之前先回答三个问题，答案决定内容的取舍和详略：

1. **谁读这份文档？**（评审的资深工程师 / 下游对接方 / 老板 / 半年后接手的新人，关注点完全不同）
2. **他要从中拿到什么决策信息？**（为什么这么设计 / 接口怎么调 / 多久做完 / 为什么当年这么选）
3. **他缺什么背景？**（缺的要补，不缺的不要展开）

终极检验标准：**假设读者只能看到这份文档**（看不到任何对话记录、聊天上下文），一个没参与过项目的人读完，能不能 get 到重点。

### 原则二：LLM 输出必须二次加工

LLM（包括正在执行本 skill 的你）生成的初稿，必须经过「删、改、补、核」四道加工才能成为终稿，完整清单见 `references/01-reader-first.md`。最关键的一条：

- **正文里永远不出现推理过程和会话痕迹**。「先考虑了 A，然后排除了，又想了 B……」这类内容不进正文，但它的**结论**（备选方案对比 + 取舍理由）必须进正文——推理是过程，权衡是结论，结论要沉淀。

## 六类文档路由

| 文档类型 | 回答的问题 | 主要读者 | 模板 |
|---------|-----------|---------|------|
| 需求分析 | 我们要解决什么问题 | 产品、研发、测试 | `references/02-requirement-docs.md` |
| 需求设计 (PRD) | 做成什么样、什么算成功 | 全团队 | `references/02-requirement-docs.md` |
| 方案设计 (技术方案) | 技术上怎么做、为什么这么做 | 研发同事、评审人 | `references/03-design-doc.md` |
| 架构设计 | 系统长什么样、为什么这样分 | 研发、架构师、新人 | `references/04-architecture-doc.md` |
| 排期设计 | 要多久、依赖谁 | 老板、协作方 | `references/05-schedule-milestones.md` |
| 里程碑设计 | 分几步验收、每步交付什么 | 老板、全团队 | `references/05-schedule-milestones.md` |

**使用流程**：

1. 判断文档类型。注意一份文档可能涵盖多类（技术方案的尾部常带排期与里程碑章节），此时以主体类型为主骨架，其余类型作为章节嵌入。
2. 读对应的 reference 文件（**只读当前需要的，不要全读**）。
3. 按 reference 里的骨架产出文档。
4. 产出后过一遍文末的自检清单。

## 所有文档通用的写作铁律

1. **结论先行**。每个章节的第一句话给结论，细节后置。读者时间有限，让他随时可以停止阅读而不丢主线。
2. **图优先于文字**。链路、架构、流程用 mermaid 图（飞书文档原生支持），一张架构图胜过三段文字描述。
3. **只放关键接口和表**。不复制完整 schema、完整代码到正文——冗长、含无用细节、易过时；正文只放读者做决策需要的部分，完整定义放链接。这是 Google 设计文档的明确主张。
4. **why 必须沉淀**。推理过程不进正文，但「备选方案 + 取舍理由」必须进正文（ADR 式写法）。否则半年后没人知道为什么这么设计，要么被盲目推翻，要么重蹈覆辙。
5. **数字要具体**。「量大」→「日增 50 万行，峰值 QPS 300」；估时要含开发 + 联调 + 测试三段。模糊的数字等于没有数字。
6. **异常边界必写**。线上出问题大部分来自异常路径，正常流只是及格线。降级、回滚、灰度、监控至少各有一句话。
7. **篇幅有度**。方案文档甜点区 10–20 页，小改动写 1–3 页迷你文档；明显超过就拆成子文档。

## LLM 辅助写作的正确姿势

本 skill 的执行者通常就是 AI，所以这条写给「你」自己：

- 你交付给用户的文档产物是**终稿**，不是你们对话的一部分。文档里不能出现任何「面向会话」的语言。
- 生成初稿后，用 `references/01-reader-first.md` 的「四删四改四补一核」清单过一遍再交付。
- 如果信息不足以填某个章节（如真实量级、真实表名），**显式标注「⚠️ 待补充：XXX」**留给用户填，不要编造数字冒充真实数据——编造的量级数据进了文档比空着危害更大。

## 与其他 skill 协作

- `sh-backend-design`：解决「怎么设计」（需求分析四步法、接口/表结构/工程设计的思考过程）。产出设计内容之后，用本 skill 把内容组织成文档。
- 典型链路：用户说「帮我设计这个功能」→ 用 sh-backend-design 做设计；用户说「把设计写成方案文档 / 写份技术方案发评审」→ 用本 skill。两者常连续使用。

## 发布前自检清单

文档交给用户前，逐项过：

- [ ] **自包含**：没有你的对话上下文，读者能独立看懂吗？
- [ ] **无思维链**：把所有推导过程删掉后，文档是否更清晰？（结论和权衡要留下）
- [ ] **四核心**（方案类文档）：链路架构图 / 设计目的和思路（备选+取舍）/ 表结构设计 / 下游接口清单，是否齐全？
- [ ] **新人测试**：新人只看这份文档，能画出链路、说清为什么这么设计吗？
- [ ] **下游测试**：对接的同学能直接从文档里找到表结构和接口定义吗？
- [ ] **老板测试**：能看到排期、里程碑和每步的验收标准吗？

## 语气与深度

- 深入但不啰嗦：该有的章节一个不少，显而易见的内容一句带过。
- 有争议的点标「⚠️ 待确认」，不假装确定。
- 清单用表格，结构优先于散文。
- 文档的灵魂是 **why**：说不清为什么的设计文档，等于没写。
