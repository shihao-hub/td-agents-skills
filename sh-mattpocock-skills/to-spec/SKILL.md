# To Spec: 目的地文档与测试接缝合成

> **反 specs-to-code 铁律（Matt Pocock）**：  
> 用规格书生成代码、出问题改规格书而不改代码，等同于放弃代码所有权的 vibe coding。Matt 的亲身经历是：第一版还行，第二版变差，第三版全是垃圾。  
> **规格书是目的地地图，不是编程语言！**  
> **只写三件事：完成时世界长什么样、怎么算验收通过、明确不做什么。不写具体实现细节——写了就滑向 specs-to-code。**

---

## 一、执行原则：无二次采访，直接合成

本技能直接以当前对话中 **[`grilling`](../grilling/SKILL.md)** 达成的设计共识与 **[`domain-modeling`](../domain-modeling/SKILL.md)** 沉淀的领域模型为输入：
- **严禁重新采访用户**：所有的业务分支与决断已在前序审问中结算，此处纯粹负责高密度合成；
- **使用项目通用语言**：严格使用 `CONTEXT.md` / `GLOSSARY.md` 中的标准术语；
- **显式界定测试接缝（Seams）**：找到最高且唯一的公共接口边界（Seam），后续所有测试只能在接缝上验证行为，绝不可面向内部细节写测试。

---

## 二、目的地文档标准模板（Destination Spec Template）

合成的规范应落盘至项目的标准规范路径（如 `.scratch/specs/<slug>.md` 或 `docs/specs/<slug>.md`），或发布到 Issue 追踪器：

```markdown
# Spec: <功能/需求标题>

## 1. 目标世界长什么样 (The Destination)
从终端用户或调用方的视角，用高度凝练的语言描述：当这个功能完工时，外部世界发生了什么可感知的改变？核心价值是什么？

## 2. 怎么算验收通过 (Acceptance Criteria & User Stories)
详尽、按序号排列的用户故事与验收断言：
1. **[场景/角色]**：当执行 X 时，应当观察到 Y，且不会破坏 Z。
2. **[关键路径]**：...
3. **[边界与异常]**：输入非法或服务受挫时，应当以规范契约抛出...

## 3. 测试接缝 (Testing Seams)
- **确定的测试接缝 (The Seam)**: `<指出最高级别的公开接口/服务入口>`
- **接缝理由**: 为什么选择该接缝作为唯一的公共观察点？
- **测试原则**: 测试只在此接缝处注入输入并捕获输出，严禁跨入私有逻辑或 mock 内部细节。

## 4. 明确不做什么 (Out of Scope)
画清边界，列出当前阶段明确不做、延迟考虑或故意排除的内容，防止范围蔓延。

## 5. 架构决策与环境依赖 (Architectural Invariants)
仅记录已 settled 的关键架构契约（引用的 ADR、数据模型变更方向），**严禁在此罗列具体的文件修改细节或脆弱的代码片段**（具体实现交由垂直切片去推敲）。
```
