# Cheatsheet — 重构决策速查（Fowler 2nd ed.）

## 决策规则

- **想加功能却觉得"得先改结构才好加"→ 立即做预备性重构**，把代码改到"加这个功能只需一小步"，再戴另一顶帽子加功能。(Ch 2)
- **同一逻辑第三次复制 → 必须重构**（三次法则）。(Ch 2)
- **提交前问自己：这次 diff 同时含有行为变化和结构变化？→ 拆开。**（两顶帽子，一次只戴一顶）(Ch 2)
- **没有测试兜底 → 先补特征测试，再重构。** 大的重构没有自测试代码等于走钢丝不系绳。(Ch 4)
- **看不懂一段代码 → 先提炼函数/改名，再读。** 写代码时让读者（三个月后的你）读懂，而非让作者写得爽。(Ch 6)
- **需要注释才能说清的代码块 → 提炼函数，函数名当注释用。** 注释只剩"为什么"该留。(Ch 3, Ch 6)
- **想在函数参数里传布尔开关 → 移除标记参数，拆成两个函数。**(Ch 11)
- **一个函数既返回值又有副作用 → 查询与修改分离，立刻做。**(Ch 11)
- **条件逻辑只在一处分叉 → 留着；同样的分叉散落多处 → 以多态取代条件表达式。**(Ch 10)
- **嵌套 if 超过一层 → 卫语句反转条件、提前退出。**(Ch 10)
- **看到 null 检查散落多处 → 引入特例（Null Object）。**(Ch 10)
- **函数依赖别的类的数据多过自家的 → 搬移函数到数据处（Feature Envy 判据）。**(Ch 8)
- **几个参数总是一起出现 → 引入参数对象。**(Ch 6)
- **字段可从其他字段算出 → 以查询取代派生变量**；性能有问题先 profiler 再说。(Ch 9)
- **类的大部分函数只是转发 → 移除中间人**；反过来客户端被迫了解委托链 → 隐藏委托关系。这是随上下文摇摆的拉锯。(Ch 7)
- **继承开始变痛（子类组合爆炸/子类依赖超类实现）→ 以委托取代子类/超类。**(Ch 12)
- **能用 IDE 自动重构的手法，别手改**（改名、搬移、提炼尤其如此）——工具保证原子性与正确性。(Ch 2)

## 坏味道 → 先看哪（快速诊断）

| 你看到… | 最可能是 | 先做 |
|---|---|---|
| 名字读不懂 | 神秘命名 | 改名 |
| 同一段结构多处出现 | 重复代码 | 提炼函数/提炼类 |
| 函数超过一屏 | 过长函数 | 提炼函数、拆分阶段 |
| 一个类总被多个不相关需求改动 | 发散式变化 | 提炼类（按变化方向） |
| 小改动要跳五六个文件 | 霰弹式修改 | 搬移函数/字段使其集中 |
| 到处传裸 map/JSON | 缺封装/基本类型偏执 | 封装记录、以对象取代基本类型 |
| switch/if 按同一类型码分叉多处 | 类型驱动分叉 | 以多态取代条件表达式 |
| 字段只在某些时刻有值 | 临时字段 | 提炼类、引入特例 |
| 子类拒绝继承的东西 | 被拒绝的遗赠 | 下移、以委托取代超类 |
| 注释在解释一段代码 | 隐藏的提炼点 | 先提炼函数，再决定注释去留 |

完整 24 味道 → 手法映射见 [ch03 Reference Tables](chapters/ch03-code-smells.md) 与 [ch12](chapters/ch12-dealing-with-inheritance.md)。

## 重构手法通用五步（每个手法的安全骨架）

1. 确认有测试兜底（没有先补）。
2. 小步走：每步编译通过、可提交。
3. 用编译器/IDE 找调用点，逐点迁移。
4. 每步跑测试，绿了再下一步。
5. 外部 API 用"旧签名转发新实现"的渐进迁移，最后删旧。

## 阈值与默认值（Fowler 的经验数）

- 函数长度：不设硬性数字，"代码块 + 意图差距"即提炼点；短到几行完全正常。
- 一个小改动需要修改的类数量：超过 1 个就开始警惕霰弹式修改。
- 复制粘贴容忍度：3 次。
- 性能：先写清晰代码 → profiler 找热点 → 只优化热点；平均 90% 时间花在 ~10% 代码上。(Ch 2)

## 明确不要做（反模式）

- ❌ 一次提交里既改结构又改行为（违反两顶帽子）。
- ❌ 为了重构而重构、追求"完美设计"——重构服务 upcoming 的修改需求（YAGNI）。(Ch 2)
- ❌ 无测试的大手术；❌ 依赖"我很小心"代替小步验证。
- ❌ 单一职责的项目里强行上继承/多态——先问分叉是否散落多处。(Ch 10, Ch 12)
- ❌ 拿"架构重构"当借口做没有结构目标的大搬家（译者序所称"刀劈斧砍"）。
