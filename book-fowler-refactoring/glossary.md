# Glossary —《重构：改善既有代码的设计（第2版）》

按字母排序；`（Ch N）`为覆盖章节。

- **两顶帽子（Two Hats）** — 同一时段只戴一顶：加功能时不重构，重构时不加功能；两件事绝不混在一次提交里。(Ch 2)
- **大卫·帕纳斯封装（信息隐藏）** — 模块边界的设计原则：按"变化方向被隐藏"来组织代码，是封装章节的理论根基。(Ch 7, Ch 19)
- **代码的坏味道（Code Smell）** — 指示"此处需要重构"的表面特征，共 24 种；坏味道不是错误，是启发式信号。(Ch 3)
- **三次法则（Rule of Three）** — 第一次做事直接做，第二次可以做类似的事，第三次做类似的事就应重构。(Ch 2)
- **中间人（Middle Man）** — 坏味道：类的大部分接口只是简单委托给别的类，过度委托应移除中间人。(Ch 3, Ch 7)
- **临时字段（Temporary Field）** — 坏味道：字段只在特定情况下才有值，暗示应提炼类或引入特例。(Ch 3)
- **以多态取代条件表达式（Replace Conditional with Polymorphism）** — 复杂条件逻辑按类型分叉时，把每个分支变成子类/多态方法。(Ch 1, Ch 10)
- **卫语句（Guard Clause）** — 提前 return 的条件检查，取代嵌套条件，突出"这条路径罕见且快速退出"。(Ch 10)
- **参数对象（Parameter Object）** — 一组总是一起传递的参数应组成一个对象（引入参数对象）。(Ch 6)
- **发散式变化（Divergent Change）** — 坏味道：一个类因多个不相关原因被反复修改，应按变化方向拆分。(Ch 3)
- **命令与查询分离（Separate Query from Modifier）** — 有返回值的函数不应有可观察的副作用；查询和修改拆成两个函数。(Ch 11)
- ** sealed class 基本类型偏执（Primitive Obsession）** — 坏味道：该用对象的地方用基本类型（如电话号码用 string），应以对象取代基本类型。(Ch 3, Ch 7)
- **特例（Special Case）** — 为"空值/默认行为"创建特例类（如 Null Object），消除到处检查的重复条件。(Ch 10)
- **神秘命名（Mysterious Name）** — 坏味道之首：改名是最低成本的重构；好名字是理解代码的起点。(Ch 3, Ch 6)
- **纯函数/查询函数（Query Function）** — 只返回值、无副作用的函数；重构应尽量把逻辑搬进查询函数以获得安全的操作顺序。(Ch 6, Ch 11)
- **继承体系并行（Parallel Hierarchy）** — 坏味道：为一个类添加子类时也要给另一个类添加对应子类。(Ch 3)
- **统筹手法（Composing Methods）** — 第6章主题：函数层面的提炼/内联/改名，是使用频率最高的重构。(Ch 6)
- **综合式修改 vs 增量式修改** — 重构让设计持续演进，避免"预先设计"与"腐化设计"的两难（演进式设计）。(Ch 2)
- **自我测试代码（Self-testing Code）** — 保证重构安全的前提：一套能频繁运行、结果可信的自动化测试。(Ch 4)
- **褐绳/数据泥团（Data Clumps）** — 坏味道：几个数据总是一起出现，应提炼类或引入参数对象。(Ch 3)
- **被忽视的 functionName 注释（Comments）** — 坏味道：注释往往是"代码不够清晰"的除臭剂；先试着提炼函数或改名，再决定是否留注释。(Ch 3)
- **被拒绝的遗赠（Refused Bequest）** — 坏味道：子类继承了自己不需要的超类成员，应以委托取代超类或下移。(Ch 3, Ch 12)
- **解释性变量/查询（Explanatory Variable）** — 为复杂表达式提炼具名变量或查询函数，让意图自解释。(Ch 6)
- **预备性重构（Preparatory Refactoring）** — 在加功能之前先把代码改得"更容易加"，让后续功能改动变小。(Ch 2)
- **驮马式修改 vs 霰弹式修改（Shotgun Surgery）** — 坏味道：每做一个小改动都要在多个类间跳来跳去，应内联/搬移使其集中。(Ch 3)
- **性能优化三法** — 先用自测试代码保证正确，再跑性能分析器（profiler）定位热点，只优化热点；多数程序大部分时间耗在小段代码上。(Ch 2)
- **暗腐的组织（Rotting Design）** — 不重构的代码库随时间腐化；重构是控制设计腐化的日常手段。(Ch 2)
- **驱动测试的边界条件（Boundary Conditions）** — 测试重点：越界、null/空、极端值；"测试那些可能出错的地方和最不可能出错的地方"。(Ch 4)
- **高圈复杂度/过长函数（Long Function）** — 坏味道：函数越长越难理解；"当感觉需要注释来说明什么时，就提炼函数"。(Ch 3, Ch 6)
- **过大的类（Large Class）** — 坏味道：类做的事太多，应提炼类。(Ch 3)
- **重复代码（Duplicated Code）** — 坏味道：同一段结构出现在多处，一改就要改多处；提炼函数/搬移/提炼类消除。(Ch 3)
- **重构（Refactoring, 严格定义）** — 在**不改变软件可观察行为**的前提下，调整其内部结构以提高可理解性、降低修改成本。行为不变是硬约束，靠测试保障。(Ch 2)
- **重构名录（Catalog）** — 每个手法按五段式记录：名称、速写（before/after 示意）、动机、做法（机械步骤）、范例。(Ch 5)
- **依赖混乱（Feature Envy 依恋情结）** — 坏味道：函数对别的类的数据比对自家数据更感兴趣，应搬移函数到数据所在处。(Ch 3, Ch 8)
- **霰弹式修改（Shotgun Surgery）** — 见"驮马式修改"条目。(Ch 3)
