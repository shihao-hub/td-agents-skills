# Patterns & Techniques —《重构：改善既有代码的设计（第2版）》

每条：**何时用 / 怎么做 / 代价与权衡**。按章节分组，手法名保留中英对照。

## 函数组织（Ch 1, Ch 6）

### 提炼函数（Extract Function）
- **何时用**：一段代码需要注释才能说清意图；或一段逻辑将被多处使用。这是使用频率最高的重构。
- **怎么做**：起一个好名字（"做什么"而非"怎么做"）；先处理局部变量与参数（读→传参，写→考虑返回或先拆变量）；小步搬移，每步可编译可测试。
- **权衡**：函数名本身的开销 vs 阅读收益；Fowler 立场：短函数（几行也可）+ 好名字 > 长函数。

### 内联函数 / 内联变量（Inline Function / Variable）
- **何时用**：函数体和名字一样清晰（间接层失去价值）；或要重组函数群前先内联归拢。
- **怎么做**：内联前检查所有调用点与多态情况；内联是搬移逻辑的"擦除动作"，常与提炼成对使用。

### 改变函数声明（Change Function Declaration）
- **何时用**：参数/返回值/名字不再准确表达契约。
- **怎么做**：一次性小改，或"改名→渐进式迁移"（保留旧签名转发新实现，逐点迁移调用方，最后删除旧签名）。对外发布的 API 用渐进式。

### 封装变量（Encapsulate Variable）
- **何时用**：全局/共享可变数据导致"找不到谁在改它"。
- **怎么做**：把数据包进函数（get/set），先让所有访问走函数，再收紧 set 的可见性；为搬移和加约束创造接缝。

### 函数组合成类 / 成变换（Combine Functions into Class / Transform）
- **何时用**：一组函数操作同一批数据；或同一份数据要派生多个计算结果。
- **怎么做**：把公共数据收进类字段或一个"变换记录"，函数改为方法，消除参数重复传递。

### 拆分阶段（Split Phase）
- **何时用**：一段代码同时处理两种不同关注点（如"解析"与"渲染"）。
- **怎么做**：提炼出中间数据结构，把两阶段分别提炼成函数，阶段间只通过该结构通信。(Ch 1 的核心示例手法)

## 封装（Ch 7）

### 封装记录 / 封装集合（Encapsulate Record / Collection）
- **何时用**：裸的 map/record 在系统里到处传递、无人知道其合法结构；集合被外部直接增删。
- **怎么做**：用类包住数据，只暴露必要的读取；集合访问器只返回包装/副本，内部才持真集合。**权衡**：封装 vs 直接操作的便利，共享面越大越值得封装。

### 以对象取代基本类型（Replace Primitive with Object）
- **何时用**：基本类型被赋予行为需求（校验、格式化、比较）时。
- **怎么做**：先封装变量，再建值对象类，逐步把行为搬进去。

### 隐藏委托关系 vs 移除中间人（Hide Delegate / Remove Middle Man）
- **何时用**：前者——客户端为了拿 `b.c.d` 得了解 a 的委托结构，模块边界被穿透；后者——中间类委托比例过高、成为纯转发层。
- **权衡**：这是同一根指针的两个方向的拉锯：封装的收益随委托结构的变化频率而变，没有永久正确答案。

### 替换算法（Substitute Algorithm）
- **何时用**：发现了明显更清晰的算法实现。
- **前提**：有测试兜底；一次只换一个算法。

## 搬移特性（Ch 8）

### 搬移函数（Move Function）
- **何时用**：函数对别处（参数/另一类的数据）的依恋超过对自家上下文——"依恋情结（Feature Envy）"。
- **怎么做**：检查函数内部的所有引用，先搬被依赖的元素或后搬；用编译器和测试逐调用点迁移。

### 搬移字段（Move Field）
- **何时用**：一个字段总被另一个类的函数使用。
- **怎么做**：先自封装该字段，再替换读写实现指向新家，最后删除原字段。

### 搬移语句 / 滑动语句 / 拆分循环（Move Statements / Slide Statements / Split Loop）
- **何时用**：代码做两件事却混在一起（含一次循环干两件事）；相关语句需要聚拢才能提炼。
- **权衡**：拆分循环会重复遍历，O(n) 内通常可接受——先求清晰，性能有疑虑时用 profiler 说话。

### 以管道取代循环（Replace Loop with Pipeline）
- **何时用**：filter/map/reduce 类变换用循环写得绕时。

### 移除死代码（Remove Dead Code）
- **何时用**：永不执行的分支/函数。版本控制会记住它，留着只添噪声。

## 数据组织（Ch 9）

### 拆分变量（Split Variable）
- **何时用**：一个变量被赋值多次且承担不同职责（循环变量/累加器/临时结果）。

### 以查询取代派生变量（Replace Derived Variable with Query）
- **何时用**：可从现有数据算出的值被存成字段——冗余状态是 bug 温床。
- **权衡**：性能敏感且计算昂贵时保留缓存字段（先测再优化）。

### 值对象 ↔ 引用对象（Change Reference to Value / Change Value to Reference）
- **何时用**：同一实体的多份拷贝需要保持一致 → 引用对象；反之不可变、按值比较更简单 → 值对象。

## 条件逻辑（Ch 10）

### 分解条件表达式（Decompose Conditional）
- **何时用**：复杂 if 条件 + 分支体。各提炼成函数：`cond()`、`then()`、`else()`。

### 合并条件表达式（Consolidate Conditional Expression）
- **何时用**：多个检查走同一结果 → 合并成一个条件函数。

### 以卫语句取代嵌套条件（Replace Nested Conditional with Guard Clauses）
- **何时用**：函数里有"不正常路径先退出"的结构。核心原则：**先处理罕见/失败路径并提前 return，主路径保持无缩进**。

### 以多态取代条件表达式（Replace Conditional with Polymorphism）
- **何时用**：同一条件分叉散落在多个函数里（每个都 switch 同一个类型码）。
- **怎么做**：建类结构（子类或策略对象），把各分支搬进多态方法；单一分叉不必为此上多态。

### 引入特例（Introduce Special Case）
- **何时用**：多处重复检查"同一个特殊值"（null/空/默认）。建特例对象统一返回默认行为（Null Object 思路）。

### 引入断言（Introduce Assertion）
- **何时用**：代码正确性依赖某个"理应恒真"的条件。断言是给读者文档，不是给运行时的控制流。

## API 重构（Ch 11）

### 查询与修改分离（Separate Query from Modifier）
- **何时用**：任何有返回值又有副作用的函数。拆开后调用方可放心缓存/重排查询。

### 移除标记参数（Remove Flag Argument）
- **何时用**：布尔/枚举参数让函数在两种行为间分叉 → 拆成两个显式函数（原"以明确函数取代参数"）。

### 保持对象完整（Preserve Whole Object）
- **何时用**：从一个对象取好几个值传给函数 → 直接传整个对象。**权衡**：引入依赖。

### 以查询取代参数 / 以参数取代查询（Replace Parameter with Query / vice versa）
- **权衡**：参数让依赖显式但增加调用负担；查询让调用简短但引入隐藏依赖。避免"一长串参数中有一半能自己算出来"。

### 以工厂函数取代构造函数（Replace Constructor with Factory Function）
- **何时用**：创建逻辑需要比 new 更表达（按类型返回不同实现、避免 new 的硬约束）。

### 命令 ↔ 函数（Replace Command with Function / vice versa）
- **权衡**：命令对象支持 undo/排队/组合；普通函数更简单。默认选函数。

## 继承（Ch 12）

### 函数/字段/构造函数本体上移（Pull Up Method / Field / Constructor Body）
- **何时用**：子类间出现重复 → 收进超类；重复的构造逻辑 → 上移构造函数本体。

### 函数/字段下移（Push Down Method / Field）
- **何时用**：超类成员只被部分子类使用——那是它们不该待的地方。

### 以子类取代类型码（Replace Type Code with Subclasses）
- **何时用**：类型码驱动行为分叉且集合不常变。不可继承的场景（如 Employee 已有超类）走间接版：先提炼类/委托再子类化。

### 以委托取代子类/超类（Replace Subclass/Superclass with Delegate）
- **何时用**：继承的两大痛点——子类随类型组合爆炸、子类耦合超类实现细节。Fowler 2 版立场：**组合优先，继承按需而用**。

### 提炼超类（Extract Superclass）/ 折叠继承体系（Collapse Hierarchy）
- **何时用**：两个类有大量重复 → 上提；一个类与超类已无差别 → 合并。
