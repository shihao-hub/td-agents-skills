# Chapter 4: 构筑测试体系（Building Tests）

## Core Idea（1–2 句）
重构的前提是一套稳固的自测试集合（self-testing code）：完全自动化、自己检查结果的测试能把"数小时的 bug 定位"压缩到几分钟。测试不是负担而是提速器——但要风险驱动地写，而非追求穷尽。

## Frameworks Introduced
- **自测试代码（Self-testing Code）**：让每个类携带自己的测试，测试与产品代码同库；测试自动检查期望输出而非人工盯屏，全部通过只输出 "OK"。来源：1992 年 OOPSLA 上 Dave Thomas "类应包含自己的测试代码" 的演讲；1997 年 Kent Beck 与 Erich Gamma 在飞机上造出 JUnit。
- **TDD 节奏（红-绿-重构）**：先写一个（失败的）测试 → 编码使测试通过 → 重构保持整洁。这个"测试、编码、重构"短循环每小时应完成多次。写测试的最好时机是动手编码之前：它迫使你思考接口而非实现，并给工作一个明确的完成标志。
- **测试应关注什么（风险驱动）**：测试"这个类应该做的所有事 + 可能出错的边界条件"，而非机械地"测试所有 public 函数"。访问函数之类太简单、不可能出错的不测；火力集中在最担心出错的地方。写测试过多反而导致测试不充分、气馁收场。
- **验证测试本身**：每个测试至少看到它失败一遍——临时在代码里引入一个错误，确认测试会红，再恢复。
- **测试结构：given-when-then / arrange-act-assert（配置-行为-断言）**，外加第四个不显眼的"拆除（teardown）"阶段（用 beforeEach 时框架自动完成）。一个 it 内原则上只放一个验证语句（紧密相关的断言可例外）。
- **夹具（fixture）策略**：每个测试前用 beforeEach 重建全新夹具，杜绝测试间通过共享可变夹具交互——那是"最恶心的 bug"和不确定性失败的温床；只有百分百不可变的夹具才可共享。
- **边界条件探测（扮演"程序公敌"）**：拿到集合就测空集合；拿到数值就测 0、负值、空字符串。边界测试还引发设计思考（负需求量合理吗？该抛错还是归 0？）。
- **重构与测试的分工**：重构保证可观测行为不变；超出可观测范畴的错误（如构造函数抛异常）对应的测试可在重构前删掉。想让代码快速失败的预设条件，用引入断言（Introduce Assertion）——断言本身就是一种测试，无须再测。
- **测试驱动重构的方式**：重构前先让代码可自测试；遇到 bug 先写一个能清楚复现它的测试，测试通过才算 bug 修完；重构途中持续补充测试。
- **何为"足够好"**：主观标准——若有人引入缺陷，你有多大自信测试集能抓住？测试覆盖率只能找出未覆盖的代码，不能衡量测试集质量。测试过多的征兆：改测试比改代码花的时间更多。

## Key Concepts
- 自测试代码（Self-testing Code）
- 测试夹具（Fixture）与 beforeEach 重建
- 红/绿条（Red/Green Bar）："看到红条时永远不许重构"、"回退到绿条"
- TDD（Test-Driven Development）："测试、编码、重构"循环
- given-when-then / arrange-act-assert / setup-exercise-verify
- 边界条件（Boundary Conditions）与 happy path（正常路径）
- 失败（failure）vs 错误（error）：验证阶段期望不符 vs 更早阶段抛出的异常
- 测试覆盖率（Coverage）：只能查漏，不能衡量质量
- 风险驱动的测试（Risk-driven Testing）

## Mental Models
- 当 bug 难定位时，用频繁运行的自动测试把搜索空间压缩到"自上次绿条以来的少量新代码"。
- 当考虑"要不要测这个"时，问"我最担心这里出错吗"——测试是风险驱动的投资，边际效用递减。
- 当改动业务逻辑时，先把复杂部分与 UI/持久化/外部服务隔离，让逻辑可独立测试。
- 当测试拖慢了你改代码的节奏（改动测试比改动代码更费时），那是测试过多的信号。

## Anti-patterns
- 共享可变测试夹具（把 fixture 提到 describe 顶层作用域）：测试间交互、结果依赖运行次序的不确定性失败
- 手动盯屏核对测试输出而非自动断言
- 一个 it 塞多个互不相关的验证语句，掩盖失败原因
- 追求"测试所有 public 函数"或穷尽一切组合——工作量太大，反而测试不足
- 以测试覆盖率作为测试集质量的指标
- 盲目相信输入、在可信来源的内部模块间堆叠重复验证（该用引入断言快速失败时才检查）
- 测试全绿就不再怀疑：应先故意弄坏代码，验证测试真的会失败
- 因为"测试不能证明没有 bug"而不写测试

## Code Examples
书中 Province 示例的典型测试写法（Mocha + Chai，含 given-when-then 风味）：

```js
describe('province', function() {
  let asia;                       // 独立夹具：每个测试重建，绝不共享可变状态
  beforeEach(function() {
    asia = new Province(sampleProvinceData());   // given：标准测试夹具
  });

  it('shortfall', function() {                   // 正常路径
    expect(asia.shortfall).equal(5);             // then：验证
  });

  it('change production', function() {           // when：修改夹具后验证
    asia.producers[0].production = 20;           // when
    expect(asia.shortfall).equal(-6);            // then
    expect(asia.profit).equal(292);
  });

  it('negative demand', function() {             // 边界条件：扮演程序公敌
    asia.demand = -1;
    expect(asia.shortfall).equal(-26);
    expect(asia.profit).equal(-10);
  });
});
```

写既有代码测试的套路：期望值先随便填 → 运行拿真实值回填（如 230）→ 临时插入错误确认测试变红 → 恢复。

## Key Takeaways
- 编写优良的测试反而提高编程速度——即使完全不重构，测试也是强大的 bug 侦测器。
- 测试必须完全自动化并自检结果；频繁运行是 bug 定位快的关键一半（另一半才是测试本身）。
- 先写测试（TDD）让注意力聚焦接口、并给工作明确的完成标志。
- 测试是风险驱动的：集中于最担心出错和边界条件处；测试写太多会气馁、反而测试不足。
- 永远用独立夹具：共享可变夹具导致的间歇性失败足以摧毁对测试体系的信心。
- 每个 bug 都先写一个复现它的测试，测试通过才视为修完——这个错误从此永不再现。
- 测试集好坏的主观判据：对"新缺陷会被抓住"的信心；改测试比改代码还费时是测试过多的征兆。
