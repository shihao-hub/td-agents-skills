# Chapter 11: 重构 API（Refactoring APIs）

## Core Idea
API 是模块与函数之间的关节：好 API 会把"读"与"写"清晰分开、参数列表恰好总结函数的可变性、并尽量倾向不可变。随着理解加深要回头修 API——本章 10 个手法全部围绕"让接口更容易正确使用、更难错误使用"展开。

## Frameworks Introduced（本章全部重构手法）

- **将查询函数和修改函数分离（Separate Query from Modifier）**：有返回值的函数不应有看得到的副作用（命令与查询分离 CQS）。做法：复制整个函数作为查询函数并去掉副作用语句，调用处改为"先查后改"两次调用，再从原修改函数中去掉返回值，最后用替换算法让修改函数内部复用查询函数。注意：无害缓存不算"看得到的副作用"。
- **函数参数化（Parameterize Function，曾用名：令函数携带参数）**：两个函数逻辑相似只是字面量不同时，合并为一个带参数的函数消除重复。做法：用改变函数声明加参数→调用处传入字面量→函数体逐个改用参数。处理"区间/档次"类相似函数时从中间那档入手最容易推广（如 withinBand(usage, bottom, top)）。
- **移除标记参数（Remove Flag Argument，曾用名：以明确函数取代参数 Replace Parameter with Explicit Methods）**：调用者传字面量（布尔/枚举/字符串）来选择函数内部走哪条分支的参数就是标记参数——它隐藏了 API 的差异性，布尔尤其难懂（`deliveryDate(order, true)` 的 true 是什么意思？）。判断标准：调用方传的是字面量、且参数值影响函数内部控制流；传"流动中的数据"不算。做法：为每个取值建明确函数（条件分发在函数最外层时用分解条件表达式，否则在原函数上建包装函数），逐一替换调用者；分发逻辑纠结在函数内部时宁可保留原函数并改名如 `deliveryDateHelperOnly`。多个标记参数组合爆炸时，是函数做太多事的信号。
- **保持对象完整（Preserve Whole Object）**：从记录结构拆出几个值再一起传参，不如传整个对象、函数内部自己取值——参数列表更短、未来加数据不用改签名。依恋情结的信号：几处代码抽取同一组数据单独做逻辑，说明逻辑该搬进对象。常见于引入参数对象之后。安全做法：新建带易搜索临时名（如 xxNEW 前缀）的空函数包装旧函数，逐一迁移调用者，内联旧函数后改名。
- **以查询取代参数（Replace Parameter with Query，曾用名：以函数取代参数）**：参数值若函数自己获取同样容易，就是参数列表里的重复。最安全场景：参数可从另一参数推导出来。代价是函数体内新增依赖；具有引用透明性的函数不要为此去读可变全局状态。做法：先提炼计算参数的查询函数，函数体内改调它，再用改变函数声明移除参数。
- **以参数取代查询（Replace Query with Parameter）**：反向手法——函数体内引用了令人不快的元素（全局变量、想剥离的依赖）时，改为参数传入，把责任交还调用者。收益：恢复引用透明性（同样参数永远同样结果），支持"纯函数核心 + I/O 外壳"结构；代价是调用方变笨重。这是一对需要反复权衡、来回调整的手法，关键是"能可靠地改变决定"。
- **移除设值函数（Remove Setting Method）**：提供 setter 就暗示字段可变；不希望构造后被改的字段就不给 setter。两种典型场景：构造函数是 setter 的唯一使用者；客户端用"构造函数 + 一串 setter"的创建脚本造对象，脚本结束后不应再改。做法：用改变函数声明把值改为构造函数参数，迁移所有创建点，内联掉 setter，字段尽量声明为不可变。若调用 setter 是为了更新被多处共享引用的对象（无法换成新建对象），放弃本重构。
- **以工厂函数取代构造函数（Replace Constructor with Factory Function，曾用名：Replace Constructor with Factory Method）**：构造函数受限——名字固定、只能返回本类实例、需要 new 特殊调用。工厂函数不受这些限制。做法：新建工厂函数委派给构造函数，迁移调用者，再缩小构造函数可见性。进阶：把类型码信息嵌进函数名，如 `createEngineer(name)` 代替 `new Employee(name, 'E')`，顺便消除字符串字面量类型码。
- **以命令取代函数（Replace Function with Command，曾用名：以函数对象取代函数）**：把函数封装成命令对象（命令模式），支持撤销、丰富生命周期、继承定制、以及最重要的——拆解复杂函数（局部变量全部变成字段后，提炼函数不再受作用域困扰，且每个方法可单独测试调试）。但灵活性以复杂性为代价：95% 的情况下选普通函数。做法：建空类→搬移函数（保留原函数转发）→参数逐个移入构造函数→execute 命名。
- **以函数取代命令（Replace Command with Function）**：命令对象不够复杂时变回普通函数。做法：提炼"创建并执行命令"的函数→内联命令的各执行函数（有返回值先提炼变量）→构造函数参数经改变函数声明移到执行函数、字段引用改为参数→内联构造与执行两步→移除死代码删掉命令类。故意删除构造函数里的字段赋值，让漏改在测试中暴露。

## Key Concepts
- **命令与查询分离（Command-Query Separation, CQS）**：查询无副作用、命令无返回值。
- **标记参数（Flag Argument）**：调用者传字面量指示函数走哪条分支的参数。
- **引用透明性（Referential Transparency）**：同参数永远同结果，函数易理解、易测试。
- **不可变性（Immutability）**：尽量让对象构造后不可改；移除设值函数与以参数取代查询都是其工具。
- **命令对象（Command Object）**：封装单个函数调用请求的对象（GoF 命令模式）。
- **修改函数/改变函数（Modifier/Mutator）**：Fowler 对"改变对象可观察状态的函数"的称呼，避免与"命令"混淆。
- **改变函数声明（Change Function Declaration）**：本章多数手法的底层操作。
- **创建脚本（Creation Script）**：构造函数调用 + 一串设值函数的对象构造方式。

## Mental Models
- **参数列表 = 函数可变性的摘要**：参数应只标示行为差异的主要来源；可推导的值、函数自取同样容易的值都是重复。
- **责任分配跷跷板**：去参数 = 责任移给函数（调用方简单）；加参数 = 责任移给调用者（解耦、提纯）。没有一劳永逸的答案，重要的是能可靠地在两个方向间切换。
- **继承/构造函数是"特别受限的机制"**：构造函数有语言级限制（命名、返回类型、调用方式），工厂函数是对冲这些限制的通用垫片。
- **95% 规则**：命令对象只在普通函数给不了所需能力（撤销、队列、拆解巨型函数）时才用；默认选函数。

## Anti-patterns
- `deliveryDate(order, true)` 式布尔标记调用——调用点完全不可读。
- 为"以后可能改"的字段保留 setter，实际制造了大量意外的可变性。
- 把所有依赖都做成参数导致冗长重复的参数列表；或反之，为省参数让函数依赖全局可变状态。
- 给巨型函数直接提炼处处受阻（局部变量纠缠），而不先转成命令对象拆解。
- 无条件执行"继承有害/绝不用命令对象"，或反向在简单场景堆命令对象——两端都是误读。

## Code Examples
移除标记参数（最典型的 API 可读性问题）：

```js
// Before：调用点的 true 毫无信息量
aShipment.deliveryDate = deliveryDate(anOrder, true);
function deliveryDate(anOrder, isRush) {
  if (isRush) { /* 加急时效表 */ }
  else        { /* 常规时效表 */ }
}

// After：意图在函数名里，工具也能区分两种调用
aShipment.deliveryDate = rushDeliveryDate(anOrder);
function rushDeliveryDate(anOrder)    { /* 加急时效表 */ }
function regularDeliveryDate(anOrder) { /* 常规时效表 */ }
```

## Key Takeaways
- 任何有返回值的函数都不该有看得到的副作用——这一条规则撑起本章一半手法。
- 标记参数的定义很精确：调用方传字面量 + 影响内部控制流；修 API 前先按此判断。
- "以查询取代参数 ↔ 以参数取代查询"是一对，要在"调用方简单"与"低耦合/引用透明"之间反复调仓。
- 优先不可变：不给 setter、构造时给全值，能消掉一整类 bug。
- 工厂函数包住构造函数，为改名、返回子类/代理、嵌类型码留出余地。
- 命令对象是拆解巨型函数的脚手架，拆完若不再需要就变回函数。
- 每个手法都靠改变函数声明、提炼/内联这些基础手法组合完成——小步 + 每步测试。
