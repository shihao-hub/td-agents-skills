# Chapter 8: 搬移特性（Moving Features）

## Core Idea
好的模块化 = 相关联的软件要素聚在一起、块间联系直观易查；而对代码的理解会不断加深，所以要不停地在上下文之间搬移函数、字段和语句，让代码结构始终匹配当前理解。本章提供从整函数、字段、语句到循环与死代码的一整套"搬家"手法。

## Frameworks Introduced
- **搬移函数（Move Function）**（曾用名：Move Method）：动机——函数频繁引用其他上下文的元素、对自身上下文关心甚少时，搬到更亲密的上下文能改善封装、减少依赖。做法：盘点函数引用的所有程序元素（被调函数若也要搬，先搬依赖最少的）→ 复制到目标上下文并调整（源上下文元素经参数或引用传入，通常顺便改名）→ 源函数改为纯委托 → 测试 → 视情况内联函数（115）删除委托。安全要点：检查多态（是否被子类覆写/覆写超类）；决定"传值 vs 传整个对象"看目标函数后续需要多少数据。两个范例方向：嵌套函数提升到顶层（用静态检查逐层暴露遗漏依赖）；类之间搬移（Account.overdraftCharge → AccountType）。
- **搬移字段（Move Field）**：动机——数据结构是程序根基，坏结构招致纠缠代码；总是同现、总是同时作为参数传递、总是要一起修改的字段多半放错了地方。做法：确保源字段已封装 → 目标对象建字段 → 确保源对象能引用目标对象 → 改源访问函数指向目标字段 → 删源字段。安全要点：裸记录先封装记录（162）再搬；当搬移意味着"共享数据"（如所有同类型账户共享利率）时，用引入断言（302）比对源/目标字段值并行运行一段时间，确认无可观测行为变化后再删源字段。
- **搬移语句到函数（Move Statements into Function）**：反向：搬移语句到调用者。动机——调用某函数时总跟着一段相同代码，就该合并进函数，改一处生效全部。做法：重复代码先用移动语句（223）靠拢目标函数 → 单调用点直接剪贴；多调用点则先对其中一个调用点用提炼函数（106）把语句连同目标函数提炼成临时名新函数 → 其余调用点改调新函数 → 内联函数（115）把目标函数并进去 → 函数改名（124）恢复原名。
- **搬移语句到调用者（Move Statements to Callers）**：反向：搬移语句到函数。动机——函数边界随系统演化偏移：原本统一的行为在某些调用点需要不同表现，把"分化的部分"搬回调用处。做法：简单场景直接剪切粘贴；多调用点则先用提炼函数留下想保留的部分 → 逐个内联原函数 → 对提炼函数用改变函数声明（124）恢复原名。安全要点：边界已严重偏移时不如直接内联→重排→重新提炼；涉及继承时需对每个子类覆写做同样提炼。
- **以函数调用取代内联代码（Replace Inline Code with Function Call）**：动机——命名良好的函数解释意图、消除重复、修改只在一处。做法极简：用既有函数调用替换内联代码，测试。要点：警惕"外表相似、本质无关"的代码——判断标准是函数名放进该语境是否协调；配库函数使用效果更佳。
- **滑动语句（Slide Statements）**（曾用名：合并重复的代码片段 Consolidate Duplicate Conditional Fragments）：动机——相关的东西应一起出现（同一数据结构的操作、声明靠近使用），且常是提炼函数的前置准备。做法：确定目的地，检查途中语句是否受执行次序影响 → 剪切粘贴 → 测试；失败就减小步子。安全要点：前移不得越过任何相关变量声明；后移不得越过引用或修改了所涉变量的语句；无副作用代码几乎可自由重排（CQS 原则让判断更容易）；有副作用时先考虑拆分变量（240）或拆分循环减少状态更新。条件逻辑同样适用：移出分支是消除重复，移入分支是刻意制造重复。
- **拆分循环（Split Loop）**：动机——一次循环做两三件事，修改时就得同时理解两件事；一个循环只做一件事，才能独立理解、独立返回值。做法：复制循环 → 各删无关逻辑使各司一事 → 测试 → 通常紧接着对每个循环提炼函数。安全要点：性能顾虑遵循"先重构后优化"（2.8 节）——真成瓶颈时合回去很容易，且循环很少是瓶颈。
- **以管道取代循环（Replace Loop with Pipeline）**：动机——集合管道（collection pipeline：slice/filter/map 等运算串接）比命令式循环可读性强，从头到尾一遍读清数据变换过程。做法：新建变量存放参与循环的集合 → 从循环顶部开始，逐块行为用管道运算替代（每步测试）→ 全部搬完删循环，管道结果赋给累加变量。范例：CSV 解析循环变成 `.slice(1).filter(...).map(...).filter(...).map(...)`。
- **移除死代码（Remove Dead Code）**：动机——死代码不花钱但有巨大阅读负担，且没有任何标记告诉读者"可放心忽略"；版本控制普及后注释掉代码的做法已无借口。做法：对外可见的死函数先查调用点 → 删除 → 测试；真要留提示就在注释里写明被移除的提交号（作者几乎从不写）。

## Key Concepts
- 上下文（Context）：任何函数赖以存活的模块环境；搬移的本质是寻找更合适的上下文
- 模块化：相关要素聚拢 + 块间联系直观，是本章所有手法的价值标尺
- 集合管道（Collection Pipeline）：filter/map 等集合到集合的运算串接，替代命令式循环
- 命令与查询分离（CQS）：有返回值即无副作用，是安全滑动语句的信心来源
- 纯委托函数：搬移过渡期源上下文保留的转发函数，视情况内联掉
- 边界偏移：函数抽象边界随系统演化而分化，是"语句搬回调用者"的信号
- 引入断言（302）：搬移字段引发数据共享时，并行期比对源/目标值的守门手段
- 小步前进：移动语句失败时减小步子（少移几行、绕开可疑语句）

## Mental Models
- **搬家模型**：搬移函数分两步——先把大箱小箱整体搬到新家（源函数变纯委托），测试通过后再"拆箱复位"（改名、内联、清理依赖）；静态检查在每一步帮你发现漏搬的依赖。
- **结构追随理解**：数据结构是程序根基但很难一次做对，"这周合理的设计下周可能就错了"——发现不适配就马上修缮，容许瑕疵累积会让代码越来越复杂。
- **先重构后优化**：拆分循环、返回集合副本这类"看似有性能代价"的手法，都遵循同一守则——先把结构变清晰，测得到瓶颈再优化；清晰的结构反而常让更强的优化成为可能。
- **重复的双向流动**：语句搬进函数是消除重复（变化只改一处），搬回调用者是有意分化重复（不同调用点需要不同行为）——两者互为反向重构。

## Anti-patterns
- **身兼多职的循环**：一个循环里攒平均年龄和总薪水，修改任何一处都要理解全部。
- **命令式循环处理集合变换**：用循环 + 控制变量（`firstLine`）+ 累加器手写 filter/map 能做的事，可读性差且易藏 bug。
- **函数边界僵化**：调用点开始出现"每次调用后都要补一段"的相同/不同代码，却不调整函数边界。
- **注释掉代码代替删除**：版本控制时代没有借口；死代码只留下理解负担。
- **无视执行次序的大步滑移**：跨过修改了所涉变量的语句移动代码，改变可观测行为；测试失败还硬移而不是减小步子。
- **外表相似即重复**：内联代码与函数只是碰巧相似时强行替换调用，函数实现变化会误伤无辜代码。

## Code Examples
以管道取代循环——CSV 数据解析（本章最能体现"消灭循环"的手法）：

```js
// Before：命令式循环 + 控制变量 + 累加器
function acquireData(input) {
  const lines = input.split("\n");
  let firstLine = true;
  const result = [];
  for (const line of lines) {
    if (firstLine) { firstLine = false; continue; }
    if (line.trim() === "") continue;
    const record = line.split(",");
    if (record[1].trim() === "India") {
      result.push({city: record[0].trim(), phone: record[2].trim()});
    }
  }
  return result;
}

// After：集合管道，一遍读懂数据变换全过程
function acquireData(input) {
  const lines = input.split("\n");
  return lines
    .slice  (1)
    .filter (line   => line.trim() !== "")
    .map    (line   => line.split(","))
    .filter (fields => fields[1].trim() === "India")
    .map    (fields => ({city: fields[0].trim(), phone: fields[2].trim()}))
    ;
}
```

## Key Takeaways
1. 搬移的判断标准是"关联度"：频繁引用别处元素、对自身上下文关心甚少的函数/字段就该搬家；决定越难做，通常说明搬不搬越不重要。
2. 搬移的标准节奏：复制到新家 → 源处改纯委托 → 测试 → 再决定是否内联委托；静态检查是发现漏搬依赖的安全网。
3. 搬移字段若意味着数据从"各自持有"变"共享"，先加断言并行运行验证无可观测行为变化，再删源字段。
4. 滑动语句的安全性取决于副作用：尽量写无副作用代码并遵循 CQS，重排就能近乎自由；测试失败就减小步子。
5. 拆分循环不是性能自杀而是结构投资：每个循环只做一件事才可能提炼函数、进而管道化。
6. 集合管道替代循环是从循环顶部逐块替换、每步测试完成的，最后删循环并把结果赋回累加变量。
7. 死代码当场删除——版本控制就是你的存档，注释留码只会浪费下一个读者的时间。
