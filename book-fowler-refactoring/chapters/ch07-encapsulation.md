# Chapter 7: 封装（Encapsulation）

## Core Idea
封装的本质是隐藏"模块的小秘密"（Parnas）：让每个模块尽可能少地了解系统其他部分，从而使变化只影响少数地方。数据结构是最常见的秘密——用类把记录、集合、基本类型和临时变量的细节藏到访问函数背后，为未来的变化留出空间。

## Frameworks Introduced
- **封装记录（Encapsulate Record）**：动机——可变数据用记录存储会强迫调用方区分"存储的"与"计算的"数据，且字段含义不直观；用类包装记录，可控制访问方式、支持渐进改名。做法：先封装变量（Encapsulate Variable，132）得到易搜索的取值/设值函数 → 用类包裹记录、返回实例 → 逐点将读取/更新改为访问函数 → 删除返回原始记录的函数。安全要点：嵌套结构优先处理更新点（用提炼函数把深查找集中为设值函数再搬移进类）；检查遗漏可用"返回深拷贝"或"只读代理/冻结副本"，靠测试暴露漏改的更新点。
- **封装集合（Encapsulate Collection）**：动机——只封装集合引用不够，`aList.push()` 绕过类的掌控；应在类上提供添加/移除方法，并让取值函数返回副本或只读代理。做法：封装变量 → 加 add/remove 方法 → 尽量移除设值函数（移除设值函数，331）→ 客户端改用新方法 → 取值函数返回只读视图。安全要点：宁可多复制一份，也不调试意外修改；同一代码库保持一种方案（副本 vs 代理）一致。
- **以对象取代基本类型（Replace Primitive with Object）**（曾用名：以对象取代数据值/以类取代类型码）：动机——简单数据项（如字符串电话号码、优先级字符串）一旦需要行为，逻辑会扩散成重复代码；先包一个薄类，日后行为有地可去。做法：封装变量 → 建简单值类（构造函数存值 + 转换函数如 `toString`）→ 设值函数存新类实例、取值函数委托 → 视需要函数改名。安全要点：明确值对象（value object）还是引用对象（将引用对象改为值对象 252 / 反向 256）；让构造函数接受自身实例可平滑过渡。
- **以查询取代临时变量（Replace Temp with Query）**：动机——临时变量妨碍分解过长函数（要传参），且计算逻辑易在多处重复；换成函数后边界清晰、无副作用可查。做法：确认变量只赋值一次且每次计算结果相同 → 先声明为 `const` 验证 → 提炼函数 → 内联变量（123）。安全要点：只适用于"只计算一次且不再修改"的变量；快照型变量（如 `oldAddress`）不可用；提炼函数若有副作用先做将查询函数和修改函数分离（306）。在类中效果最好（共享上下文）。
- **提炼类（Extract Class）**：反向：内联类。动机——类随责任膨胀变得难懂；某些数据和函数总是同现同变即该分离。做法：定新责任 → 建空类并让旧类持有实例 → 逐个搬移字段（207）、搬移函数（198）（先搬被调用多的低层函数）→ 清理接口 → 决定是否公开、是否转为值对象。信号：子类化只影响部分特性，或不同特性需要不同子类化方式。
- **内联类（Inline Class）**：反向：提炼类。动机——类不再承担足够责任（常因重构搬走了职责），或两个类想重新划分职责时"先合并再重新提炼"更简单。做法：在目标类为源类所有 public 函数建委托 → 改客户端调用委托 → 逐步搬空源类 → 删除源类。
- **隐藏委托关系（Hide Delegate）**：动机——客户端通过 `aPerson.department.manager` 这类链式调用知晓了委托结构，受托类（Department）改接口会波及所有客户端；在服务对象上放简单委托函数隔离变化。做法：为每个被委托的函数在服务对象建委托函数 → 改客户端 → 无客户端再需受托对象时删掉访问函数。
- **移除中间人（Remove Middle Man）**：反向：隐藏委托关系。动机——受托类功能变多时转发函数泛滥，服务类沦为中间人（Middle Man 坏味道，常因教条地遵循迪米特法则）；此时让客户端直接调用受托类。做法：为受托对象建取值函数 → 客户端改为链式调用 → 删委托函数。要点：合适的隐藏程度随时间变化，"重构的意义在于你永远不必说对不起"，两手法可来回调整，也可混用。
- **替换算法（Substitute Algorithm）**：动机——对问题理解加深或引入程序库后，发现更清晰的解法，就整段换掉。做法：先把原算法整理进独立函数 → 为其准备测试固定行为 → 引入新算法 → 静态检查 + 测试比对，调试时以旧算法为参照。安全要点：先尽可能分解原函数，巨大函数的直接替换极难把握。

## Key Concepts
- 封装（Encapsulation）：模块尽可能少了解系统其他部分；不只是隐藏字段，委托关系、算法都可隐藏
- 可变数据 vs 不可变数据：可变数据偏爱类封装；不可变数据记录 + 填充即可
- 值对象（Value Object）：不可变 + `equals`；封装后的小类常演进为值对象
- 命令与查询分离（Command-Query Separation）：有返回值的函数无副作用，是判断移动/查询安全性的基础
- 迪米特法则（Law of Demeter）：作者戏称"偶尔有用的迪米特建议"——过度遵循会产生中间人
- 中间人（Middle Man）坏味道：转发函数过多时服务类失去自身价值
- 只读代理 / 数据副本：封装集合与嵌套记录的两种读取控制手段，需在代码库中保持一致
- 封装变量（Encapsulate Variable，132）：几乎本章所有手法的共同第一步

## Mental Models
- **秘密隐藏模型（Parnas）**：分解模块的首要标准是识别"应隐藏的小秘密"；数据结构是最常见的秘密。
- **行为有了着落点**：一个薄包装类（如 Priority）看似价值甚微，但只要悉心照料，校验、比较等行为会不断沉积其中，成长为有用工具——"新手低估、老手最爱"的重构。
- **封装程度是可调旋钮**：Hide Delegate 与 Remove Middle Man 是一对反向手法，封装的"合适程度"随代码演化而变，随时可来回调整，不必一次做对。
- **更新优先于读取**：封装大结构时，把所有更新操作集中到设值函数是重中之重；读取可以返回副本/代理，但漏掉的更新点会直接破坏封装。

## Anti-patterns
- **伪封装集合**：getter 返回集合本身，客户端 `push()` 绕过类直接修改，封装形同虚设。
- **持有原始记录**：类包装了记录却保留返回 `_data` 原始引用的函数，破坏封装完整性（临时调试用途需尽快移除）。
- **教条遵循迪米特法则**：为每个委托特性加转发函数，服务类膨胀成纯中间人。
- **对快照变量使用 Replace Temp with Query**：多次赋值/快照型临时变量（`oldAddress`）提取成查询会改变行为。
- **注释掉死算法/死代码**：有版本控制的年代，注释留代码只是阅读负担。
- **未验证就替换算法**：不先固定行为测试就直接替换复杂算法，出错无从比对。

## Code Examples
以对象取代基本类型——Priority 从裸字符串成长为值对象：

```js
// Before：字符串优先级，比较逻辑散落在客户端
class Order { constructor(data) { this.priority = data.priority; } }
highPriorityCount = orders.filter(o => "high" === o.priority
                                  || "rush" === o.priority).length;

// After：封装成 Priority 类，校验与比较内聚其中
class Order {
  get priority()        { return this._priority; }
  get priorityString()  { return this._priority.toString(); }
  set priority(aString) { this._priority = new Priority(aString); }
}
class Priority {
  constructor(value) {
    if (value instanceof Priority) return value;
    if (Priority.legalValues().includes(value)) this._value = value;
    else throw new Error(`<${value}> is invalid for Priority`);
  }
  toString() { return this._value; }
  static legalValues() { return ['low', 'normal', 'high', 'rush']; }
  equals(other)    { return this._index === other._index; }
  higherThan(other){ return this._index >  other._index; }
}
highPriorityCount = orders.filter(o => o.priority.higherThan(new Priority("normal"))).length;
```

## Key Takeaways
1. 封装远不止"私有字段 + getter/setter"：真正要封装的是集合内容、记录结构、委托关系乃至整个算法。
2. 几乎所有封装手法的共同第一步是封装变量（132），并用"又丑又长、易搜索"的临时函数名标记过渡期。
3. 封装可变数据时更新点比读取点更重要：把修改集中到类的方法里，性能换安全通常划算，测得到影响再优化。
4. 小的值类（Priority、TelephoneNumber）是最被低估的重构——成本低而长期收益大，行为会自然向它聚集。
5. 隐藏委托与移除中间人是同一旋钮的两端，封装程度应随代码演化持续调整，无需一次定终身。
6. Replace Temp with Query 有硬前提：变量只赋值一次、计算无副作用且结果幂等；在类中施展效果最佳。
7. 替换算法前必须先把原函数分解好并用测试固定行为，调试时以旧算法为参照。
