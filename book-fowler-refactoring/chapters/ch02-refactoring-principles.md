# Chapter 2: 重构的原则（Refactoring Principles）

## Core Idea
重构有严格定义：在不改变软件可观察行为的前提下，用一系列微小、行为保持的步骤调整内部结构，以提高可理解性、降低修改成本——它的最终目的是经济性的：让你开发更快。

## Frameworks Introduced
- **重构的定义（名词/动词）**：名词 = 一次有名字的结构调整（如提炼函数）；动词 = 使用一系列重构手法调整结构。判定标准：如果代码在过程中有一两天不可用，那做的就不是重构，只是结构调整（restructuring）。
- **两顶帽子（Two Hats，Kent Beck）**：加新功能时不改既有代码；重构时不加功能。频繁换帽，但任一时刻清楚自己戴着哪顶。
- **何时重构的时机分类**：
  - **三次法则（Rule of Three，Don Roberts）**：第一次只管做，第二次尚可忍，第三次类似的事出现就重构。
  - **预备性重构（Preparatory Refactoring）**：加新功能/修 bug 之前，先微调结构使任务更容易（"往东 100 公里先往北 20 公里上高速"）。
  - **帮助理解的重构（Comprehension Refactoring）**：读到看不懂的代码就边读边重构，把脑中的理解固化进代码——像"扫去窗上的尘埃"，让你看见原本看不见的设计问题。
  - **捡垃圾式重构（Litter-Pickup Refactoring）**：顺手清理，容易就当场做，难就记下来稍后做；营地法则。
  - **有计划的重构 vs 见机行事的重构**：绝大多数重构应见机行事地融入日常编程，不专门排期；长期重构则由全团队"每靠近就推一点"渐进完成（Branch By Abstraction）。
  - **复审代码时重构**：与原作者并肩复审 + 重构效果最佳，自然导向结对编程。
- **何时不该重构**：代码丑但不需修改（可藏于 API 之下）→ 不重构；重写比重构更容易 → 别重构（需经验判断）。
- **写快速软件的三种方法**：时间预算法（实时系统专用）、持续关注法（常见但低效）、**重构导向法**——先写出构造良好、可调优的程序，后期用度量工具找性能热点集中优化。
- **数据库重构（evolutionary database design）**：用迁移脚本把结构修改与代码修改一起提交入库，小步、每次迁移后系统可运行；跨发布可用并行修改（Parallel Change / expand-contract）。

## Key Concepts
- **可观察行为（observable behavior）**：重构后用户关心的行为不变；调用栈、接口可变，既有 bug 仍会保留。
- **结构调整（restructuring）**：泛指各种代码清理；重构是其特定的、小步行为保持的子集。
- **设计耐久性假说（Design Stamina Hypothesis）**：投入改善内部设计可延长保持开发快速的时间——内部质量好的团队加功能越快，差的团队越慢直至想重写。
- **已发布接口（published interface）**：使用者与声明者彼此独立、声明者无权修改的接口；改名只能保留旧声明做委托并标记 deprecated。
- **自测试的代码（self-testing code）**：重构的第一块基石——完备且运行快速的自动化测试，测试失败即可把排查范围缩小到几行。
- **持续集成（Continuous Integration, CI / Trunk-Based Development）**：每人每天至少向主线集成一次，用特性开关隐藏未完成功能；避免语义冲突随分支寿命指数增长。
- **YAGNI（you aren't gonna need it）**：不为想象中的未来添加灵活性机制；只对当前需求构造高质量设计，等需要时再重构。判断问句："以后再重构有多困难？"
- **并行修改（Parallel Change）**：数据库字段改名分多次发布：加新字段 → 双写 → 读侧切换 → 删旧字段。
- **自动化重构工具**：基于语法树（而非文本替换）实现；静态类型语言中可做到完全安全的自动重构；即便有工具也应经常运行测试。

## Mental Models
- 当有人声称"重构期间代码停用了一两天"时，判定他们做的不是重构——重构的代码永远处于可工作状态。
- 当要在加功能与重构之间抉择时，戴两顶帽子分时段切换，绝不同时做两件事。
- 当被迫"赶快直接改完"时，先做预备性重构（看地图找最快路径）反而更快。
- 当性能成为担忧时，先写出可调优的软件再调优——90% 的代码不在热点上，不度量就优化是白费劲（Ron Jeffries 日期对象的教训）。
- 当考虑为未来添加灵活性时，只有当"以后再重构会很困难"被证实，灵活性才配增加复杂度。

## Anti-patterns
- **把"重构"当任何代码清理的泛称**：大动干戈、代码长期不可用——那是结构调整，不是重构。
- **道德化论证重构**：用"整洁的代码""工程素养"当理由是陷阱；重构是纯经济考量，价值在于让加功能、修 bug 更快。
- **细粒度强代码所有制**：每段代码唯一所有者导致人人发布接口、重构处处受限；推荐团队所有制或类开源的跨团队模式。
- **长寿命特性分支**：分支越久合并越难（指数增长），语义冲突（如一边改名一边新调用）工具无法自动解决；很多团队因此干脆放弃重构。
- **持续关注性能**：处处顺手优化使代码难维护，且因缺乏全局度量常常白优化。
- **重构与加功能的提交强行分离**：Fowler 不推荐——重构与新功能交织，分离后脱离上下文、看不出价值（非铁律，视团队而定）。

## Reference Tables
| 重构 vs 相邻活动 | 共同点 | 差别（目的） |
|---|---|---|
| 重构 | 不改整体功能 | 更易理解、更易修改（可能变慢） |
| 性能优化 | 不改整体功能 | 只求更快（可能更难理解） |

| 何种时机 | 触发条件 | 做法 |
|---|---|---|
| 三次法则 | 第 3 次写类似代码 | 立即重构 |
| 预备性 | 加功能/修 bug 前 | 先微调结构再做任务 |
| 帮助理解 | 读代码时在想"它在干嘛" | 边读边重构，固化理解 |
| 捡垃圾式 | 路过发现垃圾 | 容易就顺手改，难就记下 |
| 长期重构 | 大型改造（换库、抽组件） | 全团队渐进推进 + Branch By Abstraction |

## Code Examples
本章无代码示例（纯原则章）。最具代表性的操作示例是数据库字段改名时的并行修改节奏：新添字段（暂不使用）→ 写入逻辑双写新旧字段 → 读取侧逐个切到新字段 → 观察无 bug → 删除旧字段——每次提交后系统均可运行，体现了重构"小步且每步完整"的原则在数据库上的推广。

## Key Takeaways
- 严格使用"重构"一词：小步、行为保持、代码永远可工作；做不到就不是重构。
- 用经济论证重构（更快交付价值），不用道德论证；向不懂技术的经理可以不报备——受薪即为了快速交付，而重构是达到快速的方式。
- 重构不是独立排期的活动，而是编程流的一部分；专门的"重构周"应很少见。
- 想持续重构，必须配套自测试代码 + 持续集成；三者互相增效，是 YAGNI 与敏捷的根基。
- 分支寿命越短越好；长寿命特性分支会扼杀重构。
- 性能优化放在后期：用 profiler 找热点，集中优化，小步修改、每步度量，无效即撤销。
- 遗留代码：先找接缝插入测试（《修改代码的艺术》），再渐进清理；每次触碰都让营地更干净一点。
