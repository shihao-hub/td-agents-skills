# Chapter 9: 重新组织数据（Organizing Data）

## Core Idea
数据结构是理解程序行为的关键（Fred Brooks："给我看你的表单"），因此要保持数据结构的整洁：同一个值不承担两个用途、名字随理解加深而更新、能即时计算的派生数据就不要存成可变状态、并在"引用语义"与"值语义"之间做出有意识的选择。

## Frameworks Introduced

- **拆分变量（Split Variable）**（曾用名：分解临时变量 Split Temp、移除对参数的赋值 Remove Assignments to Parameters）
  - 动机：变量被赋值超过一次，通常意味着它承担了多个责任，令阅读者糊涂。
  - 做法：在声明及第一次赋值处改名（尽量 `const`），以第二次赋值为界修改之前的所有引用；逐段重复直到最后一处赋值。
  - 安全要点：**结果收集变量**（累加、拼接、向集合添加）是合法的多次赋值，不要拆；对输入参数再赋值时，先引入 `result` 之类的局部变量再拆。

- **字段改名（Rename Field）**
  - 动机：数据结构的命名比流程图更能传达程序意图，理解加深后应把名字更新进去。
  - 做法：作用域小则直接改并测试；否则先**封装记录（Encapsulate Record，162）**，内部数据结构与构造函数输入分开小步改名（新字段兼容旧名 → 迁移调用方 → 删除旧名），最后用**函数改名（Rename Function，124）**改访问函数。
  - 安全要点：可变结构上重复数据会招致灾难；不可变结构则可以"新旧并存、逐个迁移、删除旧字段"。

- **以查询取代派生变量（Replace Derived Variable with Query）**
  - 动机：可变数据是最大的错误源头之一；派生变量是"数据重复"，源数据更新时容易忘记同步。
  - 做法：找出所有更新点（必要时先拆分变量）→ 写计算函数 → 用**引入断言（Introduce Assertion，302）**验证"变量 === 计算值"（可先用封装变量包裹断言）→ 改读取方调用函数 → **移除死代码（Remove Dead Code，237）**删掉变量。
  - 安全要点：若有多个数据来源（如初始值 + 累计值），先拆分变量再断言；例外——源数据不可变且派生结果也不可变时（函数式变换风格），保留派生数据是合理的。

- **将引用对象改为值对象（Change Reference to Value）**（反向：将值对象改为引用对象）
  - 动机：值对象不可变，更易理解、可随意复制传递，在分布式与并发系统中尤佳。判别标准：更新时是"改内部对象属性"（引用）还是"整个换新对象"（值）。
  - 做法：确认可改为不可变 → **移除设值函数（Remove Setting Method，331）**（构造函数接管初始值，调用方改为重新赋整个对象）→ 提供基于值的 `equals`（多数语言还需覆写 `hashCode`）。
  - 安全要点：若需要多方向过共享修改可见，就不该改成值；JS 需手写 `equals` 并配测试（相等/不等/null/异类比较）。

- **将值对象改为引用对象（Change Value to Reference）**（反向：将引用对象改为值对象）
  - 动机：多个记录关联同一逻辑实体（多条订单 → 同一顾客）时，若共享数据需要更新，多副本会造成数据不一致；引用保证"一个实体只有一个对象"。
  - 做法：建仓库（Repository）→ 确保能按 ID 找到正确实例 → 修改宿主构造函数改为从仓库获取（`registerCustomer(id)` / `findCustomer(id)`），每步测试。
  - 安全要点：警惕全局仓库——"全局对象像强力药物，少用有益，过量即毒"，必要时把仓库作为参数传入构造函数。

## Key Concepts
- 循环变量（loop variable）与结果收集变量（collecting variable）——多次赋值的两种合法形态
- 封装记录（Encapsulate Record）——字段改名的前置步骤
- 数据重复（data duplication）——派生变量的本质坏味道
- 引用对象 vs 值对象（Reference vs Value）——更新语义：原地修改 vs 整体替换
- 不可变性（immutability）——值对象的核心属性，也是并发/分布式的护身符
- 仓库（Repository）——按 ID 保证实体唯一性的注册表
- 对象风格 vs 函数风格——包装计算属性 vs 数据结构变换
- 小步前进（small steps）——4 处分离改名，每步可测试

## Mental Models
- **一个变量一个责任**：赋值次数超过一次（且非收集变量）= 多重责任的信号，应拆分。
- **名字即文档**：数据结构的名字（字段名、变量名）比流程更能帮助阅读者理解程序；理解加深，名字随之更新。
- **值语义 vs 引用语义的选择是设计决策**：需要共享可见的修改 → 引用；需要安全传递与复制 → 值。
- **断言先行验证猜想**："可以即时计算"只是猜想，先用断言证明变量与计算值恒等，再动手替换。

## Anti-patterns
- 一个变量既作输入又把结果带回调用方（对参数赋值）。
- 保存一份"随源数据更新而手工同步"的累计/派生字段，忘记同步即埋雷。
- 用多个独立对象代表同一个实体，且实体可变——数据不一致的温床。
- 无节制地使用全局仓库对象。
- 把可变对象当值随意传递，内部状态被偷偷修改。

## Code Examples
以查询取代派生变量（ProductionPlan）——数据重复的典型消除：

Before:
```js
get production() {return this._production;}
applyAdjustment(anAdjustment) {
  this._adjustments.push(anAdjustment);
  this._production += anAdjustment.amount; // 数据重复：累计值可即时算出
}
```
After:
```js
applyAdjustment(anAdjustment) {
  this._adjustments.push(anAdjustment);
}
get production() {
  return this._adjustments.reduce((sum, a) => sum + a.amount, 0);
}
```

## Key Takeaways
- 变量多次赋值先问"是不是收集变量"，不是就拆，并尽量声明为 `const`。
- 改字段名走渐进路线：封装 → 内部改名 → 兼容旧名 → 迁移调用方 → 删旧名；测试挂了就说明步子太大。
- 派生变量是数据重复；用断言验证"可即时计算"的猜想后再替换。
- 共享数据需要更新时用引用 + 仓库；只读传递用不可变的值对象 + 基于值的相等性。
- 值对象必须不可变，且覆写相等性时同时覆写散列码。
- 全局仓库要节制，能传参就传参。
