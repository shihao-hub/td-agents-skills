# Chapter 12: 处理继承关系（Dealing with Inheritance）＋ 附录速查表

## Core Idea
继承是强大却常被误用的特性：特性（函数/字段）需要在继承体系里上下搬移，继承结构本身需要随演化增删折叠；当继承被用错地方（只能表达一个变化方向、超类接口不完全适用、耦合过强），就转化为委托。Fowler 的策略是"先（尽量）用继承，出问题再用委托这瓶后悔药"。

## Frameworks Introduced（本章全部重构手法）

- **函数上移（Pull Up Method）**：子类中重复的函数是滋生 bug 的温床（改一漏一）。做法：确认各子类函数体完全一致（不一致先参数化或塑造模板函数 Form Template Method 使其一致），确认引用的特性能从超类访问，复制到超类、逐个删除子类版本、每次测试。动态语言里被上移函数引用的子类特性，可用"子类未履行职责错误"（SubclassResponsibilityError）陷阱函数显式声明契约。
- **字段上移（Pull Up Field）**：各子类重复声明、以相同方式使用的字段提升到超类（protected 即可），同时为把相关行为上移铺路。动态语言中它常是构造函数本体上移的必然结果。名字不同先用变量改名统一。
- **构造函数本体上移（Pull Up Constructor Body）**：构造函数受语言规则限制，不能像普通函数那样直接提炼上移。做法：移动语句把公共语句挪到 super 调用后，逐条提升到超类构造函数、所需值作参数传入；无法简单提升的公共行为（如依赖子类先初始化的字段）先提炼函数再函数上移。太复杂就转用以工厂函数取代构造函数。
- **函数下移（Push Down Method）**：超类中只与一个（或少数）子类相关的函数下移到真正需要它的子类。仅当超类明确知道哪些子类需要时适用；不知晓就用以多态取代条件表达式。做法：复制到需要的子类→删超类版本→从不需要的子类删除→测试。
- **字段下移（Push Down Field）**：只被部分子类使用的字段搬到那些子类。做法与函数下移同构。
- **以子类取代类型码（Replace Type Code with Subclasses，包含旧手法：以 State/Strategy 取代类型码、提炼子类）**：类型码触发不同行为/携带类型专属数据时，用多态子类取代。直接继承（Employee←Engineer）简单，但类别不可变、且类别不能复用于其他继承轴；需要可变类别或类别独立成轴时，先以对象取代基本类型包装类型码再对它用本手法（间接继承，即旧版 State/Strategy）。做法：自封装类型码→逐个建子类覆写取值函数→以工厂函数取代构造函数安放选择器逻辑（直接继承方案）→全部迁移后去除类型码字段与验证逻辑→用多态/函数下移消化类型码访问函数。
- **移除子类（Remove Subclass，曾用名：以字段取代子类）**：子类支持的差异已消失或只剩一个返回值的覆写时，子类的存在成本（读者理解成本）超过价值，用超类中的一个类型字段取代。做法：先以工厂函数取代构造函数封装创建、把 instanceof 检查提炼并搬移到超类，再逐个把子类折叠为字段值。注意给所有取值（含默认）平等分配类型码，消除"为什么默认没有代码"的困惑。
- **提炼超类（Extract Superclass）**：两个类做相似的事，把共同点提炼到新超类。合理的继承常在演化中浮现，不必预先规划。与提炼类（委托）二选一收拢重复行为；提炼超类更简单，先试它，选错有以委托取代超类兜底。做法：建空超类→构造函数本体上移/字段上移/函数上移逐个搬共同元素→相似而不同名的函数先改名统一（如 totalAnnualCost→annualCost）再上移。
- **折叠继承体系（Collapse Hierarchy）**：子类与超类已无显著差别时合并。选哪个名字留下看未来哪个更有意义；用上移/下移手法把所有元素并到一个类，调整引用点，删空类。
- **以委托取代子类（Replace Subclass with Delegate）**：继承的两大短板——这张牌只能打一次（一个继承轴），以及超类/子类强耦合（改超类易破坏子类）。用委托（State/Strategy 结构）把子类差异移入委托类：工厂函数封装创建→建委托类（持子类特有数据 + 指回宿主的反向引用）→宿主加委托字段→逐个搬移函数并在宿主留分发逻辑（`this._delegate ? delegate.x : 默认`）→删子类。子类调用 super 版本的扩展型覆写，把超类逻辑提炼成"基础计算 + 委托扩展"两段避免无穷递归。可以一次消灭整个继承体系（鸟类示例）：多个委托类出现重复时，用提炼超类提炼共同的 SpeciesDelegate 超类放默认行为，宿主的分发函数因此不再需要卫语句。收益是状态可变（可运行时 bePremium）、继承轴腾给更需要的变化方向；代价是分发逻辑与双向引用，"是否值得"取决于需求。
- **以委托取代超类（Replace Superclass with Delegate，曾用名：以委托取代继承）**：超类的函数对子类并不全适用（Stack extends List），或"类型与实例名不符实"（type-instance homonym：卷轴 Scroll 并不是目录项 CatalogItem，多卷共享一个目录条目）——这些根本不该是继承。做法：子类中新建字段引用超类实例，为每个超类函数写转发函数（设值/取值一对一起转），全部转发后去掉继承关系。转发函数乏味但极简单。后续可接将值对象改为引用对象，让多个宿主共享同一委托实例。

## Key Concepts
- **针对差异编程（Programming-by-Difference）**：子类只描述自己与超类的差异，避免重复又明确表意。
- **被拒绝的遗赠（Refused Bequest）**：子类用不到超类的部分函数/字段——继承被误用的经典坏味道。
- **类型与实例名不符实（Type-Instance Homonym）**：把"类别记录"误建为"具体事物"的父类（目录项 vs 卷轴）。
- **组合优于类继承（Composition over Inheritance）**：GoF 原则；Fowler 的解读是"审慎地组合使用对象组合与类继承，优于单独使用任何一种"，而非"继承有害"。
- **状态模式/策略模式（State/Strategy Pattern）**：以委托取代子类的目标结构；间接继承版的以子类取代类型码即由此而来。
- **子类未履行职责错误（SubclassResponsibilityError）**：借鉴 Smalltalk，用抛错陷阱函数在动态语言中声明抽象契约。
- **选择器逻辑（Selector Logic）**：工厂函数中把类型码映射到子类/委托类的分发代码。
- **反向引用（Backreference）**：委托类持有指向宿主对象的字段，用于访问本属超类的数据。

## Mental Models
- **继承是"只能打一次的牌"**：一个类只有一个继承轴；多个变化方向（品种 × 野生/家养）必须有一个改用委托。
- **继承的合法性检验**：子类用得上超类的所有函数，且子类所有实例都是超类的实例——两条不满足就换委托。
- **先继承后委托的演化路径**：继承便宜直接，适合起步；需求变化（动态类别、第二个继承轴、跨模块耦合）出现时，用委托手法可靠地换轨——"能可靠地改变决定"比初始设计正确更重要。
- **继承体系是随演化浮现的**：不必预先按"真实世界分类学"设计；发现重复就提炼超类，失去差异就折叠/移除。

## Anti-patterns
- 让 Stack 继承 List只为复用存储——超类的全部不适用操作都泄进了子类接口。
- 让 Scroll 继承 CatalogItem——一物多实例 vs 目录一条目的建模错误，数据同步隐患。
- 在委托/多态结构里写 `instanceof NorwegianBlueParrotDelegate` 式显式类型检查——"几乎总是坏主意"；应让各委托类实现默认行为（由共同委托超类提供）。
- 为"将来可能的功能"预留子类（夸夸其谈通用性）——子类存在就有成本，用处太少就移除。
- 超类函数的组织只为方便特定子类覆写——超类结构被子类"绑架"，改超类时易破坏子类。
- 一个类型码既做直接子类分发又要求运行时可变——类别可变时坚持直接继承必然碰壁。

## Code Examples
以委托取代子类（本章最有代表性：继承→委托的完整转化）：

```js
// Before：继承表达"高级预订"差异
class Booking {
  get hasTalkback() { return this._show.hasOwnProperty('talkback') && !this.isPeakDay; }
}
class PremiumBooking extends Booking {
  constructor(show, date, extras) { super(show, date); this._extras = extras; }
  get hasTalkback() { return this._show.hasOwnProperty('talkback'); }
  get basePrice()   { return Math.round(super.basePrice + this._extras.premiumFee); }
}

// After：一个 Booking 类 + 可动态挂载的委托（继承轴腾空，状态可变）
function createPremiumBooking(show, date, extras) {
  const result = new Booking(show, date);
  result._bePremium(extras);
  return result;
}
class Booking {
  get hasTalkback() {
    return this._premiumDelegate
      ? this._premiumDelegate.hasTalkback
      : this._show.hasOwnProperty('talkback') && !this.isPeakDay;
  }
}
class PremiumBookingDelegate {
  constructor(hostBooking, extras) { this._host = hostBooking; this._extras = extras; }
  get hasTalkback() { return this._host._show.hasOwnProperty('talkback'); }
}
```

## Key Takeaways
- 上下搬移手法（上移/下移 × 函数/字段/构造函数本体）是继承体系的日常维护工具；重复即信号。
- 类型码→子类走两步：先自封装类型码，再逐个建子类 + 工厂函数安放选择器；类别需要可变或要复用继承轴时用间接继承（包一层类型码对象）。
- 子类不是免费的：读者要理解它的用意；只剩一个返回值的覆写就移除子类，折叠为字段。
- 继承合法性两条检验（全函数适用、is-a 成立）不满足 → 以委托取代超类；继承轴不够用或需要动态改变差异 → 以委托取代子类。
- 委托不是终点：多个委托类的重复用提炼超类收拢，"组合与继承审慎地组合使用"。
- 整个继承体系可以被委托体系逐子类替换，一次处理一个、从最简单的子类开始、每步测试。
- 动态语言中用 SubclassResponsibilityError 陷阱函数补上抽象契约的表达。
