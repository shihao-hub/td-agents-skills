# Chapter 1: Introduction

## Core Idea
IPC (interprocess communication) is message passing between processes, plus the synchronization forms that newer IPC (like shared memory) requires. Stevens organizes all Unix IPC by four properties: what it shares, how long it persists, how it is named, and how fork/exec/exit affect it.

## Frameworks Introduced
- **Evolution of message passing**: pipes → FIFOs → System V message queues → Posix message queues → RPC. Use each stage when the previous one's restriction (common ancestor, System V-only heritage, single host) binds.
- **Three ways to share information (Figure 1.1)**: (1) shared file in the filesystem (kernel involved on every access via read/write/lseek), (2) shared information within the kernel (pipes, System V message queues/semaphores — every access is a system call), (3) shared memory between processes (kernel not involved after setup, but processes must synchronize).
- **Persistence taxonomy (Figure 1.2)**: process-persistent (until last open process closes), kernel-persistent (until reboot or explicit deletion), filesystem-persistent (survives reboot until explicitly deleted).
- **Name space concept**: every IPC for unrelated processes needs a name/identifier; the set of possible names is that IPC's name space, and it is how client and server connect.
- **Wrapper functions**: capitalize the real function name (e.g., `Sem_post`); the wrapper calls the lowercase function, terminates via `err_sys` on error. Use whenever terminating on error is the common case.
- **Road-map example patterns**: file server (message passing), producer-consumer (synchronization + shared buffer), sequence-number-increment (shared memory + locking).

## Key Concepts
- IPC: message passing between processes running on an operating system; this text also covers synchronization.
- Related processes: processes with a common ancestor, generated by one or more forks.
- Threads share all global variables within a process; shared memory is inherent to the model — only synchronization is the concern.
- Process-persistent IPC: pipes and FIFOs — discarded when the last process holding it open closes it.
- Kernel-persistent IPC: System V IPC; Posix IPC must be at least kernel-persistent, may be filesystem-persistent.
- Name space: the set of possible names for a given type of IPC.
- errno: set to a positive E-constant only when an error occurs; per-thread when `-D_REENTRANT` is defined; no error has value 0.
- Pthreads (Posix.1c-1995): thread standard; mutexes and condition variables can also synchronize between processes.
- Posix.1 = IEEE 1003.1-1996 (base API + realtime 1003.1b-1993 + Pthreads 1003.1c-1995); Unix 98 is a superset.

## Mental Models
- Think of pipes/FIFOs as process-persistent despite living in the kernel: data is discarded on last close, not on reboot.
- Use kernel-mediated sharing (pipes, SysV queues) when you want every access checked by the kernel; use shared memory when you want speed and accept providing your own synchronization.
- Think of the IPC name as the "rendezvous point": the server creates the named object, clients open the same name.
- Use wrapper functions (capitalized names) as a bookkeeping device: any capitalized function in the text terminates on error.

## Anti-patterns
- Assuming persistence from where the object lives: FIFOs have filesystem names yet are process-persistent; don't reason "in kernel ⇒ kernel-persistent."
- Assuming Posix features are always present: semaphores, message queues, shared memory objects are optional (`_POSIX_SEMAPHORES`, `_POSIX_MESSAGE_PASSING`, `_POSIX_SHARED_MEMORY_OBJECTS`); check Figure 1.5 availability, not just "it's Posix."
- Ignoring the effect of fork/exec/exit on unnamed synchronization variables in multithreaded programs — messy; only variables in shared memory with the process-shared attribute survive.
- Treating errno as meaningful after a successful call — its value is undefined unless an error occurred.

## Code Examples
```c
void
Sem_post(sem_t *sem)
{
    if (sem_post(sem) == -1)
        err_sys("sem_post error");
}
```
*What it demonstrates:* the book's wrapper-function convention — capitalize the name, test the return, terminate on error.

```c
int n;
if ((n = pthread_mutex_lock(&ndone_mutex)) != 0)
    errno = n, err_sys("pthread_mutex_lock error");
```
*What it demonstrates:* Pthread functions return the errno value instead of setting errno; wrappers hide this (needed because only the calling thread blocks on an empty pipe, and error style differs).

## Reference Tables
Persistence of IPC objects (Fig 1.3):

| Type of IPC | Persistence |
|---|---|
| Pipe, FIFO | process |
| Posix mutex / condition variable / read-write lock | process |
| fcntl record locking | process |
| Posix message queue, named semaphore | kernel |
| Posix memory-based semaphore | process |
| Posix shared memory | kernel |
| System V message queue / semaphore / shared memory | kernel |
| TCP / UDP / Unix domain socket | process |

Name spaces (Fig 1.4, abbreviated):

| Type of IPC | Name to open/create | Identification after open |
|---|---|---|
| Pipe | (no name) | descriptor |
| FIFO | pathname | descriptor |
| Posix message queue | Posix IPC name | mqd_t value |
| Posix named semaphore | Posix IPC name | sem_t pointer |
| Posix memory-based semaphore | (no name) | sem_t pointer |
| Posix shared memory | Posix IPC name | descriptor |
| System V IPC (all three) | key_t key | System V IPC identifier |
| TCP/UDP socket | IP addr & port | descriptor |

Availability (Fig 1.5): Unix 98 makes mutexes, CVs, read-write locks, record locking, System V IPC mandatory; Posix message queues (`_POSIX_MESSAGE_PASSING`), semaphores (`_POSIX_SEMAPHORES`), shared memory objects (`_POSIX_SHARED_MEMORY_OBJECTS`), realtime signals (`_POSIX_REALTIME_SIGNALS`) are optional; read-write locks and doors are not in Posix.1-1996.

## Worked Example
Choosing IPC via Figure 1.1: two processes must share data. Option 1 — put it in a file: works for any processes, but every access goes through the kernel and readers/writers need locking. Option 2 — keep it in the kernel (a pipe): kernel mediates each operation via system call, synchronization built in. Option 3 — shared memory: set up once, then zero kernel involvement per access, fastest, but the processes must supply their own synchronization (mutex/semaphore). Stevens uses this triangle throughout the book: any IPC technique is a point on it, and the producer-consumer / sequence-number examples exercise the synchronization each point demands.

## Key Takeaways
- Classify every IPC object by persistence (process / kernel / filesystem), name space, and fork/exec/exit behavior before choosing it.
- Most IPC is not intended to survive reboot; requiring filesystem persistence would degrade performance — a common IPC design goal is high performance.
- All techniques work with any number of processes; "two processes" in figures is just for simplicity.
- Prefer Posix interfaces where available, but verify optional features via the `_POSIX_*` / `_XOPEN_REALTIME` constants at compile time.
- Always check every function call for errors; wrapper functions (capitalized) keep this affordable.
- Compile threaded code with `-D_REENTRANT` (or `-D_POSIX_C_SOURCE=199506L`) to get a per-thread errno.
