# 01-SublimeMerge非相邻提交Squash合并与移动重排操作指南

## 一、核心痛点与现象

在 Git 仓库演进中，常常需要把两个提交合并为一个（例如一次大功能提交 + 一次随后的细节修补或遗漏文件补全）。
但在很多情况下，**这两个提交在物理时间线上并不是紧邻的**（例如中间夹着另一个子项目或工具的提交，如下图所示）：

```text
4c50f03 (HEAD) zedhub:feat: Agent 下拉项按会话数量降序排序...  <-- 想要合并
54b5543        standalone_scripts:feat: 通用 LSP 管理器...       <-- 夹在中间的提交
3b9aba4        zedhub:feat: 支持 Claude/Codex/Pi 会话正文气泡... <-- 目标合并基底
```

### 为什么直接鼠标拖拽会失败？
Sublime Merge 的鼠标拖拽合并（Drag & Drop Squash）仅在提交物理相邻时支持直接吸附；当两个提交中间隔着其他提交时，拖拽往往无法响应或无法放置到目标提交上。

---

## 二、标准实操方案（两种 100% 成功的手法）

### 方案 A：`Ctrl` 多选合并（最快捷，推荐）

Sublime Merge 原生支持对非相邻选区进行批量操作：

1. **多选两个提交**：
   - 鼠标左键点击最新的提交（例如 `4c50f03`）；
   - **按住键盘上的 `Ctrl` 键不放**，再去点击较早的目标提交（例如 `3b9aba4`）；
   - 此时在提交树列表中，这两个提交会被同时蓝色高亮选中。
2. **右键打开上下文菜单**：
   - 右键点击高亮选区 ➔ 展开 **`Edit`** 级联菜单。
3. **选择合并策略**：
   - **`Squash Selected Commits`**：合并两个提交的代码改动，并弹出一个小窗口，允许你把两个提交的 Commit Message 拼接编辑为一个；
   - **`Squash Selected Commits, ignoring new messages (fixup)`**：合并两个提交的代码改动，但自动丢弃新提交的标题，直接沿用旧提交（`3b9aba4`）的原始提交信息。

---

### 方案 B：移动重排 + 父提交合并（最稳健）

如果多选菜单由于特定界面版本原因置灰，可以采用“物理重排”策略：

1. **下移最新提交**：
   - 鼠标右键点击最顶部的提交（`4c50f03`）；
   - 选择 **`Edit` ➔ `Move Commit Down`**；
   - *（Sublime Merge 会自动执行交互式 rebase，把该提交下移一行，使其直接紧挨在目标提交 `3b9aba4` 正上方）*；
2. **与父提交合并**：
   - 移动到位后，再次右键点击该提交；
   - 选择 **`Edit` ➔ `Squash with Parent`**；
   - 确认后，两者立即合二为一。

---

## 三、避坑技巧：为什么合并后会“误以为没反应”？

很多人在点击 `Squash` 之后，由于 Sublime Merge 没有弹出成功提示框，会误以为“界面没反应、操作失败了”。实际上它已经在后台瞬间无感完成！

### 判定合并已成功的 4 个确凿证据：

1. **旧提交从树中消失**：
   - 原先在最顶部的旧提交（如 `4c50f03`）已经彻底从 Commit 列表中消失了。
2. **生成了全新的合并 Hash**：
   - 目标提交的 Hash 会发生改变（变基生成了新提交，如 `940a891`），时间会刷新为当前操作时间。
3. **右侧面板的 `Stats` 发生变化**：
   - 点击该新提交，查看右侧面板的 `Stats: N files changed`：原本分散在两个提交里的所有文件（例如从 7 个变成了 8 个）已经全部汇集在这同一个提交里。
4. **中间夹着的提交被自动平移**：
   - 原本夹在中间的提交（如 `standalone_scripts`）会自动保留在分支最顶部（HEAD），分支线整洁顺滑。
