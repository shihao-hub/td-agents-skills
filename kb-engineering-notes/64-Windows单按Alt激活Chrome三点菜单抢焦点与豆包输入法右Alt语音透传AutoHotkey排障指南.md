# Windows 单按 Alt 激活 Chrome 三点菜单抢焦点与豆包输入法右 Alt 语音透传 AutoHotkey 排障指南

> **适用场景**：在 Google Chrome 等 Chromium 浏览器中，单按或松开 <kbd>Alt</kbd> 键（特别是使用豆包输入法时频繁按 <kbd>右 Alt / RAlt</kbd> 进行语音录入或唤醒 AI），浏览器右上角的“三个点”（自定义及控制 Google Chrome）按钮突然被浅灰色/浅蓝色高亮选中；网页内正在打字的输入框瞬间失去光标焦点；豆包输入法语音识别转写后无法正常上屏，甚至按回车直接误弹出 Chrome 主菜单。

---

## 一、现象与报错直击

### 1. 现场一：右上角三点菜单无故高亮，输入焦点被剥夺

在 Chrome 中浏览网页或在文本框（搜索框、聊天窗口、编辑器）中打字时：
- 手指轻按或松开 <kbd>Alt</kbd> 键（无论是左 Alt 还是右 Alt）；
- 右上角的「三个点」图标立即呈现圆形高亮背景，并弹出原生悬浮提示：`自定义及控制 Google Chrome`；
- 页面当前输入框的闪烁光标瞬间消失，键盘焦点被强行转移至浏览器顶层外壳 UI。

### 2. 现场二：豆包输入法长按 RAlt 录音，松手后文字无法上屏

豆包输入法（Windows 版）默认将核心语音输入绑定在 **右侧 Alt（RAlt）**：
- 用户在 Chrome 网页中长按 <kbd>RAlt</kbd> 说话，豆包正常录音并流式转文字；
- 说话结束松开手指的瞬间，Windows 将 `RAlt Up` 判定为“单按 Alt 结束”，立刻触发 Chrome 菜单高亮；
- 此时网页输入框失去活动焦点（`document.activeElement` 丢失），豆包准备上屏的文本因找不到受体而丢失；
- 用户习惯性敲击空格或回车尝试确认文字，反而直接展开了 Chrome 的全局控制菜单，严重阻断打字心流。

---

## 二、底层根因剖析

### 1. Win32 系统的菜单激活协议（`SC_KEYMENU` / `WM_SYSCOMMAND`）

自 Windows 95 起，Windows 窗口管理器（User32 / DefWindowProc）便规定了系统级快捷键行为：

```text
用户按下 Alt 键 (WM_SYSKEYDOWN / VK_MENU)
       │
   [检测期间是否有其他按键按下？]
   ├── 有组合键 (如 Alt + Tab, Alt + D) ──> 触发对应业务逻辑，不激活菜单
   │
   └── 孤立释放 (WM_SYSKEYUP，无任何其他键)
              │
              ▼
   向顶层活动窗口发送消息:
   WM_SYSCOMMAND, wParam = SC_KEYMENU (0xF100)
```

- **传统应用（记事本等）**：收到 `SC_KEYMENU` 后，激活窗口顶部的横向菜单栏（高亮“文件(F)”）；
- **现代 Chromium 架构（Chrome / Edge 等）**：移除了传统横向菜单栏，将全量功能折叠至右上角的三点主控制按钮（快捷键等价于 `Alt + F`）。为严格遵循 Windows 无障碍交互规范，Chromium 内核响应 `SC_KEYMENU` 的默认行为就是**将 UI 焦点直接赋予三点菜单按钮**。

### 2. 美式英语键盘布局下 `RAlt` 与 `LAlt` 的对称性

在标准美式键盘布局（US QWERTY，国内绝大多数 PC 默认）中：
- 左 Alt（`VK_LMENU`）与右 Alt（`VK_RMENU`）在系统底层统归为 `VK_MENU` (0x12)；
- 仅在非英语国际布局（如带 `AltGr` 键的欧洲键盘）中，右 Alt 才会特殊映射为 `Ctrl + Alt`；
- 因此在 Windows 默认环境下，**单按右 Alt 与单按左 Alt 同样会产生毫无二致的 `SC_KEYMENU` 菜单激活命令**。

### 3. 豆包输入法与 Chrome 焦点状态机竞态

豆包输入法的语音输入生命周期由底层键盘钩子（`WH_KEYBOARD_LL`）驱动：

```text
[用户按住 RAlt 说话] ──> 豆包 LL 钩子捕获 Down ──> 开启麦克风音频流
                              │
[用户松开 RAlt]      ──> 豆包 LL 钩子捕获 Up   ──> 停止音频，请求大模型转写
                              │
                              └── 系统消息泵将 Up 抛给 Chrome 窗口
                                        │
                                        ▼
                               Chrome 触发 SC_KEYMENU
                               网页输入框 blur (失焦)！
                                        │
                                        ▼
                              豆包识别文本完成，尝试向失焦窗口发字 ──> 上屏失败/乱入
```

## 三、解决方案与 AutoHotkey 掩码机制

### 1. 核心防御机制：Windows 菜单判定击溃（Menu Mask Key）

Windows 判定是否派发 `SC_KEYMENU` 的判定是极其脆弱的状态机：**只要在按下 Alt 到抬起 Alt 的期间，系统消息队列中记录到了任何一个有效键码（无论该键码是否映射了具体功能），状态机就认为当前是一次“组合快捷键”，从而自动取消派发 `SC_KEYMENU`**。

#### 为什么不能盲发 `{Esc}`？
市面上常见的一种简易脚本是在 `Alt Up` 时发送 `{Esc}`（试图关闭刚刚高亮的菜单）。
**这是极度危险的反模式**：当用户使用豆包输入法时，输入法可能正处于文本候选（Composition）状态，突发性的 `{Esc}` 会直接将输入法的候选词框强行清空撤销！

#### 正确标准：使用 `vkE8`（未分配虚拟键）
`vkE8`（Virtual Key Code 0xE8）是微软官方在 `winuser.h` 中明确保留的 **Unassigned（未分配）** 虚拟键码：
- 任何操作系统、输入法、浏览器或业务软件都不会对 `vkE8` 绑定任何业务逻辑；
- AutoHotkey 官方内置的修饰键消除变量 `A_MenuMaskKey` 官方推荐值亦为 `vkE8`；
- 它只起到一个作用：**告诉 Windows“刚才有按键组合发生”，让 Chrome 彻底闭嘴，同时不产生任何字符与副作用**。

### 2. 生产级实战代码（针对 AutoHotkey v2）

在开机自启的 AutoHotkey 脚本（如 `app_switcher.ahk`）中，加入以下针对 Chrome 的精准规则：

```ahk
; ========================================================
; 修复 Chrome 中单按 Alt (特别是豆包输入法占用右 Alt / RAlt) 导致右上角三点菜单被高亮选中的问题
; 1. ~ 修饰符代表按键透传，豆包输入法仍能正常捕获 RAlt/LAlt 的按下与长按录音
; 2. Send "{Blind}{vkE8}" 向系统发送无害未分配键码，消除 Windows 菜单栏激活 (SC_KEYMENU) 机制
; ========================================================
#HotIf WinActive("ahk_exe chrome.exe")
~RAlt::Send "{Blind}{vkE8}"
~LAlt::Send "{Blind}{vkE8}"
#HotIf
```

#### 代码要点剖析：
1. **`~`（波浪号透传）**：至关重要！如果不带 `~`，AutoHotkey 会完全拦截吞噬该物理键，豆包输入法就会变成“聋子”收不到语音唤醒。带上 `~`，豆包输入法的底层钩子原封不动地收到物理 `RAlt Down`，录音流毫秒级拉起；
2. **`Send "{Blind}{vkE8}"`**：在物理键落下的微秒级瞬间注入无害键，完成对 Windows 菜单状态机的“静默拆弹”；
3. **`#HotIf WinActive("ahk_exe chrome.exe")`**：严格限定作用域，仅在前台为 Chrome 时生效，避免影响其他可能依赖 Alt 菜单的特定桌面软件。

---

### 3. 免脚本平替方案：在豆包输入法中切换为「右 Ctrl」

如果你不想运行任何常驻脚本，也可以直接在豆包输入法自身配置中实现完美规避：

1. 右键任务栏右下角的 **豆包输入法图标 ➔ 设置**；
2. 进入 **快捷键** 面板；
3. 将语音输入唤醒键从 `右 Alt` 更改为 **`右 Ctrl`（RCtrl）** 或 **`右 Shift`**。

| 对比维度 | 右 Alt (RAlt) 原生 | 右 Ctrl (RCtrl) 替代方案 | AHK 掩码透传方案 (本文) |
|---|---|---|---|
| **按键位置** | 空格右侧 | 右 Alt 旁边（相隔一个或紧挨） | 维持原位不变 |
| **肌肉记忆** | 无需改变 | 需 1~2 天适应右移 1~2 厘米 | 完全无需改变 |
| **Chrome 抢焦点** | 严重（频繁选中三点） | **零冲突**（Windows 单按 Ctrl 从不激活菜单） | **已彻底消除** |
| **对其他软件侵入** | 依赖全局环境 | 零额外脚本常驻 | 仅需已有 AHK 进程挂载 2 行规则 |

## 四、验证与防复发闭环

修改并重新加载 AutoHotkey 脚本后，按以下三步进行全功能验证：

- [ ] **验证 1：单按 Alt 焦点稳固**
  在 Chrome 打开任意网页（如 Bing/Google），点击输入框使光标闪烁，轻按并松开 <kbd>右 Alt</kbd>。
  *预期*：右上角三点菜单无任何高亮背景、无悬浮提示，输入框光标依然持续闪烁。
- [ ] **验证 2：豆包语音输入与正常上屏**
  在输入框内长按 <kbd>右 Alt</kbd>，麦克风正常收音；说一句完整句子后松手。
  *预期*：输入法转写文字准确上屏进入输入框，光标停留在文字末尾，无多余按键回车或弹窗干扰。
- [ ] **验证 3：组合快捷键兼容性**
  在 Chrome 中按下 <kbd>Alt</kbd> + <kbd>Tab</kbd> 切窗口、<kbd>Alt</kbd> + <kbd>D</kbd> 定位地址栏、<kbd>Alt</kbd> + <kbd>←</kbd> 后退页面。
  *预期*：所有常规 Alt 组合快捷键均保持原有功能无任何退化。
