# Git 批量提交代码 Agent 高思考档分析瘫痪根因排障与灰色资产判决指南

> **适用场景**：用户发出类似 `monorepo 提交全部代码` / `git commit push` 的明确交付指令时，Agent 却在思考链中陷入长达数分钟的推理停滞；思考链中反复纠结某个非代码未跟踪文件（如 `test_*.png`、`*_bak.png`）的来龙去脉、甚至调用 Python 工具反查图片分辨率与源码引用；或把一次常规的提交流水线误当成全库重构审计，导致整体流转极度缓慢。

---

## 一、现象与报错直击

### 1. 现场一：批量提交指令触发超长思考停滞
用户输入一句利落的交付指令：
```text
/sh-user-skills monorepo 提交全部代码
```
模型（尤其在 High/Max 思考档位下）并没有迅速梳理 git status 执行暂存提交，而是陷入数分钟的内部推理（Thinking Token 消耗数千至上万），用户体验表现为“界面卡住、AI 迟迟不动”。

### 2. 现场二：陷入“边缘灰色文件”的微观考古
在状态扫描中遇到未跟踪文件：
```text
?? taskbarguard/scripts/vscode/current_extracted_code_exe.png
?? taskbarguard/scripts/vscode/test_extracted_bak.png
```
Agent 触发过度推理陷阱：
- 怀疑是“运行时垃圾”（因文件名带 `test_` 和 `_bak`），害怕违背“禁止提交运行时产物”规范；
- 同时又害怕误删资产，违背“禁止擅自删除未知文件”规范；
- 于是调用工具读取图片二进制/分辨率、反查脚本代码是否有提取逻辑、逐行推演此图是谁在何时生成的；
- 导致核心提交流程被两个边缘测试图片严重阻塞。

### 3. 现场三：SOP“审查清单”诱导逐行重审已有稳定代码
SOP 文本中若包含：
> “审查至少包括：入口、核心业务逻辑、数据路径、CLI/MCP 契约、文档真实行为、并发与资源生命周期...”

Agent 会将该清单视为**硬性前置阻塞条件**，试图在 commit 前把整个子仓每一个存量子项目的业务逻辑与架构全盘重审一遍，诱发严重的**分析瘫痪（Analysis Paralysis）**。

---

## 二、深度根因剖析

### 1. 思考档位认知膨胀（Reasoning Budget Bloat）
在高思考档（High/Max）下，模型拥有极充裕的推理 Token 预算。当规则出现**模糊区间**或**冲突边界**时，低思考档模型倾向于直接按常理执行，而高思考档模型会竭力穷尽推演所有潜在边界与假设分支，导致“过度谨慎带来极度迟缓”。

### 2. 资产判定规则存在“灰色死角”
传统 Git 规则通常是非黑即白的二元对立：
- **白名单**：源码、文档、正式配置文件 ➔ 提交；
- **黑名单**：`.venv/`、`__pycache__/`、`*.test`、`dist/`、锁文件、自产数据库 ➔ 排除/清理。

**盲区在于灰色地带**：位于源码目录下的测试对比样本（`test_*.png`）、参考数据、实验临时脚本。既不是标准编译产物，也不是核心业务代码。缺乏确定性的默认判定策略时，Agent 就会反复横跳。

### 3. “提交流水线”与“代码重构审查”的意图混淆
用户的诉求是**交付流（Delivery Pipeline）**：把当前工作区变动按仓库与项目边界打包、经自动化测试检验后安全推送；  
而 SOP 原文过细的检查列表把流程误导成了**审计流（Audit Pipeline）**，造成职责漂移。

---

## 三、排障与防御机制（10 秒快速判决法则）

### 1. 意图分流：全量交付 vs 深度审计

```text
用户指令判断
 ├─ 批量交付模式（"提交全部代码" / "commit push"）
 │    └─ 聚焦边界隔离 + 自动化验证（go test/cargo test/uv test） ➔ 绿灯即提交推送
 └─ 深度审计模式（"逐项审查代码质量" / "review 代码"）
      └─ 深入业务逻辑、并发、接口契约与异常链路
```

- **全量交付模式下**：以项目原生的自动化测试/构建命令作为代码可提交性的唯一定量标准。测试通过即视为代码逻辑健康，绝不对已有稳定逻辑展开主观全盘审查。

### 2. 灰色与存疑未跟踪资产三步判定法（Anti-Paralysis Invariant）

对未跟踪文件按以下优先级在 10 秒内完成决策，严禁调用查看二进制、查图片分辨率等深层反查工具：

| 资产类型 | 典型特征 | 处理动作 | 是否阻塞 |
| :--- | :--- | :--- | :---: |
| **敏感特征文件** | `.env`、`*id_rsa*`、含 token/secret 关键词 | **立即阻断**，向用户警示确认 | 是 |
| **标准运行时/构建垃圾** | `.venv/`、`__pycache__/`、`dist/`、`build/`、`*.test`、`coverage`、自产 db/log | **清理或排除**（按 .gitignore） | 否 |
| **项目内灰色/测试样本资产** | `test_*.png`、`extracted_*.png`、样本数据、辅助脚本 | **默认随项目原子提交**，在 commit 中客观记录 | 否 |

- **铁律**：非敏感凭据的非标准生成物，只要位于项目合法目录下，默认作为项目资产保留并随该项目提交。如有重大存疑，在最终汇报中一并列出，绝不在内部思考中反复空转。

## 四、SOP 改造对照（前后对比）

### 修改前（诱发过度审计与反查）：
```markdown
## 阶段 3：逐项目审查与验证
审查至少包括：
- 入口、核心业务逻辑和异常处理；
- 数据路径是否符合项目约定；
- CLI、MCP、schema 或 API 契约；
- 是否存在明显的连接、资源、并发或错误报告问题。
```

### 修改后（快速交付，自动化命令裁决）：
```markdown
## 阶段 3：逐项目审查与验证
### 区分全量交付与深度代码审查（防分析瘫痪）
- **全量提交/批量交付场景**：
  核心目标是项目边界隔离划分、状态归拢与安全交付。审查聚焦于：
  1. 暂存清单严格限定在当前逻辑项目内；
  2. 依赖声明与锁文件匹配；
  3. 执行项目声明的真实自动化验证命令（go test / cargo test / pytest / build）。
  验证通过即判定具备提交基线，果断推进，不卡在主观代码推演上。
- **专项审查场景**：
  仅在用户明确要求审查代码质量时，方按需展开深层审计。
```

---

## 五、复盘与验证检查点

1. **指令响应速度**：接收到“提交全部代码”后，首个工具调用应在 5~15 秒内发起（`git status` / `git diff`），而非进入数分钟的长考；
2. **工具调用纯粹性**：提交流水线中只执行 Git 基础命令与自动化测试构建命令，不出现 `PIL.Image.open` 等针对非代码静态文件的深层元数据探查；
3. **隔离与提交原子性**：各子项目保持独立 commit/push，父仓更新子模块指针保持独立 commit/push，plans 文件保持单文件独占，既快又符合 Monorepo 纪律。
