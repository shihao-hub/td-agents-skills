# Windows内存防死机与Pagefile提交内存归因优化指南

# sh-windows-memory-guard — Windows 内存过载防护与虚拟内存调优

针对“多开开发工具(Zed/VSCode/Cursor)、大模型、Chrome 几十个标签导致内存飙升（90%+），担忧电脑超内存死机或蓝屏”。
核心原则：**用高速 NVMe SSD 虚拟内存构筑兜底防线，以平滑的后台 I/O 换页替代系统死机与 OOM 闪退；配合标签休眠彻底治愈浏览器内存黑洞**。

> **两条最容易误判的定式（2026-10-10 实战校验）**：
> ① **提交内存 ≠ 物理内存**：提交压力的真凶常常是“私有数 GB / 物理十几 MB”的已换出冷数据，在物理 Top 榜上完全隐形；
> ② **物理 87% + 提交余量 7GB 时，正解可能不是“扩容虚拟内存”而是“关掉一个遗留进程”**（本机实测单个 ComfyUI 释放 7.13GB 提交）。

## 七条核心认知（先读这个）

1. **物理内存占满 90%+ 绝不会直接死机或蓝屏**。Windows 拥有成熟的分页机制，物理内存吃满后系统会自动将冷数据转移至硬盘的 `pagefile.sys`。
2. **只有“提交配额（Commit Limit）”耗尽才会发生应用闪退**。物理内存 + 虚拟内存全部耗尽时，系统才会触发 OOM 保护机制强杀进程。只要手动将虚拟内存底座锁定在 32GB~48GB（总提交配额突破 55GB~70GB+），即可彻底杜绝死机与闪退。
3. **“卡顿”是安全代价，非系统故障**。当数据在物理内存和固态硬盘之间置换时，SSD 相对物理内存的延迟差距会导致后台切前台时有 1~2 秒唤醒延迟。这是“用慢换不崩”的正常表现。
4. **虚拟内存置换不产生 CPU 高温，风扇狂转为伴生现象**。虚拟内存换页是存储 I/O，不引起 CPU 发热；开机 40 分钟内风扇狂转源于软件重启后的集中初始化（IDE 索引重建、杀毒扫描、AMD CPU 激进睿频），属正常暂态。
5. **Chrome 等现代浏览器是物理内存的第一膨胀源**。由于多进程沙箱架构、会话恢复全量预加载及流媒体“免死金牌”，浏览器极易在启动时霸占 5GB~8GB+。必须配合精准标签休眠（Discard）剥离冷内存。
6. **物理内存占用量排名 ≠ 提交内存排名，提交压力的真凶往往在物理榜上完全隐形**。典型形态是“私有提交数 GB / 物理工作集仅十几 MB”的**已全量换出冷数据**——遗留的模型服务（ComfyUI 等）、推理后端、忘了关的常驻服务。排查提交压力**必须看 `PrivateMemorySize64`（私有提交），而不是 `WorkingSet64`（物理）**。本机亲测：ComfyUI 私有 6.75 GB / 物理 16 MB，物理 Top 8 里根本看不到它，却是提交爆表的唯一主因。
7. **“剩余提交配额 < 8GB”是需要归因的信号，不是“立即扩容虚拟内存”的判决**。页面文件在“初始值~最大值”区间内会**自动增长**，提交上限随之抬升（本机亲测 32 GB → 36 GB 自动扩容，提交上限 55.22 → 59.29 GB）。正确动作是**先归因（Step 2.5），再决定是否扩容**：能在归因表里定位到可关闭进程的，关掉即回收，根本不用动虚拟内存。

## 工作流

1. 只读体检（`memory-triage.ps1` 输出物理内存、提交配额、页面文件大小及峰值使用）
2. 压力判型（区分是正常高负载换页、虚拟内存不足，还是浏览器/进程内存暴涨）
3. 底座防护加固（通过 `sysdm.cpl` 手动锁定 32GB~48GB 护城河）
4. 应用层内存治理（Chrome 原生性能模式 + Auto Tab Discard 黄金策略）
5. 调优决策与答疑（调优上限边界、系统默认妥协原因、Discard 底层机制）
6. 提交内存归因（`PrivateMemorySize64` 排序，捞出“已换出冷数据”——提交真凶常在物理榜隐形）
7. 物理内存容量判断（`Win32_PhysicalMemory` 读槽位/单条容量，区分“配置未满”与“平台到顶”）
8. 验证与汇报

## Step 1 只读体检

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File <skill目录>\scripts\memory-triage.ps1
```

输出项及诊断重点：
- **物理内存占用率**：超过 85% 触发冷页置换（只要可用物理内存留有 2G~4G 缓冲即属健康）；
- **已提交 (Committed) vs 总配额 (Commit Limit)**：若 Committed 超过 Commit Limit 的 85%，说明提交池亟需扩容；
- **页面文件峰值 (Pagefile PeakUsage)**：大于 1GB 说明系统正平稳利用虚拟内存安全代偿，非系统故障；
- **[5] 提交内存归因 Top 8（按私有提交排序）**：**本 skill 最关键的一块输出**。脚本自动标出“私有 ≥ 500MB 且 物理/私有 < 10%”的**已换出冷数据**候选（行尾带 `<== 疑似换出冷数据` 标记）。物理榜看不见的提交大户，全靠这一块揪出来；
- **[7] 内存硬件与扩容可行性**：输出每条内存的槽位/容量/厂商/频率/料号、插槽占用数、SMBIOS 平台上限，用于回答“该不该加内存条”。

## Step 2.5 提交内存归因（物理榜看不见的大户，在这里）

**核心判据**：把 `PrivateMemorySize64`（私有提交，≈ 该进程实际占用的提交配额）与 `WorkingSet64`（物理）放一起看比值。

| 比值（物理 / 私有） | 含义 | 动作 |
|---|---|---|
| ≥ 50% | 热数据，物理榜也会出现 | 常规排查 |
| 10%~50% | 部分换出 | 观察 |
| **< 10% 且私有 ≥ 500MB** | **近乎全量换出到 pagefile 的冷数据** | **高度可疑——优先确认它是不是遗留服务/忘了关的进程** |

典型命中对象：**遗留的模型服务**（ComfyUI / Stable Diffusion WebUI / 推理后端）、忘了关的数据库、挂了很久没退出的后台任务。

> 本机铁证（2026-10-10）：ComfyUI 私有提交 **6753 MB**、物理 **16 MB**（比值 0.24%）。
> 它在物理 Top 8 里**完全不可见**，却是提交余量只剩 6.29GB 的唯一主因；关闭后提交余量 **6.29 → 13.42 GB**，物理仅降 **0.31 GB**。

**处置纪律**：确认不是正在跑的任务后直接终止。捞进程示例（**当心关键词匹配到脚本自身路径**，见踩坑备忘）：

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match '<服务专有标识>' } |
  Select-Object ProcessId, Name, @{n='Commit_MB';e={[math]::Round($_.PageFileUsage/1KB,1)}}
```

## Step 2.6 物理内存容量判断（该不该加内存条）

只做三件事，就能把“配置未满”和“平台到顶”分开：

1. `Win32_PhysicalMemory` → 读出**每条**的槽位、容量、厂商、频率、料号；
2. `Win32_PhysicalMemoryArray` → 读出 `MemoryDevices`（**总插槽数**）与 `MaxCapacityEx`（**平台上限**）；
3. 对照：**插槽占用 = 总插槽数** ⇒ 加装无门，**只能成对替换**；**占用 < 总数** ⇒ 直接加装即可。

三条硬纪律：

- **禁止单条凑容量**：双通道被打断的代价，在带核显的机型（AMD APU 尤甚）上远大于那点容量收益；
- **插槽满了就必须整组替换**，并优先与原条**同代次、同频率**（DDR5-5600 SODIMM 就继续用 5600）；
- **加内存前先做 Step 2.5 归因**：本机实测清掉一个遗留服务就回收 7.13GB 提交，“该加内存”的结论要在归因之后才成立。

本机实测样例：

```
DIMM 0 / DIMM 0 (P0 CHANNEL A / B) | 12 GB | Crucial | 5600 MHz | CT12G56C46S5.M4B1
插槽占用 : 2 / 2        平台上限 : 128 GB (SMBIOS MaxCapacityEx)
⇒ 24GB 是“配置未满”而非“平台到顶”；扩容走 2×32GB = 64GB（成对替换）
```

## Step 3 处置与调优 SOP

### 3.1 虚拟内存加固配置（系统级防死机核心）

让系统不再受制于动态分配的瞬时延迟，直接开辟大容量安全气囊：

1. 按 `Win + R` 键，输入 `sysdm.cpl` 回车，打开“系统属性”。
2. 点击 **“高级”** 标签页 ➔ “性能”分组框内的 **“设置(S)...”**。
3. 在性能选项中，再次点击 **“高级”** 标签页 ➔ “虚拟内存”分组框内的 **“更改(C)...”**。
4. **取消勾选**最上方的 *“自动管理所有驱动器的分页文件大小”*。
5. 选中剩余空间充足的高速 NVMe SSD 盘符（首选系统 C 盘，空闲建议 >40GB）：
   - 单选 **“自定义大小”**：
   - **初始大小 (MB)**：填写 `32768`（即 32 GB）
   - **最大值 (MB)**：填写 `49152`（即 48 GB）
6. ⚠️ **关键操作**：**必须点击右侧的【设置(S)】按钮**，确认上方列表出现数值变更！
7. 点击【确定】依次关闭窗口，根据系统提示**重启电脑**生效。

### 3.2 Chrome 内存黑洞治理与 Auto Tab Discard 调优（应用级节流核心）

每次重启 Chrome 拉到 5GB+ 的病根：**会话恢复全量加载 DOM + 预加载机制 + 抖音等流媒体拥护“免死金牌”不主动释放**。

#### A. Chrome 原生设置调优
1. **开启省内存模式**：
   - 访问 `chrome://settings/performance`；
   - 开启【省内存模式（Memory Saver）】，并将休眠策略档位选为 **【最大限度（Maximum）】**。
2. **关闭预加载网页**：
   - 访问 `chrome://settings/performance` 或在隐私设置中搜索“预加载”；
   - 将【预加载网页（Preload pages）】设为 **【关闭（No preloading）】**，禁止后台预取页面吃带宽和内存。

#### B. 安装并调优 Auto Tab Discard 扩展
Chrome 原生机制对“正在播放音频/视频、含长连接（如大模型问答）、有表单输入”的标签坚决不休眠（免死金牌）。必须借助 `Auto Tab Discard` 强制执行底层 `chrome.tabs.discard`：

1. **安装**：Chrome 应用商店搜索并安装 `Auto Tab Discard`。
2. **黄金配置项（打开插件选项页逐项配置）**：
   - ✅ **勾选【启动时休眠所有非固定标签页（Discard all inactive tabs on startup）】**（核心：彻底终结启动即吃 5G 的偷跑行为）；
   - ✅ **勾选【启动时休眠全部未加载标签页（Discard unloaded tabs on startup）】**；
   - ✅ **勾选【记录 YouTube 播放进度（Remember YouTube position）】**（休眠后不丢视频进度）；
   - ❌ **取消勾选【打开临时空白页面（Discarded tab opens a temporary blank page）】**（避免切换标签时突兀白屏，保持平滑原位激活）；
   - 💡 **免死金牌裁决**：当开启多个抖音/B 站后台标签吃满数 GB 时，直接点击插件图标 ➔ 选择 **【休眠所有非活动标签页】** 强制回收。

### 3.3 深度原理问答

- **问：为什么调完虚拟内存后，多开 IDE 物理内存也只占 80% 出头？**
  - **答**：系统开机即拥有 55GB+ 提交配额和预分配连续 32GB 空间，内存管理器（Memory Manager）由“紧绷”变为“从容”。当打开新 IDE 时，系统毫秒级将后台闲置软件的冷工作集裁剪（Working Set Trim）并置换进预留的 Pagefile 中，零延迟把物理内存让给前台。
- **问：为什么 Chrome 自带的“省内存模式”感觉用处不大，启动依然 5GB？**
  - **答**：原生省内存策略极其保守。开机恢复上次标签时，它会并发拉起所有网页进程并渲染；且抖音、音乐、大模型长连接会被打上“不可丢弃”标记。Auto Tab Discard 直接调用底层 API 剥离渲染树与 JS 堆，只保留轻量元数据，所以能瞬间从 5G 压降到 2G。
- **问：虚拟内存继续调大到 64GB 或更大，会更好吗？**
  - **答**：**不会**。边际效益递减，32GB~48GB 是黄金甜点位。开满重度工具 Commit 才用了 ~32GB，后面闲置 23GB+。盲目再大不仅无法让电脑更快，反而白白浪费宝贵的 SSD 存储与写入寿命。
- **问：刚开机开齐软件风扇为什么变响？**
  - **答**：开机后 40 分钟内是软件集中唤醒期：Zed/VSCode 密集扫描项目索引、杀毒扫描、AMD 处理器激进睿频冲刺 5.0GHz+ 引发瞬时温升。虚拟内存属于存储冷文件，完全不发热，几分钟后负载下降风扇即自动安静。

## 实战案例（2026-10-03 ~ 2026-10-10 本机压测与闭环）

- **底座加固实测**：通过 `sysdm.cpl` 锁定虚拟内存 32GB（初始 32768MB / 最大 49152MB），总 Commit Limit 达 55.2GB+。
  - 并发压测：同时拉起 **Zed (13 进程) + Cursor + VS Code + Chrome (数十标签) + Vibe助手 (6.3GB) + DeepSeek Harness**；
  - 铁证数据：总提交负载达 **31.90 GB**，`Pagefile PeakUsage: 2.4 GB` 平稳换页，**物理内存稳定在 81.1%~81.9%**，空闲留有 4.2GB 缓冲，彻底杜绝死机与闪退！
- **Chrome 内存黑洞实测**：
  - 初始痛点：Chrome 每次重启拉起会话，后台 5 个抖音等标签吃掉 2.8GB，整体飙升至 **5.1 GB**；
  - 处置验证：关闭预加载网页，配置 Auto Tab Discard 开机全休眠与一键裁决；
  - 铁证数据：执行标签休眠后，Chrome 内存**瞬间从 5.1GB 暴降至 2.0GB**（立省 3GB+ 物理内存），标签点击时毫秒级无缝重载。

### 案例 3：遗留服务白占 7GB 提交却丝毫不占物理（2026-10-10）

- **起点误判**：用户反馈“没开什么软件，但电脑很吃内存”。体检显示物理 87%、提交 88%（余量仅 6.29GB），命中“接近 OOM 警戒线”。
- **物理榜误导**：物理 Top 8 全是正常开发工具（chrome / dwm / opencode / Zed / Cursor），**看不出任何异常**。
- **归因破局**：改按 `PrivateMemorySize64` 排序，立刻揪出 `python.exe (ComfyUI main.py --listen 8188)`——**私有提交 6753 MB，物理仅 16 MB**，自 10-04 起遗留运行 6 天。
- **铁证数据**（关闭前后）：

  | 指标 | 关闭前 | 关闭后 | 变化 |
  |---|---|---|---|
  | 物理已用 | 21.02 GB (91%) | 20.71 GB (89%) | −0.31 GB |
  | 已提交 | 48.93 GB | **41.80 GB** | **−7.13 GB** |
  | 提交余量 | 6.29 GB | **13.42 GB** | **+7.13 GB** ✅ |
  | 页面文件实占 | 4182 MB | 2901 MB | −1281 MB |

- **结论**：**提交内存 ≠ 物理内存**。提交压力要按私有提交归因，而不是盯着物理 Top 榜；同时印证 Step 2 的修正口径——余量 <8GB 时先归因，别急着扩容虚拟内存。

### 案例 4：启动项数量 ≠ 内存占用（同日校准，纠错记录）

- 曾把“21 个启动项”直接换算成“精简可省 1~3GB”，**实测打脸**：
  - 所有**在跑**的启动项合计仅 **≈1.47 GB**，其中 **飞书 983MB** 一家独大；
  - `BaiduYunDetect`（YunDetectService）**仅 9.2 MB**；
  - `Warp`、`ApifoxAppAgent`、`Docker Desktop`、`Claude`、`eudic`、`发送至 OneNote` 等**根本没在运行**（启动项注册存在 ≠ 进程在跑）。
- **纪律**：启动项只说明“可能会起”，**必须按进程名实测**才能谈占用；不要把条目数当占用量。

## 踩坑备忘

- **必须点击【设置(S)】按钮**：在虚拟内存设置界面输入数字后，如果不点击右侧“设置(S)”直接点确定，修改将完全不生效且无任何报错提示。
- **严禁完全关闭虚拟内存**：即使物理内存 64GB+ 也绝不可关闭虚拟内存，许多大型软件和 Windows 核心组件依赖 Pagefile 预留 Commit 空间，关闭极易引发随机崩溃。
- **虚拟内存必须置于高速 NVMe SSD**：机械硬盘做虚拟内存会导致严重系统假死；高速 NVMe SSD 能把换页延迟控制在平滑感知范围。
- **Auto Tab Discard 慎选“打开临时空白页面”**：开启该项会导致点击休眠标签时先跳到扩展空白页再刷新，体验割裂；取消勾选后保持原 URL 就地重新加载，体验最佳。

- **物理榜会系统性漏掉“换出冷数据”**：任何一轮内存排查，都必须**同时**看物理 Top 和私有提交 Top（脚本 [5]/[6] 两块），只看物理榜必然放过最大的那个凶手。
- **提交余量 <8GB 先归因，再谈扩容**：commit limit 会随页面文件在“初始~最大”区间自动增长（实测 32GB→36GB），余量低不等于必须扩容虚拟内存。
- **杀进程时当心关键词自匹配**：用 `CommandLine -match '<关键词>'` 捞进程时，**若本次执行的脚本自身路径含该关键词，会把工具调用自己的 shell 链一起匹配掉**（实测：`kill-comfy.ps1` 因路径含 `comfy` 而自杀，导致脚本没输出 AFTER 数据）。防御写法：① 关键词用**服务专有标识**（如 `main.py --listen 8188`）而非项目名；② 或先打印命中清单，人工确认后再终止。
- **不要用启动项数量推算内存占用**：必须按进程名实测（本机 21 个启动项在跑的合计仅 ~1.47GB）。
- **SODIMM 插槽满了只能成对换**：严禁加装单条凑容量，双通道被破坏在核显机型上代价更大。

- **不要把 ACP agent 的子进程数误读为“多开会话”**：Zed 侧只有一条 ACP 会话链（`Zed.exe` → `powershell.exe` → `agy_acp_server.exe`），底下那十几个 `localharness_external.exe` 是 **Antigravity ACP 服务自己按需 spawn 的常驻子进程池**，随使用时长累积、几乎不回收。实测 14 个进程在 20 秒采样内 CPU 增量全为 0（占着内存不干活），且存在进出 churn。**判据是进程的父子关系，不是进程数量。**
